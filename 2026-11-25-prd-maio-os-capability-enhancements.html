Maio OS - Capability Enhancement PRD

1. Reading of the request

  • The subject is Maio OS, the cockpit served at https://ricardos-mac-mini.taile9f837.ts.net:9443/#wheel, built in T3 Code (Nightly) from the repo above.
  • The request is to enhance every capability the site has, not one section, and to assign the responsibility for that work to Google Neon.
  • Google Neon is read here as the Gemini 4 Neon lane on the Google AI subscription through Antigravity, the lane already configured in this fleet as the hardest-reasoning seat. It is a model lane, not a company entity and not a cloud service the site depends on. If the intent was a different "Neon", say so and this document is re-pointed before any work starts.
  • The enhancement details were not supplied by the requester. Where a target number, date, budget or scope decision is required and cannot be measured from the system, the field reads [unspecified].

2. Product in five lines

  • What it is: a fixed-section household cockpit, one static shell plus a generated snapshot plus a loopback companion, with four folded apps behind the same origin.
  • Who uses it: Ricardo, on this Mac and over the tailnet, to answer "what needs attention now, and where does a record live".
  • What it is not: a public site, a multi-user service, a window desktop, or a React application. Those are non-goals inherited from v2 and not reopened here.
  • What makes it work today: 18 visible sections, a live companion on the same origin, read-only vault access, and five gated fix actions with a cooldown and a log.
  • What this PRD adds: twelve capability workstreams, each with a measured baseline, a stated enhancement, a runnable acceptance test, and Google Neon as the accountable owner.

9. Risks

  • Google Neon is a shared daily quota. A twelve-workstream plan can exhaust it in one day if the lane is used for mechanical edits. Mitigation: design and review calls only, batched; the runner produces the evidence.
  • The generator owns data.js, and the shard split changes that contract. A half-migrated generator can leave sections reading a shard that no run writes. Mitigation: the manifest is written last, and the page falls back whenever a shard is absent.
  • The checkout already carries 1,222 dirty paths on a feature branch, so the snapshot mirror lags the running page. Any mirror-based acceptance check can pass or fail for the wrong reason. Mitigation: every criterion is run against the served page and the running generator, never against git.
  • The Wheel app and the cockpit share an origin but not a data contract. A read-only summary must not turn into a second writer. Mitigation: open the store read-only, and prove with A12 that no write route exists.
  • Accessibility and contrast figures in v2 predate this HEAD. Treating them as current would ship a false claim. Mitigation: A15 has to run before any stage is called done.
  • CSP work can break the inline script surface, the icon sprite and the folded frames at once. Mitigation: stage S3 lands after the hashed assets, and the policy is tested on the loopback origin before the tailnet.
