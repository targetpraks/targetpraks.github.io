Findings, ranked

P0

d3-gate holds 10.4 GB to answer single-label questions

d3-flash-Q8_0.gguf (8.9 GB) + a 595 MB vision projector, 16k context, 8192 batch, KeepAlive.

Evidence

pid 16036  10,916,384 KB RSS   elapsed 02:47
maio-d3-gate -m "AI Hub/llama-cpp/d3-flash-Q8_0.gguf"
  --mmproj mmproj-d3-flash-Q8_0.gguf
  -c 16384 -b 8192 -ub 8192 -np 1 --flash-attn auto   → :8110

Why it matters

  • The gate answers bounded decisions — one label from a list, a rubric score, a yes/no. That workload needs a few hundred tokens of context, not 16,384.
  • It carries a multimodal projector despite the decision path being text-only. 595 MB of weights plus vision buffers, allocated, for a capability the gate never exercises.
  • It is KeepAlive, so the 10.4 GB is permanent — it is not a spike that decays.
  • It is genuinely used — one profile alone has 1,697 gate decisions logged, the most recent today at 14:48. So this is not an idle service to switch off; it is a wildly oversized footprint for real work.

Fix — no download required

Drop the projector, cut context to what a classifier needs, and shrink the compute buffers. Same model, same quality on text, roughly half the footprint:

-  -m d3-flash-Q8_0.gguf --mmproj mmproj-d3-flash-Q8_0.gguf
-  -c 16384 -b 8192 -ub 8192
+  -m d3-flash-Q8_0.gguf
+  -c 4096 -b 2048 -ub 512

Expected: 5.5–7 GB resident, recovering 3.5–5 GB. A Q4_K_M quant would take it near 5 GB but needs a download and re-validation against the 1,697-decision history — I would not do that without you choosing it.

Risk: low and reversible — one line in d3-gate.sh, then launchctl kickstart -k. Validate by replaying a sample of logged gate decisions and confirming the labels are unchanged.

P0

The Colima VM reserves 6 GiB to run eleven containers, seven of them Postgres

Hypervisor memory is wired: it cannot be compressed or swapped. Every idle database costs full price.

Evidence

colima: aarch64 · 4 CPU · 6 GiB · 100 GiB · macOS Virtualization.Framework
containers: 11 — signet-pg ×6, hindsight, metamcp, metamcp-pg, constellation-dev-pg

Why it matters

  • Seven separate Postgres instances at shared_buffers defaults each hold memory that macOS can never reclaim while the VM lives.
  • This allocation is present from login, which is why the first swapfiles appear two minutes after boot — before any agent has done anything at all.
  • MetaMCP itself runs inside this VM and is reached through an SSH forward, so every MCP tool call crosses an extra hop (see the topology finding below).

Fix

colima stop && colima start --memory 4 --cpu 4

Before shrinking, dump every database and consolidate the seven Postgres containers into one cluster with separate databases and roles. Isolation is a real requirement only if you actually need separate versions — otherwise this is six copies of the same idle daemon.

Risk: medium — database outage during restore. Dump first, consolidate, verify, then shrink.

P1

The RAM guard detected the emergency and told nobody

It flipped to HIGH at 17:50 and suppressed its own alert because of a cooldown.

Evidence

[2026-10-23 17:50:00] alert suppressed (cooldown) — flipped to HIGH silently
RAM_GUARD=HIGH
RAM_GUARD=HIGH
RAM_GUARD=HIGH

Why it matters

Detection works. Escalation is broken. A guard that goes silent exactly when the machine enters the state it exists to prevent is worse than no guard, because it manufactures false confidence. Everything else in this report could have been caught hours earlier by an alert that actually arrived.

Fix

  • A first transition into HIGH or CRITICAL must always alert, regardless of cooldown.
  • Cooldown may suppress only repeats of an already-delivered alert.
  • If HIGH persists beyond five minutes, re-escalate even inside the cooldown window.
  • The alert should carry the top five memory consumers and current swap, so it is actionable on arrival.
P1

The macOS firewall is off, and six services listen on every interface

Not a memory problem. A catastrophic-risk problem.

Evidence

socketfilterfw --getglobalstate → Firewall is disabled. (State = 0)

bound to 0.0.0.0:  ollama :11434   node :8181    Python :8011   Python :8012
                   snappier :8800  Orca :6768    ARD :3283
                   rapportd :49152 ControlCenter :5000 and :7000

Why it matters

  • No packet filter, and the fleet's control surfaces sit on a wildcard bind. Anything on the LAN — a guest device, a compromised IoT gadget — can reach the Ollama API and the agent gateway directly.
  • Tailscale has five peers. Peer ricardos-macbook-air is active; two others are stale entries from 5 and 22 days ago. Stale nodes still hold keys.
  • 66 orphaned SSH sessions and 34 zombies are consistent with a session-management defect, but with the firewall off I would not dismiss the possibility that some of that traffic was not yours.

Fix — ordered

# 1. bind to loopback (real control)
OLLAMA_HOST=127.0.0.1:11434
#     then the same for :8181, :8011, :8012, :8800, :6768 in their configs

# 2. then the firewall
sudo /usr/libexec/ApplicationFirewall/socketfilterfw --setglobalstate on
sudo /usr/libexec/ApplicationFirewall/socketfilterfw --setstealthmode on
sudo /usr/libexec/ApplicationFirewall/socketfilterfw --setallowsigned on

Use Tailscale Serve for intentional remote access rather than a wildcard bind. Remove the two stale tailnet nodes. Risk: lockout — keep a local console open while changing this, and change binds before enabling the firewall, not after.

P2

MCP runs as two control planes, and every call crosses the VM boundary

13 launchd KeepAlive MCP servers on the host, plus MetaMCP inside Colima reached over SSH.

Evidence

host, launchd KeepAlive=true:  browseruse cloudflare composio copilot docs gamma
                               gate krea magnific pipedream qmd superhuman todoist
:12008/tcp  →  ssh .../colima/ssh.sock [mux]     (MetaMCP lives inside the VM)
:12008/mcp  →  401 (auth required — correct, endpoint is healthy)

Why it matters

  • Each of those thirteen is a permanently resident node or python process on the host, and MetaMCP is a second, permanently resident server inside the VM. Two ownership models for one capability.
  • Tool calls route host → SSH mux → VM → back out to host-side MCP servers. Every MCP round trip pays that latency twice, and the SSH mux is exactly where the 66 leaked sessions accumulate.
  • Whether MetaMCP spawns its own children or only proxies decides the fix. From the outside, the process table shows no children under the mux, which points at proxying — verify before removing either side.

Fix

Pick one control plane. Most sustainable: MetaMCP on the host as the single gateway, spawning stdio MCP children on demand with a hard cap of 4–6 concurrent, KeepAlive on the gateway only, and the thirteen launchd singletons retired. That removes a dozen resident processes and collapses the SSH hop.

Risk: disabling the wrong side silently breaks every tool. Verify parentage first, change one server at a time, and confirm the tool list is intact after each.

P2

A duplicate MCP registration spams a 30 MB error log with no rotation

Portable MCP server 'rea' conflicts with native config; skipping — three times per tool cycle, all day.

Evidence

~/.hermes/logs/gateway.error.log   30 MB, actively growing at audit time
WARNING tools.mcp_tool: Portable MCP server 'rea' conflicts with native config; skipping   ×3 per cycle
MallocStackLogging: can't turn off malloc stack logging because it was not enabled  ×dozens/min

Why it matters

rea is registered twice — once as a portable server, once natively — so one copy is discarded on every single tool load. The REA toolset is large (200+ tools); loading it twice per cycle is real CPU and real log I/O on a machine with no CPU headroom. The MallocStackLogging line is inherited environment noise, not a leak, but it buries the signal.

Fix

# keep exactly one authoritative 'rea' definition, restart the gateway,
# confirm 'rea' appears once in the loaded tool list
# add newsyslog rotation: gateway.error.log  644  5  20480  *  J
P2

Two schedulers run the same estate: 69 launchd agents against 4 Hermes cron jobs

Plus two jobs failing, and two reporting a stale -15 exit while running.

Evidence

launchctl list | grep com.maio  →  69 agents
~/.hermes/cron/jobs.json        →   4 jobs
  t3 serve watchdog      every 5m   (286 runs)
  disk headroom          every 360m
  CLIProxyAPI guard      ~11m
  weekly LLM benchmark

com.maio.hiksemi-recover   last exit 1
com.maio.constellation-dev last exit 1, spawn scheduled

Why it matters

Two independent schedulers over one estate means nobody owns the full schedule and duplicate work is invisible until it shows up as load. Note that launchd agents cannot read /Volumes — that path is EPERM for launchd — so any job touching the Hiksemi drive must live in Hermes cron. That is a structural reason the split happened, and the fix is to make the boundary explicit rather than to pretend one scheduler can do both.

Fix

Declare one boundary: launchd owns processes (keepalive daemons, supervisors); Hermes cron owns schedules (anything timed or touching external volumes). Then repair hiksemi-recover — it is failing precisely because of the EPERM path problem — and retire constellation-dev if the service it fronts has moved into Colima.

Sustainability — 32 profiles on 25 GB

The principle: 32 profiles are data and queued work, not 32 resident agent stacks. A profile that is not mid-turn costs nothing but disk. Any architecture that keeps runtime per-profile cannot fit on this box, and should not try.

launchd
├── one scheduler boundary (launchd = processes · Hermes cron = schedules)
├── MetaMCP gateway, one owner, KeepAlive
│   └── stdio MCP children on demand, hard cap 4–6
├── Colima 4 GB max, or native Postgres
│   └── ONE cluster · 32 databases and roles, not 7 instances
├── Hermes supervisor + queue
│   └── worker pool 4–6 · one active turn per profile
├── d3-gate: resized for classification (~5.5–7 GB, loopback, on demand)
└── RAM guard that escalates + log rotation + health checks

Budget that fits: macOS and UI 5–6 · VM 4 · Postgres 2–3 · MCP gateway and children 1.5–2.5 · supervisor and 4–6 workers 4–6 · gate 5.5–7 · headroom 4–5. That lands at 22–29 GB, which is why the gate has to shrink or move off-box — it is the difference between fitting and not.

Acceptance criteria, all measurable: no swapfile created in the first 30 minutes after boot · swap flat under steady load · wired below 11 GB · load under 4 · no 0.0.0.0 listener except an intentional Tailscale service · one scheduler, one MCP owner · guard alerts on first critical transition.

What I corrected in my own audit

Two things I got wrong before the council caught them, recorded because they change the diagnosis:

  • I read etime (elapsed time) as a clock time and concluded 33 SSH sessions had been orphaned since 03:20. They are 3h30m old, started around 14:25, and trace to the Colima SSH mux — a session-management defect, not a fourteen-hour-old intrusion.
  • My first process listing sorted by CPU, which hid the largest memory consumer entirely. Sorting by RSS is what surfaced the 10.4 GB gate process. The audit was wrong until that changed.

Neither changes the headline, but both change the fixes — and a report that silently keeps its early mistakes is worth less than one that shows where it was corrected.
