1. What "latest" meant by the time it ran

Upstream shipped twice overnight: v1.91.0 and v1.92.0 (the latter at 21:48Z on 23 Nov). Meanwhile the deployment itself grew a second local layer — agenticos-backend:1.82.2-private-unit-count-d0ff6708f9f5 plus a matching frontend — which adds the private ClickUp unit-task count: six unit_clickup_* services, one route module, a unit-task-summary page in four languages, and host mounts for the policy file, inbox and replies.

So the upgrade was not "pull 1.92.0". It was a merge of two local overlays, fourteen files, onto a release that moved the same modules twice more.

2. The merge method (repeatable)

Rather than re-anchoring hunks by hand, the merge was done properly in git on the host:

  1. commit the upstream 1.82.2 tree;
  2. overwrite backend/app/ with the fourteen files extracted from the running production image and commit;
  3. branch from the 1.82.2 commit (not the overlay commit), replace that tree with 1.92.0, commit;
  4. merge the branch back into the overlay commit.

Three conflicts, all in agent_runner.py, all resolved by keeping both sides: the caller-scoped owner selection plus upstream's new reporting_only credential path; the personal-connector suppression after upstream's new delegation block; the unit-report instruction injection alongside upstream's routine-result instructions. Every other file — config.py, mcp_catalog.py, mcp_connection.py, api/routes/v1/__init__.py — auto-merged.

Branching after the overlay commit makes the merge a silent fast-forward and quietly discards the overlay. It happened on the first attempt; the tree still contained 1.92.0 and nothing else. Check git log --graph before trusting a clean merge.

6. What the run exposed

  1. The disk reached 100 % (562 MB free) minutes after the swap. Docker's build cache had grown to 18.75 GB across three image builds. docker builder prune -af returned it to 16 GB free (79 %). Prune the builder cache after building, and check df before and after any image work.
  2. The nightly backup cron is alive — it wrote twice at 02:15 (two dumps 31 s apart, worth a look at the duplicate), and the log reads backup ok: 73M. The three-day gap reported on 23 Nov has closed.
  3. The positive ClickUp count path was not re-exercised. It needs an employee's own connected ClickUp account; the refusal path and the route wiring are proven, the authorised count is not.
  4. Staging's worker was stopped as soon as it proved it boots — a restored dump carries live background_schedules, and the staging worker would fire them at ClickUp, Zoho and SMTP.
