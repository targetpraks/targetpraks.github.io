2. Home Assistant — zero snapshots ever produced

The nightly job (com.maio.home-assistant-backup, 03:20 daily, last exit code = 1) copies the config out of the container fine — the work dir for today is 12 MB and complete — then dies on tar:

$ tail -3 ~/.config/maio-stack/home-assistant/backup.log
open /Volumes/Hiksemi 1TB/AI-Drive/backups/home-assistant: no such file or directory
tar: Failed to open '…/home-assistant-config-2026-11-17.tar.gz'
tar: Failed to open '…/home-assistant-config-2026-11-18.tar.gz'

$ find "/Volumes/Hiksemi 1TB/AI-Drive/Backups/home-assistant" -name "*.tar.gz" | wc -l
       0
$ ls -d home-assistant/.work-* | wc -l ; du -sch home-assistant/.work-* | tail -1
      18
164M    total

The case difference (backups vs Backups) is not the cause — the volume is case-insensitive APFS, same inode 4030036.

The cause is TCC. In the tccd log at 03:20:05, bsdtar (pid 27548, responsible process /bin/zsh pid 27530) asked for Removable Volumes and was refused, while the docker CLI in the same second was allowed:

AUTHREQ_CTX:    msgID=435.8850, service=kTCCServiceSystemPolicyRemovableVolumes, preflight=yes
AUTHREQ_RESULT: msgID=435.8850, authValue=1, authReason=0        # bsdtar — denied
AUTHREQ_RESULT: msgID=435.8848, authValue=2, authReason=2        # docker cp — allowed

Because set -e aborts on the tar failure, the rm -rf "$WORK" on line 16 never runs, so a work copy of the whole house config is left behind every night — 18 copies, 164 MB, growing. This is the same failure class as the documented com.maio.backup TCC break (launchd zsh lacks the removable-volume grant); that job was fixed with an osascript TCC wrapper, this one was not.
