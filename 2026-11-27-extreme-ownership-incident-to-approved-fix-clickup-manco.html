3. What the API refused — statuses

This is the one part of the design that cannot be automated, and it is worth recording exactly why, because the endpoint appears to exist and then refuses at the last step.

Attempt Result
POST /list/{id}/status {"status":"Logged", …} 400 STATUS_026 "Status name is required"
{"name":"Logged", …}, {"status_name":…}, {"statuses":[…]}, ?status=Logged 400 STATUS_026 — same
{"status":{"name":"Logged","type":"open","color":…}} 400 STATUS_028 — "New 'open', 'closed', or 'done' statuses not supported at this time"
{"status":{"name":"Owner writing plan","type":"custom",…}} 200 — created, but stored lower-cased as owner writing plan
PUT /list/{id}/status/{status_id} (rename) 404 — no route
PUT /list/{id}/status with an id (rename) 405 — no route
DELETE /list/{id}/status/{id} (route probe on a bogus id) 404 — no route

So the API can only append lower-cased custom statuses. It cannot rename, cannot delete, and cannot create the open-type or closed-type bookends the flow needs. The six statuses Ricardo asked for — capitalised, one open, one closed — are therefore UI work.

The status the probe created was removed again by switching the list back to override_statuses: false (PUT /v2/list/{list_id} → 200). Verified afterwards: the list is back to its six inherited statuses and override_statuses is false, i.e. no leftover scaffolding for Ricardo to clean up before he starts.

Two smaller refusals, both recorded rather than worked around:

  • Default view: PUT /view/{id} accepts default_view: true with 200 but silently drops it — GET /list/{id}/view still reports default_view: null. It is a UI click.
  • Status filter on the "Awaiting approval" view: the filter is dropped on both POST and PUT while the status Awaiting approval does not exist, so the view is currently unfiltered. Add the filter after the statuses exist.
