2. Findings that shape the design

  1. Organisation scope was wrong in v2. There are 22 company agents, not 24; Architect and AgenticOS belong to Ricardo's personal scratch org. Any census must group by organisation first, and the cross-organisation pairs must not be "consolidated".
  2. Runs happen; delivery is not recorded. 44 routines have a completed run and report delivered, yet routine_deliveries is empty. The delivery table is not wired, so "did it reach anyone, and what did it say" cannot be answered from data today.
  3. The feed is not sufficient for the checks it is asked to power. The FIN feed (generated 19:31) reports 167 open tasks, 0 overdue-with-owner, 25 unassigned, 0 without a due date — but carries no task update timestamps and truncates long lists. Stale/duplicate detection and "zero field gaps" cannot be computed from it.
  4. Knowledge is empty where it matters, and partly unprovenanced. 8 KBs hold ≤ 1 document (7 empty, DID 1); the SOP library holds zero; 60 of 142 rows have no source_path; 2 rows are in error.
  5. The pause list is a dependency list, with a routing gap. Three templates wait on Zoho Mail/People/WorkDrive scopes; NVP has no ingestion route at all; SNR EXCO is paused.
  6. One routine carries a real collision risk, not a proven failure. All 13 Weekly SOP audit routines run at 20:00 in creator mode with no notification channels. The current evidence shows FIN completing, so the claim is risk, not current defect — the failure mode is unproven but the design invites it.
  7. Two operational facts outrank the plan. The host has 16.5% free disk, below the PRD's gate, and the platform is two minor releases behind with no release-watch routine. Capacity and backup-restore evidence therefore move into P0.
  8. Write authority is missing. Superman's table bindings are read-only; SOP Bot is forbidden to write SOPs; unit-bot prompts forbid record changes. A ledger that "bots write" needs a named writer and tested grants, not an assumption.

3. Goals and non-goals

Goals

  1. One complete maintenance check, proven end to end — authorised input, execution, delivery receipt, independent read-back — before anything is multiplied across the fleet.
  2. Every routine is provable per due slot. A missed slot is an alarm; a run that completed but never reached a destination is a failure, not a success.
  3. Shaped routines become workflows where the arithmetic is real, with typed calculation, bounded budgets, node records and a shadow comparison against pinned inputs.
  4. Capacity, backup restore and release drift are known in P0, not discovered at P4.
  5. Knowledge is prioritised and honest: a declared corpus, provenance, freshness, measured ingestion throughput, and an evaluation harness that exists before a pass rate is claimed.
  6. ClickUp has one real intake path and a bounded write policy, before any sampling or enforcement plan.
  7. Independent audit. Batman and SOP Bot verify; the executing bot never signs its own week.

Non-goals

  • Ricardo's Macs, Hermes profiles, Courage/Dexter/Reviewer, Maio OS, personal devices.
  • New bots, models or MCP servers before the existing 22 agents and 4 connections are used with granted authority.
  • Autonomous production upgrades, autonomous structural ClickUp change, any deletion, any spend.
  • Re-indexing 13.38 TB. Coverage is a declared corpus (§10).
  • Merging personal-scratch agents into the company organisation.

5.1 Routines become workflows where the job has a shape

A routine is a prompt on a cron. A workflow is a drawn route with per-node records, a bounded budget, retries and a testable draft. The test is sequence plus arithmetic or a join, not "it sounds structured".

Revised conversion list after review:

Phase Template Why
P1 ClickUp overdue chase date filtering, 30-day buckets, per-owner counts are arithmetic
P1 Unassigned work triage pairing two lists plus a workload ranking — but the assignment policy must be agreed first (§8)
P1 Tables base reconciliation (EXP, TLF) joins feed work to table rows, tests mandatory fields, counts exceptions
P2, after the feed contract Stale and duplicate watch needs updated_at per task, which the feed does not carry today
P2, after eval harness Knowledge base upkeep the deterministic inventory part converts; the judgment part stays a routine
Not converted Friday stand-up pack the feed already carries precomputed person counts; conversion adds no numeric truth
Not converted Weekly SOP audit its defect is the schedule collision and creator mode, not prose arithmetic — fix those, keep it a routine
Not converted Context base drift judgment over a snapshot; no arithmetic to move

A workflow costs more than a prompt: graph and version ownership, an execution principal, bindings, node events, budgets, retries, test cases and retention. That cost is why three convert in P1, not five.

5.3 The ledger is a virtual table — with a named writer

Three tables, and one authority decision that v2 left implicit:

  • estate_inventory — one row per asset: id, kind (agent, routine, workflow, KB, host, service, account, token, document set), organisation, owner, criticality, expected version, check, update lane, window, rollback.
  • maintenance_ledger — append-only: ts, workflow, bot, asset, check, status (ok | drift | fixed | failed | blocked | needs-approval | missed), observed, expected, evidence (run id, artifact id, receipt), next action.
  • maintenance_findings — one open issue per row: finding, severity, owner bot, due date, ClickUp task id, closure evidence.

Writer: a single service identity with write grants on these three tables — most likely Superman after an explicit grant, because its current table bindings are read-only. DASH Bot needs a read binding to render them (it has none today). Until both are granted and proven with a write-then-read-back, the ledger is a design, not a system.

No row is green without a run id, an artifact, or a destination receipt.

5.4 Delivery and escalation

  • Daily: one digest artifact, built from the ledger, posted to the maintenance channel (not primary chat).
  • Weekly: the maintenance pack — slot coverage, exceptions, conversion progress, KB throughput, ClickUp intake — linked from each unit space.
  • Escalation: unit bot → Superman → Batman (Ricardo's decision) → Ricardo. Money, legal, deletion, staff access and production upgrades go straight to Ricardo.

6. W1 — Enhance our systems (the platform's own upkeep)

Owner: Superman · Builder: Architect Bot · Auditor: Batman · Cadence: daily 05:30, weekly review

  2. Per-slot proof. For every active routine, check each due slot in its cron timezone: a run, a terminal status, a deadline, a destination receipt. Report missed, not "no data".

  6. Conversion (staged). Architect Bot builds the draft; Superman runs it beside the routine on pinned inputs, with an independently computed expected result — not the routine's answer as the oracle. Batman compares. Only then does the routine pause.

Acceptance: census reconcilable to zero unexplained assets; every active routine has a per-slot verdict; one delivery row per delivered run; pause register complete; one conversion comparison on pinned inputs stored as an artifact.

Steps

  5. Staging proof (Mondays). Eight named checks, each with a stored evidence id: (1) gateway health 200; (2) login through Cloudflare Access; (3) one agent turn calling one MCP tool; (4) one document upload → embed → retrieval hit; (5) one routine dispatch; (6) one sandbox run; (7) one artifact render; (8) DB migration state consistent. 8/8, or no promotion.

  7. Production (Thursdays, gated). Ricardo + Tuan approve; the lane applies; Superman re-runs the same eight checks and records each.
  8. Monthly access and secrets board. MCP connections (4), OAuth scopes, admin members, keys, expiry — names and status only.

10. W5 — Knowledge, SOPs and reference material

Owners: unit authors (SOPs) · DOC Bot (documents) · unit bots (unit KBs) · Superman (pipeline) · SOP Bot (audit) · Approves: Ricardo for retirement and corpus

The problem in numbers: 22 KBs, 142 rows (140 done, 2 error, 60 without source_path), 8 KBs at ≤ 1 document, the SOP library at zero, an ingestion ceiling of 210 uploads/night across 14 eligible departments, and 1.27M files claimed behind them (UNVERIFIED).

The pipeline

  1. Declare one corpus. 200 documents company-wide for phase 1 (the lower bound of the 200–500 range), chosen by class and unit, with path, class, owner, TTL and expected source; grow to 500 only after throughput is measured. v2's "per unit" phrasing is withdrawn — it would have meant 2,600+ documents.
  2. Measure ingestion before promising it. Track indexed successes per night, not uploads attempted. At 210/night the theoretical ceiling is 1–3 nights for 200 documents if they are evenly reachable; a single-department bottleneck is 14 nights. Report which it is.
  3. Route the gaps. NVP has no ingestion route and SNR EXCO is paused with no KB — both are findings to close before any "all units covered" claim.
  4. Provenance and freshness. Every admitted document has path, unit, owner, effective date and freshness date. The 60 rows without source_path are repaired or quarantined; the 2 error rows are fixed or removed from the count.
  5. Build the evaluation harness, then the bar. No datasets, cases, suites or eval runs exist today. Register versioned questions per unit with expected source documents and a scoring rule; run 5 per unit monthly as a smoke test, the full set quarterly. The 90% bar applies only once the harness exists; before that the metric is "harness built, first run recorded".
  6. SOPs are written by unit authors, audited by SOP Bot. SOP Bot's instructions forbid writing; it names gaps, orphans, stale and contradictory procedures. The SOP KB is populated by unit SOP documents, not by the auditor.
  7. Refresh the reference layer (monthly). Taxonomy tables re-read from a live portal where a connection exists, otherwise a dated export; skills and contexts checked for dead references; feeds checked against their source timestamp.
  8. Close the gap loop. knowledge_searches (89) and the gap topics (1) drive the next corpus additions; a gap with no owner becomes a finding.

Acceptance: corpus manifest pinned at 200 with 100% provenance; ingestion measured per night for two weeks; harness exists with a first run; SOP KB populated by unit authors with SOP Bot's audit attached; NVP route decision recorded.

17. Acceptance criteria (rewritten to be falsifiable)

  1. One loop, proven. A single unit's check runs from input to run to destination receipt to Batman's independent read-back, with ids stored in the ledger. Fail if any link is missing.
  2. Per-slot coverage. For a pinned manifest of active routine ids, every due slot in a 7-day window has a run, a terminal status, and a receipt, or an explicit pause record. Fail on any silent slot.
  3. Writer authority. A test row written to maintenance_ledger and read back by DASH, with the grant recorded. Fail if only one of the two works.
  4. Feed canary. A marker row injected into one unit's feed appears in that unit's next output with a matching source timestamp. Fail if it does not.
  5. Conversion comparison. Three workflows run on pinned inputs against independently computed expected results, stored as artifacts. Fail if the only oracle is the old routine.
  6. Capacity and restore. A dated capacity finding (disk, growth, competition) and a dated restore rehearsal with time-to-restore. Fail if either is absent.
  7. Corpus manifest. 200 documents, each with path, unit, owner, effective date and provenance; two weeks of indexed-success counts. Fail on any missing field.
  8. SOP library. ≥ 50 SOPs indexed, each with owner and review date, from unit authors, with SOP Bot's audit attached; contradiction review dated, zero open findings in the reviewed set.
  9. ClickUp intake. One genuine MANCO Briefed-In task with the eight Brief fields and a correct Requested by, read back by id.
  10. Release watch. A finding for the live gap (1.82.2 → v1.84.0) with a rollback manifest, and eight named staging checks recorded before any production step.
