2. Seven findings that shape the design

  1. The fleet is scheduled but unproven. 128 of 132 routines have produced no run. next_fire_at in the future plus last_fired_at = null looks identical on the console to a working routine. Nothing measures "did the 20:03 chase actually run last night".
  2. Delivery is invisible. Reports land in primary chat, not in a run log; routine_deliveries is empty. Nobody can prove a nightly job reported, or what it said.
  3. The unit bots are blind to live systems. No MCP servers, a snapshot document, and no signal when the snapshot is stale. They narrate ClickUp and Zoho state they cannot see.
  4. Knowledge is nearly empty where it matters. Nine KBs hold ≤ 1 document; the SOP library holds zero — the SOP Bot's entire subject. TLF and EXP hold 91 of the 142 documents between them.
  5. The pause list is a dependency list. Team Inbox zero, Weekly hours check and WorkDrive STS tidy wait on Zoho Mail, People and WorkDrive scopes the organisation has not granted. 39 paused routines are a scope decision, not a bug.
  6. One routine is fragile by construction. Weekly SOP audit runs as its creator, calls a skill, and lands in awaiting_approval with no notification — a silent failure mode for all 13 units, all at the same minute.
  7. The platform is behind upstream and nobody watches. 1.82.2 against v1.84.0, with no release-watch routine and no upgrade workflow.

3. Goals and non-goals

Goals

  1. Every routine is provable. Each active routine has a run record, a delivery record and a health row; a routine that did not run is an alarm, not a silence.
  2. Shaped routines become workflows. Jobs that are a sequence plus arithmetic get fixed routes, per-step records, retries, error routing, budgets and test drafts — not prose and hope.
  3. The ledger is a platform object. Inventory, findings and maintenance history live in virtual tables and KBs on AgenticOS, not in files on anyone's Mac.
  4. Knowledge is prioritised and fresh. A declared priority corpus per unit, provenance on every document, freshness scored, retrieval proven against gold questions, SOP library brought to life.
  5. ClickUp becomes the work surface it was bought for. Field-complete tasks, non-empty Briefed-In lists, unit routines reporting from real ClickUp data.
  6. AgenticOS tracks upstream within one minor release, with a staging proof and a rollback path before production.
  7. Independent audit. Batman and SOP Bot verify claims read-only; Superman cannot certify its own work.

Non-goals (v2)

  • Ricardo's Macs, Hermes profiles, Courage/Dexter/Reviewer, Maio OS, personal devices — separate system, separate PRD.
  • New bots, models or MCP servers before the existing 24 agents and 4 connections are fully used.
  • Autonomous production upgrades, autonomous ClickUp structural changes, any deletion, any spend.
  • Re-indexing all 13.38 TB of WorkDrive. Coverage is prioritised (§10).

5.1 Routines become workflows where the job has a shape

A routine is a prompt on a cron. A workflow is a drawn route with a run record per step, retry from the failed step, error routing, a per-run budget, and a draft that can be tested before it goes live. The test: does the job contain a sequence with arithmetic or a join? If yes, the model should not be doing the counting in prose.

Five of the eleven templates qualify immediately (ClickUp overdue chase, Unassigned work triage, Stale and duplicate watch, Friday stand-up pack, Knowledge base upkeep). The rest stay routines until scoped — do not convert what has no shape.

5.2 Every routine gets a proof-of-life contract

Applied to all 132 rows in agent_triggers:

Field Required setting Why
delivery_mode a dedicated maintenance channel plus the unit's own space — never only primary chat Reports become findable and auditable
overlap skip A slow run must not stack on itself
runs_as_creator off — run as a service identity with pre-consented read-only skills Removes the silent awaiting_approval failure
pinned_version_id set A prompt edit cannot silently change a routine
monthly_budget_usd set on every routine No unbounded spend
last_run_id non-null within two cadence periods Turns silence into an alarm
notification_channels failure and missed-run routes named Someone hears it

5.3 The ledger is a virtual table

Three tables on the platform — DASH Bot renders them, the bots write them:

  • estate_inventory — one row per asset: id, kind (bot, routine, workflow, KB, host, service, account, token, document set), owner, criticality, version/expected, check, update lane, window, rollback.
  • maintenance_ledger — append-only: ts, workflow, bot, asset, check, status (ok | drift | fixed | failed | blocked | needs-approval | missed), observed, expected, evidence (artifact or run id), next action.
  • maintenance_findings — one row per open issue: finding, severity, owner bot, due date, ClickUp task id, closure evidence. Findings that are work become ClickUp tasks through Batman, per the Brief standard; the ledger keeps the task id.

No row is "green" without a run id or an artifact behind it.

5.4 Delivery and escalation

  • Daily: one maintenance digest artifact (DASH Bot) — counts by workflow, exceptions, missed runs, anything needing a human.
  • Weekly: the maintenance pack — SLO table, recurring failures, conversion progress, KB coverage, ClickUp completeness — posted to the maintenance channel and linked from the unit spaces.
  • Escalation ladder: unit bot → Superman (fleet) → Batman (Ricardo's decision) → Ricardo. Money, legal, deletion, staff access and production upgrades go straight to Ricardo; they never wait in a bot's queue.

6. W1 — Enhance our systems (the platform's own upkeep)

Owner: Superman · Builder: Architect · Auditor: Batman · Cadence: daily checks, weekly conversion review

Steps

  1. Fleet census (daily 05:30). Read every agent, routine, workflow, KB, table, context file and skill; diff against estate_inventory; reconcile orphans (agents in no group, routines on unpublished agents, KBs with no owner, workflows with no live trigger).
  2. Proof of life (daily). Flag every active routine whose last_run_id is older than two cadence periods; every workflow with a failed last run; every routine in awaiting_approval longer than one cycle. This is the fix for the 128-unproven-routines problem.
  3. Delivery check (daily). routine_deliveries must show a row per scheduled run. A non-zero run count with zero deliveries is a delivery defect.
  4. Quality sampling (weekly). SOP Bot reads a sample of unit-bot outputs and scores: did it use the data it was given, did it invent numbers, did it answer the question asked. Findings carry the run id.
  5. Conversion (weekly, staged). Architect builds the workflow draft; Superman runs it against last week's inputs beside the routine; Batman compares outputs; only then is the routine paused and the workflow made live. A conversion that disagrees with the routine is a finding, not a rollout.
  6. Content-asset drift (weekly). Skills, contexts and prompts referencing dead paths, removed tools, old field names or stale versions are flagged — 83 skills, 29 context files today.
  7. Consolidation (monthly). Duplicate agents (AgenticOS/AgenticOS Bot, Architect/Architect Bot), overlapping routines, unused seats. Proposals only — Batman brings them to Ricardo.

Acceptance: 100% of active routines have a run record and a delivery row; 0 routines in approval limbo beyond one cycle; conversion backlog visible with owners; every finding has a ClickUp task.

7. W2 — AgenticOS platform upkeep

Owner: Superman · Approvers: Tuan (staging), Ricardo + Tuan (production) · Window: staging Monday 04:30, production Thursday 03:00 SAST

What Superman can and cannot do (verified): it can browse, research, run sandboxes, drive a coding agent, read and write KBs, tables and contexts, and file findings. It has no host shell. Host mutation therefore runs in an explicit execution lane — Tuan/IT or a declared, allowlisted runner on the host — while Superman owns the decision, the evidence, the verification and the report. That boundary is a design rule, not an obstacle to route around.

Steps

  1. Release watch (daily 04:00). Read upstream releases and changelog; compare with the deployed version (today 1.82.2 vs v1.84.0); classify patch/minor/major/security; open a finding when the gap exceeds one minor release.
  2. Pre-flight. Database backup present and fresh (host cron 02:15); disk headroom ≥ 20%; current image digests recorded; previous compose file archived; rollback package named.
  3. Staging proof (Mondays). Request the staging upgrade through the execution lane, then verify with a smoke suite: gateway health; login through Cloudflare Access; one agent turn using one MCP tool; one document upload → embed → retrieval hit; one routine dispatch; one sandbox run; artifact render. 8/8 required.
  4. Soak (24 h). Compare error rate, latency and agent-run success against the previous week's baseline.
  5. Production (Thursdays, gated). Ricardo + Tuan approve; the execution lane applies; Superman re-runs the same eight checks and records each with evidence.
  6. Backup proof (monthly). Restore the database backup into a scratch container, apply migrations, confirm one read; record time-to-restore. A backup that has never been restored is a belief.
  7. Capacity (monthly). DB size, document count, embed queue, container memory, per-bot spend versus budget.
  8. Access and secrets (monthly). Org MCP connections (4 today), OAuth scopes, admin members, API keys, expiring credentials — names and status only, never values.

Acceptance: version lag ≤ 1 minor release and ≤ 14 days; smoke suite 8/8 before and after; rollback package verified by dry run; restore proof dated within 30 days; zero credential values in any report.

10. W5 — Knowledge, SOPs and reference material (who keeps it current)

Owners: SOP Bot (SOPs) · DOC Bot (documents) · unit bots (unit KBs) · Superman (pipeline health) · Approves: Ricardo for retirement, Batman for business priority

The problem in numbers: 22 KBs, 142 documents, 9 of them effectively empty; the SOP library at zero; 1.27M files behind them; a nightly budget of 15 uploads per department. Today the platform answers from a rounding error of the company's documents, and nothing scores freshness.

The pipeline

  1. Select (once, reviewed quarterly). A declared priority corpus per unit: 200–500 documents company-wide — policies, price lists, SOPs, brand kits, current plans, product catalogues, org charts — stored in estate_inventory with WorkDrive path, class and TTL. A document without provenance is not admitted.
  2. Ingest. Keep the nightly budget sync for the long tail; add a priority lane that re-reads only changed files (modifiedTime) for the priority corpus. Deduplicate by content hash.
  3. Enrich. Title, owner, unit, effective date, supersedes, freshness date on every document. Superseded versions are archived, never deleted.
  4. Prove. Twenty gold questions per unit with expected source documents; pass rate ≥ 90%. A unit below that is a finding, not a silent degradation.
  5. Cover. SOP Bot drives the SOP library up from zero: each function needs a written procedure with a named owner and a review date; gaps are named in the words a person on the floor would use.
  6. Refresh the reference layer (monthly). Taxonomy tables (143 Function types, 14 Client/Brand, tiers, priorities) re-read from the live portals where a connection exists, otherwise from the portal export; skills and context files checked for dead references; ROUTINE FEED documents checked for staleness against their source.
  7. Close the loop (weekly). knowledge_searches (15 today) and the knowledge-gap tables (0 today) are read: the questions the bots could not answer are the next corpus additions. A gap with no owner becomes a finding.

Acceptance: priority corpus 100% present and < 90 days; gold-question pass ≥ 90% per unit; 0 documents without provenance; SOP library ≥ 50 owned, dated SOPs with 0 unresolved contradictions; every unanswered question triaged within a week.
