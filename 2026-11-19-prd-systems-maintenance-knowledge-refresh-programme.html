2. Goals / non-goals

Goals

  1. One inventory, one ledger. Every host, device, container, service, account, token and scheduled job is declared in one machine-readable inventory, and every maintenance action is recorded in one append-only ledger with evidence.
  2. Drift is detected daily, fixed weekly. Version, patch, certificate, token and configuration drift is measured every day and closed inside a fixed window — autonomously where risk is low, with Ricardo's go where it touches production.
  3. AgenticOS tracks upstream within one minor release, upgraded through staging with a health gate and an automatic rollback.
  4. Knowledge is fresh and cited. The top business documents are in the KB with provenance, staleness is scored, retired documents are retired, and skills/context/tables are reviewed on a cadence.
  5. ClickUp becomes the single work surface with enforced fields, live Briefed-In lists and a weekly hygiene pass.
  6. Every claim verified by a second bot. Reviewer independently re-checks a sample and signs the weekly report.

Non-goals (v1)

  • No migration off Zoho, ClickUp, Cloudflare or the current hosting model.
  • No new model or MCP server beyond what the roster already carries.
  • No auto-merge of code, no autonomous production application deploys (AgenticOS version upgrades are the only production change in scope, and they are gated).
  • No handling of money, contracts or personal data outside existing policy.
  • No full-corpus re-index of 13.38 TB — coverage is targeted (see W4).

Three artefacts carry the whole design:

  1. inventory.yaml — the single declaration of what exists (schema in §11.1). Everything else is a diff against it.
  2. Health ledger — append-only JSONL, one row per check or action (§11.2). It is the only accepted evidence in reports.
  3. Runbooks — one file per workflow with front-matter (owner, cadence, risk, gate, rollback, last_verified) and numbered steps that map 1:1 to ledger checks.

W1 — Mac & connected-device upkeep

Owner: Courage · Risk: low · Window: daily checks anytime; mutation Mondays 03:00 SAST

Trigger: daily 02:30 drift scan; weekly Monday 03:00 update sweep (dc3a02759447, already live).

Scope: Mac mini (this host), MacBook Air (rmmacbook@192.168.0.123 / tailnet 100.86.69.126), office Mac mini (infmini, user infmac), CuaDriver/Lume/Ollama/Docker daemons, and the iOS device posture that depends on them (no device management — only "is the companion app reachable and current").

Steps

  1. Scan (daily, read-only). brew outdated, mas outdated, softwareupdate -l, hermes --version, npm -g outdated, uv tool list, docker image digests, Ollama version, CuaDriver version, Lume version, free disk, RAM pressure, launchd job state for the com.maio.* fleet, and per-machine reachability (ssh -o BatchMode=yes ... 'sw_vers').
  2. Diff against inventory. Any version or expected-daemon mismatch becomes a ledger row status=drift.
  3. Classify. auto (brew formula, npm global, uv tool, skills, Cua, Lume) / report (macOS point update, MAS apps, Ollama app) / blocked (needs admin password).
  4. Apply (weekly). Existing fleet-update.sh phases 1–11, Mac mini first, then the Air over SSH with the detached-nohup pattern (never one foreground ssh). Skip any phase whose service is mid-run (Paperclip runs, kanban workers).
  5. Verify per machine. sw_vers, brew outdated (expect empty), hermes --version, daemon health, and one end-to-end agent turn per machine.
  6. Record + report. Append rows; post one Discord message only if something changed, failed or needs Ricardo.

Checks (acceptance): every phase has a pass/fail row with the command's real output fragment; brew outdated empty on both Macs; no running GUI app quit; gateway restarted only via the detached recycle and verified listening afterwards.

Gates: OS installs and mas upgrade need Ricardo's admin password → never typed by a bot; the run reports the exact command for him. Any change that would restart the agent gateway outside the window is deferred.

Rollback: brew keeps old cellar versions; docker phases already re-pin the previous digest on a failed health gate; Hermes core update keeps the previous ~/.hermes checkout — the runbook names the exact revert command per phase.

Known gaps this closes: no daily drift signal today; documentation says 05:00 while the job runs 03:00 (fixed by making inventory.yaml the schedule source of truth and generating the skill's table from it).

W2 — AgenticOS lifecycle (build, release, upgrade, recover)

Owner: Courage · Risk: high (production) · Window: Mondays 04:30 staging, Thursdays 03:00 production after approval

Current state: 11 containers on macserver (macmini-inf, Linux aarch64) behind a gateway; app/frontend 1.82.2; upstream 1.84.0. Backups: backup-db.sh at 02:15 daily. Health today: all containers up, DB healthy, public door 302 → Cloudflare Access, tailnet admin 200.

Steps

  1. Release watch (daily 04:00, read-only). Query the upstream releases API and the changelog; compare against AGENTICOS_VERSION; classify patch / minor / major / security. Ledger row.
  2. Pre-flight (per upgrade). Fresh backup-db.sh inside 6 h; disk headroom ≥ 20%; staging host reachable; current image digests recorded; rollback compose saved as docker-compose.yml.bak-preupgrade-<version>.
  3. Staging first. Upgrade macserver compose stack to the target tag; wait for healthy; run the smoke suite (below); 24 h soak with the embed worker and one agent run per unit.
  4. Smoke suite (must be scripted, deterministic): gateway /health; login through Cloudflare Access; one agent turn that calls one MCP tool; one document upload → embed → retrieval hit; one scheduled job dispatch; KB count unchanged or explained; sandboxd healthy; artifact render returns an image.
  5. Production promotion. Only if staging is green and the changelog shows no breaking migration and Ricardo has said go for that version. Promotion is the same compose swap + smoke suite on the production host, inside the window.
  6. Post-checks (24 h). Error-rate and latency comparison against the 7-day baseline; embed queue depth; agent-run success rate; no orphaned volumes.
  7. Rollback. Re-pin previous digests, restore the compose backup, verify smoke suite, restore DB only if a migration ran (documented, gated).

Checks (acceptance): version in the UI and in .env both equal the target; DB alembic_version consistent; smoke suite 8/8; 24 h error rate within +10% of baseline; rollback package on disk and verified by a dry docker compose config against it.

Gates: staging upgrade is autonomous. Production is never autonomous — it needs a green staging report, a fresh backup, and an explicit yes from Ricardo (recorded in the ledger with the message id). Major versions are proposal-only.

Capacity adjunct: monthly review of DB size, rag doc count, embed queue, container memory; the Mac mini RAM guard (≥85% → unload models) already exists and stays in force.

W3 — Infinity Brands host, edge and credential upkeep

Owner: Courage · Risk: medium · Window: Tue/Thu 04:00

Scope: bastion (jumpnut, Debian 12), macserver (macmini-inf), infmini (office Mac mini, infmac), the Cloudflare tunnel + Access app, DNS records, TLS certificates, and the Zoho/company credentials the platform depends on.

Steps

  1. Host sweep (weekly, read-only first). OS patch level, reboot-required flag, disk, swap, NTP, sshd config drift, unattended-upgrades status, listening ports, container list vs inventory.
  2. Patch application. Debian/Ubuntu hosts: apt-get -s upgrade first, then unattended security upgrades inside the window; reboot only with a maintenance flag and a health check on the way back. Never patch during a platform upgrade week.
  3. Edge checks (daily). Public door status + Access redirect; certificate expiry (≥ 21 days); DNS for every host in inventory (existing DNS health check job extends to cover all); tunnel connector count; WAF/rate-limit config hash vs repository.
  4. Credential expiry board (weekly). Zoho refresh tokens (system user and the ZOHO_ALL_REFRESH_TOKEN used by WorkDrive sync), Ollama company key, Cloudflare token, ClickUp pk_… token, SMTP auth, GitHub/DevMini access. Each row: last verified, expiry/rotation date, owner, runbook. Values never enter the ledger — only "verified / expires / rotate-by".
  5. Scope drift check (monthly). Re-probe the granted Zoho scopes and report refusals. Known today: CRM and Cliq 200; Projects and Mail listing 401 INVALID_OAUTHSCOPE; WorkDrive absent from the system user grant (F7007) and served instead by ZOHO_ALL_REFRESH_TOKEN. This is a standing finding, not a surprise.
  6. Recovery drill (monthly). Restore the AgenticOS DB backup to a scratch container, run migrations and a smoke read; record time-to-restore.

Checks: reboot-required = 0 on all hosts; certificate ≥ 21 days; DNS 100% resolve; tunnel up; every credential has a verified date < 30 days; restore drill RTO recorded.

Gates: DNS changes, Cloudflare config changes, and any scope re-consent are Ricardo's — the bot prepares the exact change and waits. No secret is read into a report; only names and statuses.

W4 — Knowledge refresh: WorkDrive → KB → tables → skills → context → documents

Owner: Adrianna A (design) · Executed by: Courage (pipeline) + Scribe (drafting) + Beast (vault filing) · Risk: medium (content quality) · Window: nightly 03:05 (exists) plus weekly review

Current state: nightly wd-sync uploads ≤ 15 docs per department per night into 22 KBs; rag_docs = 142; WorkDrive corpus = 1,274,298 files / 13.38 TB. Embed regeneration runs every 5 minutes on the host. Net effect: the assistant answers from a rounding error of the company's documents, and nothing tracks whether a document is stale, duplicated or superseded.

The pipeline (five stages, each with its own ledger rows):

  1. Select. Maintain a priority corpus in the inventory: for each BU, the folder paths and document classes that matter (policies, price lists, SOPs, contracts templates, product catalogues, brand kits, org charts, current-year plans). Target 200–500 documents, not 1.2M. Ranking inputs: folder criticality, last-modified, filename class, and what staff actually ask the assistant.
  2. Sync. Keep wd-sync for the long tail; add a priority lane that re-syncs the priority corpus on any change (WorkDrive modifiedTime), not on the nightly budget. Dedupe by content hash, not filename.
  3. Normalise + enrich. For each ingested doc: extract title/owner/date/unit, detect duplicates and superseded versions, attach provenance (WorkDrive file id + path + modified time) and a freshness date. A document without provenance is not admitted.
  4. Index + verify. Embed, then run a retrieval proof: 20 gold questions per unit with expected source documents; pass rate ≥ 90%. A failing unit is reported, not silently shipped.
  5. Retire + curate. Documents older than their class TTL (policy 2 years, price list 90 days, org chart 180 days) are flagged; superseded versions are archived (never hard-deleted without Ricardo). Monthly, produce a coverage map: unit → KB → doc count → freshness → gaps.

Beyond documents — the reference layer:

  • Tables/registries: the canonical field lists (Function 143 types, Client/Brand 14, tiers, priorities) are re-read monthly from the live portals (Zoho Projects picklists, ClickUp custom fields) and diffed against the local taxonomy; drift opens a ticket.
  • Skills: weekly drift check already exists for design skills; extend to all skill stores for stale commands (a job ID or path that no longer exists). Broken commands are the most common skill rot.
  • Context files: AGENTS.md/CLAUDE.md/profile context are diffed against inventory.yaml monthly (paths, ports, job IDs, versions). The Monday 03:00 vs 05:00 discrepancy is the worked example.
  • Documents: Scribe maintains a small set of living reference documents (estate map, credentials-expiry board, runbook index, BU contact sheet); Beast files them; the digest links them.

Checks: priority corpus 100% present; gold-question pass ≥ 90% per unit; 0 docs without provenance; 0 duplicate hashes across KBs; every taxonomy value matched or ticketed; every skill command resolves.

Gates: ingesting a department's documents is allowed (read-only copy of company data the platform already serves). Publishing a new knowledge document to the vault goes through Beast. Any deletion is Ricardo's.

W5 — Infinity Brands ClickUp governance

Owner: Batman (business rules) · Checks run by: Courage (no-agent script) · Risk: medium · Window: audit Tuesdays 03:30, hygiene Thursdays 04:00

Current state: workspace 4627083, Business plan, 40 seats, 16 spaces: 12 BU spaces (FIN, HRM, ADM, ITC, MKT, SAL, EXP, TLF, PPP, DID, FXS, FXL), plus NVP, MANCO, EXCO, REP. MANCO Briefed-In and MANCO Projects are empty. The Brief standard (eight machine-written lines, <BU> Briefed-In) is defined but not enforced anywhere.

Steps

  1. Schema audit (weekly, read-only). For each space: folders, lists, statuses, custom fields, views, automations. Diff against the canonical blueprint: every BU has Briefed-In, Daily, Recurring, Reporting, Projects/Ad-hoc, Meeting Action; required fields = Client/Brand, Engagement Tier, Service Tier, Priority, Frequency, Function, Due Date, Requested by.
  2. Task hygiene (weekly). Missing required fields, past-due without update, duplicates (same title + same client within 7 days), tasks with no assignee, lists with > 90-day-stale open items, orphaned subtasks, tasks closed without a comment.
  3. Brief compliance. Sample 20 tasks and verify the eight lines and the wording of the task name. Report the pass rate.
  4. Access review (monthly). Seats used vs 40, guests, inactive members > 60 days, API tokens and their last use, integrations.
  5. Usage telemetry (monthly). Tasks created/closed per BU, Briefed-In inflow, time-to-first-comment, time-to-close. This is the number that tells Ricardo whether ClickUp is actually being used.
  6. Apply (gated). Creating missing lists, adding missing custom fields and fixing field options is a structural change → Batman proposes, Ricardo says go. Filling fields on existing tasks is Batman's within the brief standard, but bulk edits need Ricardo.

Checks: 0 tasks missing required fields; every BU Briefed-In exists; duplicate rate < 2%; access review signed; token last-used < 90 days or rotated.

Rollback: ClickUp has no transactional undo — so structural changes are staged as a documented diff, applied in one batch after a workspace JSON export, with the previous field/list definitions saved to the control plane.

Owner: Reviewer · Risk: none (read-only) · Cadence: daily 08:00 sample; weekly formal sign-off
