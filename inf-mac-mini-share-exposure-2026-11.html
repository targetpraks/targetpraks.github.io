01 What was measured, and from where

Two vantage points, both legitimate: the staging VM at 192.168.88.226 — a bridged guest on the same office LAN, so it sees exactly what any office laptop sees — and an SSH shell on the Mac mini as infmac, which is an administrator account but has no passwordless sudo. Everything below is read-only: port tests, service banners, directory records and preference reads. Nothing was changed, and no password was entered or requested.

This note covers the side question in the original request — the exposure of SMB, Screen Sharing, ARD and Kerberos. The wider inventory of what runs on the box (Hermes under hermes-deploy, the :8099/:9377/:9390 endpoints) is in the access report and is not repeated here.

03 SMB on 445

SMB answers, but it does not let anyone in without an account. From the machine itself, an anonymous session was refused on both the loopback address and the LAN address:

$ smbutil view -N //127.0.0.1
smbutil: server rejected the authentication: Authentication error
$ smbutil view -N //192.168.88.173
smbutil: server rejected the authentication: Authentication error

That is consistent with the rest of the configuration: there is no Guest account on the machine at all, and the login window has GuestEnabled = 0. There is exactly one share, INF’s Public Folder, mapped to /Users/infmac/Public, and it is shared to the group com.apple.sharepoint.group.1 — which infmac and hermes-deploy both hold. The folder holds nothing sensitive: two entries, .localized and a write-only Drop Box.

Two things are worth fixing anyway. First, the share record still carries guest-access flags (smb_guestaccess: 1, afp_guestaccess: 1): they are inert today only because the Guest account is disabled, and they would become live the moment somebody turns it on. Second, no signing requirement is configured on the SMB server — the server preferences contain only the code page, NetBIOS name and description, and SigningRequired is not set. On a flat VLAN with dozens of seats, that leaves NTLM relay as the realistic attack: an attacker who can answer ARP or spoof a name can relay an office machine's authentication attempt to 445 and ride it. The files on this share are not the prize; the credential of an admin account is.

What SMB is, in one line

A file door that is shut to anonymous users but has no signature check on the knock — and the only account behind it is the administrator who is logged in at the console.

04 Screen Sharing and ARD

Screen Sharing on 5900

The banner is RFB 003.889. The security types offered after the version handshake are 30, 33, 36 and 35 — all of them Apple's Remote Desktop authentication family. Type 1 (None, no authentication at all) and type 2 (legacy VNC password) are not offered, so the “VNC viewers may control screen with password” option is off and there is no unauthenticated way onto the display.

# version handshake against the local listener
server banner: b'RFB 003.889\n'
num security types byte: b'\x04'
offered security types: [30, 33, 36, 35]

Access is restricted, not open to everyone. The service ACL com.apple.access_screensharing nests the admin group (its only nested group resolves to admin), and there is no com.apple.access_all_screensharing record at all — the record that would exist if “All users” had been chosen in Sharing settings. In practice: infmac, root and the setup user.

The reason this still lands at Medium is the state of the session behind the door. The console has been logged in as infmac since 28 October (who: infmac console), the machine never sleeps (pmset sleep 0), and the screen locks five minutes after the display sleeps (sysadminctl: screenLock delay is 300 seconds). Anyone with that one password gets an already-unlocked administrator desktop — the browser sessions, the Cliq client, the terminal, and the staged VM — not merely a shell.

Apple Remote Desktop on 3283

ARDAgent is running as infmac and listening on all interfaces:

$ ps aux | grep ARDAgent
infmac 1125 ... /System/Library/CoreServices/RemoteManagement/ARDAgent.app/Contents/MacOS/ARDAgent
$ lsof -nP -iTCP:3283 -sTCP:LISTEN
ARDAgent 1125 infmac 9u IPv6 ... TCP *:3283 (LISTEN)

The ARD access list is the Remote Access ACL, com.apple.access_remote_ae, which also nests only admin. The Remote Management preferences carry no ARD_AllLocalUsers key, so “all local users” has not been granted. What we cannot see without sudo is the privilege set — whether the allowed administrator can control and observe, send UNIX commands, copy items, or restart the machine. If Remote Management is enabled with the full control privilege, an ARD session is materially stronger than Screen Sharing, and the same password is the only gate.

One structural note from Apple's own guidance: Screen Sharing and Remote Management cannot be on at the same time — "you can't have both" (Apple Support). Since Screen Sharing is the one enabled on this box, Remote Management is off, and the 3283 listener belongs to ARDAgent running inside the console session rather than to an enabled ARD service. It still answers the VLAN and still speaks ARD, which is exactly why the privilege set should be read with the ARD privilege panel rather than assumed to be empty.

05 Kerberos on 88

A Heimdal KDC is running as root and listening on TCP and UDP 88, on all interfaces, since boot on 28 October:

$ ps aux | grep -i kdc
root 147 ... /System/Library/PrivateFrameworks/Heimdal.framework/Helpers/kdc
$ netstat -an -p tcp | grep '\.88 '
tcp4 0 0 *.88 *.* LISTEN
$ netstat -an -p udp | grep '\.88 '
udp4 0 0 *.88 *.*
udp6 0 0 *.88 *.*

This is not a deliberate Kerberos deployment: the machine is not bound to Active Directory (dsconfigad -show returns nothing), there is no /etc/krb5.conf, and the only Kerberos configuration record is a local realm — LKDC:SHA1.44D1767D11… in /Config/KerberosKDC — created by Apple's one-shot configureLocalKDC on 29 July at 12:36, the same minute as /etc/krb5.keytab.

The reason it is exposed at all is in the launchd job. com.apple.Kerberos.kdc keeps itself alive on the state of three other services:

KeepAlive → OtherJobEnabled:
    com.apple.AppleFileServer  true
    com.apple.smbd             true
    com.apple.screensharing    true

So the KDC runs because File Sharing and Screen Sharing are on — it is Apple's local single-sign-on helper for exactly those two services, not something somebody chose. That is the answer to the question in the original request: no, port 88 is not a deliberate KDC role.

Risk is Low, and honestly stated: the realm is machine-local, so an attacker cannot use it against the rest of the estate, and the principal list and pre-authentication flags live in root-only files we could not read. What remains is unnecessary attack surface — a daemon on every office seat that nobody watches, plus the possibility that a local principal without pre-authentication is roastable. Both deserve a check with admin rights, not an alarm.

06 The finding behind all four

No network control, one credential

The application firewall is off, stealth mode is off, and block-all is off:

Firewall is disabled. (State = 0)
Firewall stealth mode is off
Firewall has block all state set to disabled.

Nothing on the host filters anything. Every one of the four services is reachable from every one of the roughly dozens of devices on the office VLAN, and each of them ends at the same account: infmac, uid 501, member of admin, logged in at the console since 28 October. The machine also hosts the staging VM and a self-hosted GitHub Actions runner registered to the organisation, so a single credential does not merely open a file share — it reaches the build pipeline and the VM underneath.

Two accounts exist on the box. infmac is the administrator and is in every relevant group: com.apple.access_ssh, com.apple.access_screensharing, com.apple.access_remote_ae. hermes-deploy (uid 599) is a standard user, but it is in com.apple.access_ssh and in the file-sharing group, so it too has a shell on 22 and a seat on 445 — with no administrator rights, which is the right shape for a service account and the wrong shape for the share if the point was to keep the admin account off the network.

That is the exposure in one sentence: the security of four network services is the strength of one password, with no packet filter, no second factor and no separate account in between.

07 What to change, in order

All of these need an administrator password on the box, so they are for Tuan to run with Ricardo's approval. Nothing here was applied — the shell we hold has no passwordless sudo, and changing a live business machine is not ours to do unasked.

  1. Put a filter in front of the box.
    Turn the macOS firewall on and allow only what is used, or — better, because it survives a reboot into a bad state — allow-list these four ports to a management subnet at the router, and reach them over VPN from anywhere else. The firewall options and what each one blocks are documented by Apple.
    Tuan · needs admin · highest value, lowest effort
  2. Decide whether SMB is used at all.
    If nothing mounts INF’s Public Folder, turn File Sharing off: port 445 disappears, and the local KDC stops with it. If it is used, keep it and do the next two items.
    Ricardo decides · Tuan executes
  3. Close the guest flags and require SMB signing.
    sudo dscl . -delete "/SharePoints/INF’s Public Folder" smb_guestaccess, then sudo defaults write /Library/Preferences/SystemConfiguration/com.apple.smb.server SigningRequired -bool true and restart smbd. Signing is the control that kills NTLM relay; the macOS Security Compliance Project is the reference baseline for this class of setting.
    Tuan · needs admin
  4. Decide on Remote Management.
    If nobody uses ARD, turn it off and keep Screen Sharing for support — port 3283 goes away. If it is used, read the privilege set first and strip everything except what the support workflow needs.
    Tuan · needs admin
  5. Keep Screen Sharing on administrators, and stop sharing the console admin.
    The ACL is already “administrators only”; the defect is that the administrator is also the account sitting unlocked at the console. A dedicated standard user for file sharing, with admin reserved for administrative work, breaks the “one password opens everything” chain.
    Ricardo approves · Tuan creates the account
  6. Stop the KDC if it is not needed.
    sudo launchctl disable system/com.apple.Kerberos.kdc. Do this only after confirming that SMB and screen-sharing sign-in to local accounts do not depend on it — and check the principal list with sudo kadmin.local -q list_principals before deciding.
    Tuan · needs admin · after item 1
  7. Turn off SSH password authentication.
    sshd_config sets no PasswordAuthentication directive, so the default (yes) applies — a password guess against port 22 is a second, quieter way to the same account. Keys are already in place for both accounts we use.
    Tuan · needs admin
