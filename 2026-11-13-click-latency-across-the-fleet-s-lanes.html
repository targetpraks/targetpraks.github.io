What a click actually costs

Measured, not estimated: every lane below was run against a live target, and the click had to show up on screen before it counted. Same machine, same minute, ten to twenty-five clicks per lane. The spread is three orders of magnitude — 1.2 ms to 522 ms per click — so the lane you pick decides whether a thousand-click setup takes two seconds or nine minutes.

The fast-looking option is the broken one. fast_path=on reports 2.2 ms/click and lands 0 of 10 presses, twice, on two different configurations. It sends input and returns without waiting for the app to consume it. If you switch it on for a bulk run you will get a beautiful throughput number and an unchanged screen. The same applies to my own run_script JS loop: 410 ms/click and 0/10 landed, so it is not the shortcut it reads like.

What to actually do

If the setup lives in a browser

  • Drive the DOM, headless: humanize=False + force=True → 3.5 ms, ~286 clicks/s.
  • Use page.click without force (31 ms) only where you actually need actionability checks.
  • Never leave humanize on for bulk work: it is 90× slower and only matters when evading bot detection.
  • A 1 000-click setup: 3.5 seconds.

If it is a native app

  • post_action_wait="none" on every click: 522 → 204 ms, still 10/10 landing.
  • Skip run_steps for repeated clicks — it was slower (271 ms) than single calls.
  • Attack the click count instead of the click cost: set_value for fields, hotkeys for menus, one type_text per field.
  • A 1 000-click setup: 3.4 minutes — the floor for AX on this driver.
Reproduce: bench_cua2.py (native, with the correctness gate) and bench_web.py (browser, humanize on/off) in ~/AI Hub/camoufox. Targets: a backgrounded Calculator instance and a local HTML page with 60 buttons — no network in the loop, so these are protocol costs, not page-load costs. Numbers are medians of one run each on an idle M-series mini; treat ±20% as noise.
