3. What was actually delivered — #7 / AC-10

AC-10 reads: "prefers-reduced-motion disables all canvas and Framer Motion animations." It wasn't true. I measured the defect before changing anything, and found three causes, not the one the issue assumed:

  1. MotionConfig reducedMotion="user" only disables transform and layout animations. Opacity tweens keep running. That was already in the tree and looked like a fix.
  2. initial={{}} is not "skip the animation" — Framer still tweens from the current value. initial={false} is the sentinel.
  3. Framer's own useReducedMotion() never re-renders. Its source is useState(prefersReducedMotion.current) with no subscription, and carries a TODO admitting it. It is correct on first render and then never updates — which is exactly why the live-change clause failed.

Measured on unfixed main: 5 entrances on / at 800/1000/800/600/300 ms — the hero heading and paragraph among them — plus 2 on /book-briefing/ and 3 on /packages-pricing/. Same count, same durations, same elements the issue reported.

After: 0 under reduce, 84 when motion is allowed (so it is not a blanket disable), 0 elements still fading after a live flip. reports/ac10/*.json hold the raw measurements.

Deliberately not done: no threshold lowered, no test that merely waits for animations to settle, no remount of the app.
