PRD: dsh-maio-nexus — Unified DeepSeek Harness Plugin Suite + Ecosystem Adoption

Targets: Web profile (dsh web), official DSH Desktop app, and the super-agent bundle (dsh-superagent-prototype, MIT, research code) · Memory: Mnemosyne (active Hermes provider, per-profile SQLite, isolation ON) · Vault: Beast / OpenKnowledge (AI-Space, read-only) · Model path: local Ollama gateway :11434/v1 · Staged by Adrianna A, reviewed and manually installed by Ricardo.

Executive summary. Two deliberate workstreams, one plan. (A) Build a custom suite — dsh-maio-nexus — that gives DSH shared memory with Hermes and read-only recall over the Maio Hub vault, designed to run inside the super-agent's Router/Worker split rather than as a plain session plugin. (B) Adopt a curated, verified subset of the community plugin ecosystem alongside it — each with an explicit adopt / evaluate / reject decision and a manual install step owned by Ricardo.

What changed in v4. The super-agent design is now a first-class constraint: a long-lived Router that talks to people and dispatches work, plus context-isolated Worker sessions that execute in parallel. The memory bridge and vault recall are split across those layers — Router gets the shared context and the dispatch decision, Workers get a scoped slice and a per-task tool — instead of pretending DSH is one flat session. v3 still stands on memory (Mnemosyne) and governance.

1. Vision & Problem

Problem. DeepSeek Harness sessions are isolated from the rest of Ricardo's Mac stack. A DSH session cannot see Hermes memory (user preferences, standing rules, cross-session facts), cannot query the Obsidian vault (Maio Hub) for PRDs, research or guidelines, and has no curated, risk-assessed path to the community plugin ecosystem. With the super-agent, the problem gets sharper: work is spread across a Router and many Workers, so context must be deliberately placed — shared where it must be shared, isolated where it must be isolated.

Solution. dsh-maio-nexus registers Cordis handlers that (a) feed the Router a compact shared memory + vault context, (b) let the Router package a scoped context slice for each Worker dispatch, (c) give Workers a read-only vault_recall tool and a scoped Mnemosyne query, and (d) return durable facts from Workers to the Router, which is the only writer through Hermes' memory tools. No second memory store; no cross-worker leakage.

Memory source of truth (verified on this Mac, 2026-11-02). Provider mnemosyne; profile_isolation: true; store ~/.hermes/mnemosyne/data/mnemosyne.db (227 MB, WAL 88 MB at check time); schema includes working_memory (10,004 rows), episodic_memory (0), facts, fts_working family, graph_edges, triples, memory_embeddings; embeddings are local (nomic-embed-text, 768-dim, via 127.0.0.1:11434/v1). A mnemosyne_stats call returned database is locked during the check — the file was under an active writer, so the read path needs a busy timeout and retry.

2. Super-agent fit — how nexus works with the Router/Worker

The prototype's architecture, from its README and the DeepSeek design article: a long-lived Router handles people and dispatches; context-isolated Workers do one work item each in their own session and directory; events (chat, GitHub, CI) arrive as triggers; a Watchdog checks progress; state lives in a database while compute and machine are separated. The Router "cannot do the work" — it only decides which Worker gets which request.

2.2 The Router's dispatch decision (the "vote" step)

The prototype has no formal voting mechanism. The Router's dispatch is a rules-first, model-judged decision: deterministic filters run in code, and the model judges only what passes. nexus models that step explicitly in nexus-context-packet: the Router picks the Worker type, assembles the scoped memory + vault slice, and records why. If "router vote" meant a literal multi-agent vote, say so and I will add a scoring variant — otherwise this is the decision step the PRD implements.

2.3 Event-driven recall (proactive, but gated)

  • Triggers: new or changed vault note, a Mnemosyne write, a chat message, a GitHub comment, a CI result. Code filters first — a note that fails the AI-Space scope filter never reaches a model.
  • Observe mode: unrequested proactive work is recorded only until Ricardo approves the rule that allows it — matching the prototype's "acts only when asked, or when a written rule allows it."
  • Freshness: a vault write invalidates the recall cache and schedules a reindex; the Router never answers from a stale index without saying so.

2.4 Continuity across channels

Discord, Telegram, DSH Web and DSH Desktop all terminate at the Router, so the same memory slice and vault scope apply everywhere. A Worker subscribes to its own thread, so follow-ups skip the Router — exactly the prototype's behavior — while the Router keeps the cross-channel record.

Acceptance criteria. F1 (memory): a canary fact written through Hermes' Mnemosyne tool is recalled by a DSH session unprompted. F2 (vault): vault_recall returns exact vault snippets and vault file hashes are unchanged. F3 (bundle): one bundle installs on Web, Desktop and the prototype without root or core breakage. F4 (index): nightly job completes silently and idempotently. S1 (Router): the Router injects shared memory + vault context and produces a context packet for every dispatch. S2 (Worker isolation): Worker A cannot recall Worker B's scratch facts or open a sibling profile's store. S3 (follow-up): a follow-up in the same thread reaches its Worker without a Router re-decision; the Router still records it. S4 (event freshness): a vault write is visible to recall within the configured SLA (default 5 min) or the answer says "stale index". S5 (watchdog): a forced Mnemosyne lock is detected, reported in plain language, and the recall path degrades fail-closed. S6 (cross-channel): a plan agreed in Discord is recalled in a DSH Web session for the same profile. Fail-closed: if Mnemosyne is locked/unreachable, DSH proceeds with built-in MEMORY.md/USER.md context and logs a warning — no fatal errors.

5. Plugin governance policy (applies to A and B)

  • No blind installs. Every plugin is staged, its dsh.bundle / cordis.patch.yml read, network calls and filesystem writes reviewed, license checked.
  • Ricardo installs. Adrianna A stages; Ricardo installs after reviewing the manifest. I never install third-party code or change a live profile on my own.
  • One memory source of truth. Mnemosyne. No parallel store, no direct DB writes; Worker facts return to the Router, which writes through Hermes' memory tools.
  • Read-only vault. No plugin gets write access to Maio Hub. Beast remains the sole writer via OpenKnowledge.
  • No credentials. No key, token or password enters any plugin config, log or artifact — the credential hard stop applies unchanged.
  • Proactive work is gated. Unrequested actions run in observe mode until Ricardo approves a written rule — the prototype's own philosophy.
  • Fail-closed and revertible. A plugin failure degrades to standard DSH behaviour; every install has an uninstall step and a Safe Mode first run where offered.

6. UX & UI design

DSH Settings → Maio Nexus: Mnemosyne status (provider, DB path, last write, lock/degraded badge), vault scope (AI-Space default, read-only badge), Router/Worker panel (active Workers, dispatch reasons, context-packet sizes), recall latency and token telemetry, adopted-plugin list with version + install state. Third-party plugins keep their own pages; the panel only reports.

7. Non-functional requirements

  • Security: 100% local; no vault, memory or credential content leaves the machine; read-only vault and Mnemosyne; no telemetry.
  • Performance: vault FTS recall < 50 ms warm; Mnemosyne recall < 100 ms warm; Router dispatch adds no visible latency; context packets stay within a token budget (default 2k).
  • Reliability: SQLite busy timeout + bounded retry; fail-closed; nightly index idempotent; Watchdog detects lock/staleness.
  • Compatibility: DSH ≥ 0.2.x on Web and Desktop; super-agent bundle format tracked as research code (MIT, not an official product; may break); Mnemosyne schema read via documented tables with capability detection.

Out of scope. Installing any plugin without Ricardo's sign-off; writing to the vault; sending credentials to any plugin, gate or sandbox; auto-merging upstream code; replacing Mnemosyne or Beast; building against Hindsight or a second memory store; pointing the super-agent prototype at a real repository without an allowed list and observe mode.
