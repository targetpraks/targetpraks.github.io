1. Problem and vision

1.1 The request, in the owner's words

"Goal is to build out a PRD for this catalogue. It needs to include absolutely everything for ACDC Express, Local Farmer, Papa Pasta, Infinity Brands. It needs to be able to toggle what is or needs to see what is always… always a product that has to be in stock, and it should show the minimums and maximums of that product. And then also, it should allow a manager to sign off on, maybe loading new products. So, when a new product comes in, it's got a section says 'Newly added', so that we can then sign off on the artwork, and that can be done in each kind of section. I need all of Infinity Brands team members to have access to this. So it needs to be hosted on a link that everyone will have access to… ClickUp login or Zoho login to the application so that you can sort out any form of authentication."

1.2 What that means, requirement by requirement

# Owner's words Requirement as written Type
R1 "absolutely everything for ACDC Express, Local Farmer, Papa Pasta, Infinity Brands" Every active item in those four brands appears in the catalogue, grouped by brand then section P0
R2 "toggle what is or needs to [be]… always a product that has to be in stock" A core-range flag per item plus a toggle that shows only core items; a second toggle for stock health (below min / within / above max) P0
R3 "show the minimums and maximums of that product" Minimum and maximum stock level shown on every item, visible to all staff, editable by managers P0
R4 "allow a manager to sign off on loading new products" A per-section approval queue; a new product cannot be shown as live until a manager approves it P0
R5 "a section says 'Newly added', so that we can then sign off on the artwork" New items land in Newly added with their artwork image; approval is given on the item and its artwork, with a comment on rejection P0
R6 "that can be done in each kind of section" The Newly added queue exists inside every brand and every section, plus one cross-brand queue for managers P0
R7 "all of Infinity Brands team members to have access… hosted on a link" One HTTPS address; every team member signs in; no client install P0
R8 "ClickUp login or Zoho login… sort out any form of authentication" Single sign-on through one of the company's existing identities; role (staff / manager) derived at sign-in P0

One sentence of the request is ambiguous and is recorded as an open question (§17 Q1): "toggle what is or needs to see what is always…". This PRD reads it as two separate toggles — "core range only" and "stock health" — because that is the only reading that gives the sentence a distinct meaning from R3.

1.3 Vision

One link. Every product the group sells or gives away, with its photo, its price, its stock and its limits. Every new product lands in a queue that a named manager must clear before staff ever see it as approved. Zoho Inventory stays the single source of the item; this application is the place people decide about it.

4. Source of truth and data model

4.1 The rule

Zoho Inventory owns the item. Name, SKU, brand, category, price, photo, stock, minimum and — by the MoA's ruling — the maximum and core-range flag as item custom fields, so the item master stays the one place a product is described. The app adds only the approval record and its own audit, plus a read mirror of the limits for fast filtering.

4.2 Entities

Entity Owner Key fields
Item (synced, read-mostly) Zoho item_id, sku, name, brand, category_code, unit, rate, purchase_rate, status, image, stock_on_hand, min_level (Zoho reorder_level), track_inventory
Section App brand + category_code + display order + manager
CatalogueEntry App item_id, section, state (new / approved / rejected / retired), artwork_state (missing / pending / approved / changes_requested), approved_by, approved_at, snapshot_hash
Approval (append-only) App entry_id, action, actor, role, comment, snapshot_hash, created_at
ItemLimit Zoho (custom fields), mirrored read-only in the app item_id, max_level, core_range (bool) — written to Zoho as Maximum Level and Core Range; updated_by, updated_at kept in the app
UserRole App idp_subject, email, display_name, role, brand_scope, section_scope
SyncRun App started_at, finished_at, items_read, items_changed, errors
AuditEvent App actor, action, object, before, after, at

4.3 The snapshot hash — carried over from the generator

The static catalogue already proves this pattern works (b3d648ba…): a SHA-256 over the canonical item payload. The app keeps it per approval, so "what the manager approved" is provable even after the item changes: re-hashing the item as it stood produces the same value. Artwork is included in the hash by its image id and byte length, not its bytes.

4.4 State machine

Zoho item created ──► NEW (Newly added)
                        │  manager reviews artwork + fields
        ┌───────────────┼────────────────┐
        ▼               ▼                ▼
   APPROVED        CHANGES REQUESTED   REJECTED
   (live to staff)  (back to the        (hidden, reason kept)
                     submitter)
        │
        ▼
    RETIRED (item deactivated in Zoho)

Rules: an item with no artwork cannot be approved (R5). A rejected item stays visible to managers with its reason. Retiring in Zoho retires it here on the next sync, never deletes the approval history.

7. Flows

7.1 Sign-in

Identity provider → Cloudflare Access → app session. The app maps the IdP email to a UserRole row. An email with no role row lands as Staff (read-only) and an admin sees them in Settings → Users to promote. No one is ever locked out by a missing role.

7.2 Browse and find

Home → brand → section → card. Or type a SKU anywhere and press enter. Toggles live in the URL so a manager can send "ACDC Uniform, core only, below min" as a link.

7.3 A new product arrives

  1. An item is created in Zoho (by whoever loads products today), with a photo attached.
  2. Nightly sync (or an admin's refresh) creates a CatalogueEntry in NEW and it appears in Newly added for its section.
  3. The section manager opens it: artwork large, fields beside it, "check these" list (name, category, price, unit).
  4. Approve → entry becomes APPROVED, snapshot hash recorded, item visible to staff. Reject → comment required, entry REJECTED, the person who loaded it is named in the comment thread.
  5. The history stays forever; a later edit to the item in Zoho creates a "changed since approval" flag rather than silently replacing what was signed off.

7.4 Setting a limit

Manager opens Limits → filters "not set" → sets min and max → saves. Change is audited. If a max is set below the min, the form refuses with a plain sentence. Zoho's reorder_level takes the min; the max and the core flag are written to the two item custom fields.

7.5 Rejection and re-submission

A rejected item stays in Newly added for managers with the reason; once the artwork is replaced in Zoho and the sync runs, the manager sees the new image beside the old one and can approve.

9. Authentication and hosting

9.1 The choice

Three viable lanes, with the evidence that decides it:

Lane Coverage today New accounts Role model Cost
ClickUp login (OAuth) 39 members in workspace 4627083, verified live None — the team is already there ClickUp member + app-side role table R0 (Business plan already paid)
Zoho login (OAuth / Zoho Directory) 26 Inventory users, 12 active None for Zoho users; staff without a Zoho seat need one Zoho roles exist (8 job roles built 2026-11-24) Zoho seats
Cloudflare Access email PIN Any company email None App-side role table R0 (Access included)

The MoA chose Zoho login, and its reason is sound: the same OAuth token can read Inventory, and staff already live in Zoho Mail, Projects and WorkDrive. But the premise behind the vote — "every staffer already has a Zoho One account" — is unverified, and the one number we can measure points the other way: Inventory holds 26 users with 12 active, while ClickUp holds 39 members. Zoho's directory may be larger than its Inventory seats (a seat is not a login), but until that is counted, the safe reading is:

  • Primary — Zoho login, if the Zoho Directory (or Zoho One user list) is confirmed to contain all 39 team members. That is a five-minute check in the Zoho admin console, and it is Q2.
  • Fallback — ClickUp OAuth, which provably covers the team today (39 of 39, verified).
  • In both cases Cloudflare Access stays in front as the edge gate and the sign-in audit, so an unauthenticated request never reaches the app even if the app's own auth has a bug.

9.2 Hosting

The Infinity staging server already publishes internal apps behind Cloudflare Access in one command, verified live:

  • staging-host register catalogue --port <port> --access emails --allow @infinitybrands.co.za
  • HTTPS name: https://catalogue-staging.infinityapps.co.za (or a production-style name on Ricardo's instruction)
  • Container on staging-ingress, no host ports; database on the app's private network

That gives a real link, real authentication and real audit of sign-ins without buying a product. If the MoA instead picked Zoho Creator, hosting moves to Zoho and this section becomes a configuration task rather than a build.

9.3 Sessions

HttpOnly, Secure, SameSite=Lax cookie; 8-hour session; server-side role check on every API call; no item data in the browser's local storage.

10. Sync and integrations

Integration Direction Frequency Failure behaviour
Zoho Inventory items + stock + images read nightly 02:00 + admin on demand keep last good data, show staleness, alert
Zoho reorder_level (min) write on manager save retry with backoff; if it fails, the app value stands and the row is flagged "pending Zoho"
Zoho item custom fields (max, core) write on manager save same
IdP directory read on sign-in deny with a plain message
Cliq / email notifications (P1) write on NEW items queue and retry

Two item custom fields must be created in Zoho before the limits feature ships: Maximum Level (number) and Core Range (checkbox). The minimum uses the native reorder_level, which exists on every item today and is set on none.

Measured constraint: Zoho throttles at roughly 100 requests/minute and the image endpoint blocks for 15+ minutes after a burst — the sync must pace at ≤ 1 request/second for images, cache them, and never re-fetch an unchanged photo.

12. Testing strategy

  • Unit: state machine (NEW → APPROVED/REJECTED → RETIRED), scope checks, limit validation, hash canonicalisation.
  • Contract: a recorded Zoho read fixture so sync tests never hit the live org; one live read-only smoke test per release.
  • End-to-end: sign-in → find a section → open an item → approve as manager → verify it appears for staff; reject → verify hidden with reason; scope denial → 403.
  • Acceptance: each P0 feature's criteria in §5.1 becomes a test case; the count check (729 items, one section each) runs on every deploy.
  • UAT: three real managers (one per brand, ACDC split in two) clear five seeded new items before launch.
  • Evidence rule: a feature is done when the test output is quoted, not when it "should work".

18. What "done" looks like

A person in the warehouse opens one link on their phone, signs in with the account they already have, finds any of the 729 products, sees its photo, price, stock, minimum and maximum, and can tell at a glance which products must never run out. A manager opens Newly added, looks at a new product's artwork, and approves or rejects it with a comment that will still be there in three years. Nobody edits a spreadsheet to publish a catalogue.
