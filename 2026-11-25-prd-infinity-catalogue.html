4. Source of truth and data model

4.1 The rule

Zoho Inventory owns the item. Name, SKU, brand, category, price, photo, stock, minimum and — by the MoA's ruling — the maximum and the stock policy as item custom fields, so the item master stays the one place a product is described. The app adds only the approval record, the brand-approver table and its own audit, plus a read mirror of the policy and limits for fast filtering.

4.2 Entities

Entity Owner Key fields
Item (synced, read-mostly) Zoho item_id, sku, name, brand, category_code, unit, rate, purchase_rate, status, image, stock_on_hand, min_level (Zoho reorder_level), track_inventory
Section App brand + category_code + display order + manager
CatalogueEntry App item_id, section, state (new / approved / rejected / retired), artwork_state (missing / pending / approved / changes_requested), approved_by, approved_at, snapshot_hash
Approval (append-only) App entry_id, action, actor, role, comment, snapshot_hash, created_at
StockPolicy Zoho (custom fields), mirrored read-only in the app item_id, stock_mode (STOCKED | MADE_TO_ORDER | UNSET), max_level, lead_time_days (made-to-order only), policy_note — written to Zoho as Stock Policy (picklist) and Maximum Level (number); updated_by, updated_at kept in the app
BrandApprover App brand, idp_subject, email, display_name, granted_by, granted_at, active — the per-brand approval authority, filled from the Zoho directory
UserRole App idp_subject, email, display_name, role, brand_scope, section_scope
SyncRun App started_at, finished_at, items_read, items_changed, errors
AuditEvent App actor, action, object, before, after, at

4.3 The snapshot hash — carried over from the generator

The static catalogue already proves this pattern works (b3d648ba…): a SHA-256 over the canonical item payload. The app keeps it per approval, so "what the manager approved" is provable even after the item changes: re-hashing the item as it stood produces the same value. Artwork is included in the hash by its image id and byte length, not its bytes.

4.4 State machine

Zoho item created ──► NEW (Newly added)
                        │  manager reviews artwork + fields
        ┌───────────────┼────────────────┐
        ▼               ▼                ▼
   APPROVED        CHANGES REQUESTED   REJECTED
   (live to staff)  (back to the        (hidden, reason kept)
                     submitter)
        │
        ▼
    RETIRED (item deactivated in Zoho)

Rules: an item with no artwork cannot be approved (R5). An item with no stock policy may be approved, but it stays flagged "policy not set" in the manager's queue until a brand approver sets it — because 0 of 729 items carry one today and blocking on it would stall the catalogue. A rejected item stays visible to managers with its reason. Retiring in Zoho retires it here on the next sync, never deletes the approval history.

5.1 P0 — the app that ships first

ID Feature Acceptance criteria
F1 Single sign-on through Zoho Every one of the 39 team members can sign in with the Zoho account they already have; no account created by us. A first-time user reaches the catalogue in ≤ 3 clicks. Sign-out clears the session. Unauthenticated requests never see item data. Proven by a sign-in from each of the 39 during the pilot, recorded in the audit.
F2 Brand and section browsing Home shows the four brands with item counts. Opening a brand lists its sections with counts. Opening a section shows a card grid: photo, name, SKU, price, min/max, stock. Every in-scope item appears in exactly one section — a count check against Zoho returns 729.
F3 Search and filter chips Free-text search over name and SKU returns in < 300 ms at 729 items. Filter chips: All · Must be in stock · Made to order · Policy not set, plus Stock health (below min / within / above max) and Status (new / approved). Filter state survives a page refresh (URL query).
F4 Item detail Photo, description, SKU, brand, section, unit, list price (ex-VAT), purchase price to approvers only, the stock-policy pill, stock on hand, min, max (or lead time when made to order), and approval history. Blank limits read "Not set", never 0.
F5 Newly added queue per brand and section Each brand and section shows a Newly added count. The queue lists items in NEW state with artwork thumbnail, submitted date, the fields an approver must check, and the stock policy the brand default would apply. Ricardo has one cross-brand queue.
F6 Approve / reject with artwork — one click, per brand Only a configured approver for that brand (or Ricardo) may act. Approve is a single click that requires the artwork image to have loaded; it records actor, time, role and snapshot hash. No e-signature. Reject requires a comment (≥ 10 characters). An approved item becomes visible to staff immediately (≤ 2 s). Approving an item with no image is impossible.
F7 Roles, brand authority and scoping Server-side enforcement, not just hidden buttons: staff read-only; an approver acts only inside the brands assigned to them; Ricardo on all brands; admin-only settings. The brand-approver list is managed in Settings from the Zoho user list (search a name, grant a brand, revoke). A direct API call outside scope returns 403.
F8 Sync with visible health Nightly full sync + on-demand refresh by an admin. Sync writes a SyncRun row with counts and errors. If Zoho fails or throttles, the app keeps serving the last good data and shows "last synced 6h ago" rather than an empty catalogue.
F9 Audit trail Every approval, rejection, role change, stock-policy flip and limit change is an immutable row: who, what, before, after, when. Exportable to CSV by an admin.
F10 Stock policy — the on/off switch Every item carries exactly one state: Must be in stock or Made to order (plus "not set" until someone decides). A single switch flips it, per item or in bulk from the Stock policy screen; a brand default covers new items. Staff see a coloured pill — green "Must be in stock" with min/max, amber "Made to order" with lead time, grey "Not set" — on every card and in the drawer, and the section header shows the split. Made-to-order items never show a minimum. Flipping a policy is audited and mirrored to Zoho within the same request.

7. Flows

7.1 Sign-in

Identity provider → Cloudflare Access → app session. The app maps the IdP email to a UserRole row. An email with no role row lands as Staff (read-only) and an admin sees them in Settings → Users to promote. No one is ever locked out by a missing role.

7.2 Browse and find

Home → brand → section → card. Or type a SKU anywhere and press enter. Filters live in the URL, so an approver can send "ACDC Uniform, must be in stock, below min" as a link.

7.3 A new product arrives

  1. An item is created in Zoho (by whoever loads products today), with a photo attached.
  2. Nightly sync (or an admin's refresh) creates a CatalogueEntry in NEW and it appears in Newly added for its section.
  3. An approver for that brand (or Ricardo) opens it: artwork large, fields beside it, a "check these" list (name, category, price, unit) and the stock policy the brand default would apply.
  4. Approve → one click, entry becomes APPROVED, snapshot hash recorded, item visible to staff. Reject → comment required, entry REJECTED, the person who loaded it is named in the comment thread.
  5. The history stays forever; a later edit to the item in Zoho creates a "changed since approval" flag rather than silently replacing what was signed off.

7.4 Setting the stock policy — the switch

An approver opens Stock policy → filters "not set" → for each item flips the switch:

  • ON — Must be in stock: the item is forced as a stocked line. Min and max become required; the card carries a green pill and the stock-health filters apply to it.
  • OFF — Made to order: the item is made when ordered. The minimum disappears (it is meaningless), lead time in days is asked instead, and the card carries an amber pill.

Saving is one click, audited, and mirrored to Zoho (Stock Policy picklist, Maximum Level, plus reorder_level for the min). If a max is set below the min the form refuses with a plain sentence. Bulk set: select a section or brand, choose the state, apply; each item still writes its own audit row and its own Zoho call, paced. A brand can carry a default so every new item arrives with a state instead of "not set".

7.5 Rejection and re-submission

A rejected item stays in Newly added for approvers with the reason; once the artwork is replaced in Zoho and the sync runs, the approver sees the new image beside the old one and can approve.

7.6 Deciding who approves a brand

Settings → Brand approvers → pick a brand → search the Zoho user list by name or email → grant. Revoke is the same row. Ricardo holds every brand by default and cannot be revoked from himself. A brand with no approver other than Ricardo shows a warning on the brand card, so "nobody can approve this" is visible rather than discovered on a Friday.

Decided: Zoho login. Ricardo confirmed on 2026-11-25 that the Zoho user list carries all 39 team members, which settles the coverage question the MoA could not answer from the Inventory seat count (26 users, 12 active — a seat is not a login). The same OAuth token reads Inventory, and staff already live in Zoho Mail, Projects and WorkDrive, so one identity does the whole job.

  • Primary — Zoho login, confirmed for all 39.
  • Fallback — ClickUp OAuth stays wired but unused, and is switched on only if a real sign-in fails during the pilot. 39 of 39 verified in ClickUp workspace 4627083.
  • Cloudflare Access stays in front either way, as the edge gate and the sign-in audit, so an unauthenticated request never reaches the app even if the app's own auth has a bug.
  • Roles come from the app, not Zoho: the directory proves who a person is; the brand-approver table (§4.2) decides what they may approve.
  • Evidence note. The coverage figure rests on Ricardo's confirmation, not on a machine count: the fleet's current Zoho token carries no Zoho Directory scope, so both directory endpoints answered 404 when probed on 2026-11-25 (recorded in scripts/scratch probe_directory.py). The pilot therefore proves coverage the hard way — a recorded sign-in from each of the 39 before staff launch.

10. Sync and integrations

Integration Direction Frequency Failure behaviour
Zoho Inventory items + stock + images read nightly 02:00 + admin on demand keep last good data, show staleness, alert
Zoho reorder_level (min) write on manager save retry with backoff; if it fails, the app value stands and the row is flagged "pending Zoho"
Zoho item custom fields (Stock Policy, Maximum Level) write on approver save same
IdP directory read on sign-in deny with a plain message
Cliq / email notifications (P1) write on NEW items queue and retry

Two item custom fields must be created in Zoho before the policy feature ships: Stock Policy (picklist: Must be in stock / Made to order) and Maximum Level (number). The minimum uses the native reorder_level, which exists on every item today and is set on none. Core Range from v0.9 is dropped — the picklist replaces it, because a checkbox cannot express "made to order".

Measured constraint: Zoho throttles at roughly 100 requests/minute and the image endpoint blocks for 15+ minutes after a burst — the sync must pace at ≤ 1 request/second for images, cache them, and never re-fetch an unchanged photo.

12. Testing strategy

  • Unit: state machine (NEW → APPROVED/REJECTED → RETIRED), brand-scope checks, stock-policy state transitions (stocked ↔︎ made-to-order, min required only when stocked), limit validation, hash canonicalisation.
  • Contract: a recorded Zoho read fixture so sync tests never hit the live org; one live read-only smoke test per release.
  • End-to-end: sign-in → find a section → open an item → flip its stock policy → verify the pill and the Zoho field; approve as that brand's approver → verify it appears for staff; reject → verify hidden with reason; a TLF approver attempting an ACDC approval → 403.
  • Acceptance: each P0 feature's criteria in §5.1 becomes a test case; the count check (729 items, one section each) runs on every deploy.
  • UAT: three real managers (one per brand, ACDC split in two) clear five seeded new items before launch.
  • Evidence rule: a feature is done when the test output is quoted, not when it "should work".
