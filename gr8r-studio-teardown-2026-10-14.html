Is it hard to build something like this? No — and that is the trap.

The app behind the tweet is a front-end shell: 4,646 lines of source, zero endpoints, zero database, zero real auth. The pretty 10% has 100% of the attention; the other 90% is the part that takes the months — and we have already paid for most of it.

1 · What it actually is

Three readings, in the order they matter.

Their own admission

“The app runs in the browser with local demo data, and it is structured so a real API can replace that data later.”

Signed in as a demo user; any email containing @ with a 4-character password is accepted. Workspace data lives in the browser.

The demo you can click

The deployed demo isn't even the Next.js repo — it's a single 357,788-byte Vite bundle with 1 outbound call and no API anywhere in it.

Every task, project and person is hardcoded text.

What is genuinely good

The taste: 73,473 bytes of hand-tuned CSS, a real design system, 24 screens, drag-and-drop board, ⌘K search, drawer with subtasks and comments.

That is the hard-to-fake part, and it is a copyable shell.

The conclusion

We already own stages 2–4: schema, migrations, sessions, invites, password reset, roles, audit log, e2e tests.

A task workspace on top of that is a UI project, not an app project.

Recommendation

  1. Don't clone it. Cloning buys the look and re-buys the backend we already run.
  2. Take the shell to our data. Put a gr8r-grade board / list / timeline in front of Constellation's 24 models — or in front of Paperclip's ticket store, which is already a real, persistent work queue with lanes, assignees and blocked states.
  3. Prove the estimate before spending it. One-day spike: a coding agent builds the board + list + task drawer against the Constellation dev database, so stage 1 is measured instead of argued.
