App Planning & Build Workflows — Design

For: Targetpraks (Ricardo)
What this is: Two runnable, agent-orchestrated workflows — one that turns an app idea into a detailed PRD, one that turns that PRD into a shipped, tested app. Both route every decision through the mixture of agents (LLM Council) first, and the local decision model (d3-flash gate) for bounded choices, exactly as specified.

Decision arbitration — the rule that runs through both

Every time the workflow hits a decision, it asks two questions and routes:

Decision type Examples Route
Deliberative architecture, UI direction, "should we build X", conflict resolution, high-stakes trade-offs Mixture of agents first → council_deliberate (4 advisor seats + chairman)
Bounded pick from a shortlist, yes/no, classify, score, priority tag, lane routing Local decision model → mcp__maio_gate__decide / ask, or gate --q
Both apply a deliberative call that reduces to a shortlist Council frames the shortlist + criteria → local gate makes the pick
Owner-only money, legal, external publication, live-system writes, final merge Ricardo — prepare, then wait

Council advises; it never authorises. Money/legal/ship always comes back to Ricardo. Every gate row is logged to AI-Drive/Agent-Output/<slug>/gates.csv. Secrets never go into gate state or the council question.

Portable fallback (plain Claude Code, no Hermes tools): decision-gates → scripts/portable-gate.py for the bounded layer, and 3–5 parallel sub-agent advisors in place of the council.

Workflow 1 — Planning (idea → detailed PRD)

Skill: app-planning-workflow

Steps and the skills each uses:

Step What happens Skills / tools
0 Intake: capture the idea + constraints; scan the repo if it exists codebase-inspection
1 Bounded clarification — 2 rounds, ≤7 questions each; facts researched, not asked; deferred decisions arbitrated grilling (+ council_deliberate / local gate)
2 Domain language: GLOSSARY.md + ADR seeds grill-with-docs, domain-modeling
3 Structure: module map, data model, IA, integrations, diagrams codebase-design, archify, architecture-diagram
4 UX/UI (heavy): flows, hi-fi mockups, design tokens, a11y claude-design, prototype, popular-web-designs, design-md
5 PRD synthesis: vision, users, features + acceptance criteria, structure, UX flows, UI system, NFRs, test strategy, decision log repo-prd-authoring / vault-report-authoring
6 Sign-off check before publish local decision lane (gate --q ready choice)
7 Publish + hand to build publish-document

The "no millions of questions" guarantee: grilling normally drives a full design tree in rounds. Here it's capped at 2 rounds, ≤7 questions per round, every question carries a recommended answer, all discoverable facts are looked up by sub-agents, and anything the user defers is resolved by the council or the gate — not re-asked.

PRD table of contents (enforced): Vision & problem · Target users & JTBD · Feature list + priorities + acceptance criteria · Application structure (modules, data model, IA) · UX flows + screen inventory · UI design system · NFRs · Testing strategy & seams · Out of scope/assumptions/risks · Decision log.

Workflow 2 — Build (PRD → shipped app)

Skill: app-build-workflow

Steps and the skills each uses:

Step What happens Skills / tools
0 Setup: repo contract, worktree convention, ledger /setup-matt-pocock-skills
1 Slice into tickets — vertical tracer-bullet slices with blocking edges to-tickets
2 Prefactor — make the change easy, then the easy change improve-codebase-architecture, domain-modeling
3 Orchestrate lanes — one worktree/branch/DB/port per ticket; briefs + watchdog chief-of-staff, agent-fleet-orchestration, delegate_task, wayfinder
4 Implement each feature test-first at pre-agreed seams implement / implement-spec, tdd
5 UX/UI build against tokens + mockups; verify with screenshots design-md, claude-design, popular-web-designs, impeccable, auteur
6 Test thoroughly: unit/integration, exploratory QA, security pre-commit tdd, dogfood, requesting-code-review, systematic-debugging
7 Independent two-axis review (Standards + Spec) as parallel sub-agents code-review
8 Acceptance matrix — every P0 → path:TestName + status implement finish pass
9 Integrate, gate at the frozen head, write the PR body; owner-only merge pr, chief-of-staff

Feature orchestration: the PRD's tickets become the unit of work. Independent tickets run as parallel lanes (each its own worktree and branch); dependent ones respect blocking edges. wayfinder handles work too big for one session by mapping it onto decision tickets. The orchestrator never rebuilds a lane itself — it dispatches, verifies handles, and merges in overlap order.

UX/UI, made concrete: design-md locks tokens first (single source of truth), claude-design produces the hi-fi mockups, and the build is only "done" when real screenshots match the design and the user flows pass.

Testing, made concrete: TDD at seams during build; dogfood for real journeys; requesting-code-review (security + quality gates) before commit; full suite serial once at the frozen head; the acceptance matrix turns green tests into proof the PRD was actually met.

Guardrails (both workflows)

  • Council and gate advise; Ricardo authorises money, legal, and ship. Never auto-merge, never push to a remote without his word.
  • Never file, assign, or close work in a live business system on your own — prepare, show, wait.
  • Every claim is backed by real command output; a child's "done" is a self-report until the handle (SHA, test output, file) is verified.
  • Finalized documents go to the vault (via Beast); working notes stay in AI-Drive. Publish every document and link it — never a bare path.
  • English only in anything addressed to Ricardo.
  • Long-term best option over the quickest fix.

Improvements applied (2026-10-30)

Field-verified corrections baked into both skills after review:

  • Liveness authority — orca orchestration worker-list --run <id> --include-remote is the liveness source, not orca worktree ps (which only shows local worktree/pane state).
  • Remote placement — --on takes a saved environment name (never an ssh id, that is --host); remote rejects current/new-child worktrees; address follow-ups by --dispatch <id>; project/repo list accept only --environment (colima returns []), so remote needs project setup-clone first.
  • Claude entry pinning + surface — pin Orca's Claude entry or pass --model (a bare claude can die "Prompt is too long"); prefer --surface chat for native-chat agents so transcripts/accounting parse.
  • Accounting matrix — hook-reliable: claude, codex, hermes; omp chat-not-hook; opencode via relay; freebuff scraped.
  • Model routing by strength — Codex → Go/CI/infra/migrations; Claude → Next.js/TS/UI + PRD; omp/opencode → bulk mechanical/doc; local ollama → triage.
  • Teams vs worktrees — teams = messaging topology (one checkout); worktrees = lifecycle topology (isolated slices).
  • GitHub 403 preflight (blocker) — pushes/PRs 403 on 28/29 repos from Orca/Claude/Codex; probe gh auth status + gh repo view before Step 9, fall back to local commit/bundle and report the gap.
  • Claude-native planning — use AskUserQuestion (1–4/call) + permission-mode plan instead of emulating grilling.
