2. Home Assistant — work dir fills, archive never written (20 nights)

~/.config/maio-stack/home-assistant/backup.sh does docker cp into .work-<date>/ (that step works — today's dir has the 5.9 MB SQLite db, its 4.0 MB WAL and the log), then tar -czf the result. The tar step is denied:

tar: Failed to open '/Volumes/Hiksemi 1TB/AI-Drive/backups/home-assistant/home-assistant-config-2026-11-20.tar.gz'
open /Volumes/Hiksemi 1TB/AI-Drive/backups/home-assistant: operation not permitted

Two things are wrong here, both visible in that one line:

  • the path is spelled backups, not Backups. The real tree is AI-Drive/Backups. APFS resolves it case-insensitively, but TCC grants are matched per path string — the removable-volume grant held for Backups does not cover backups.
  • the job has no TCC wrapper. com.maio.backup runs its script through the osascript/JavaScript shim (~/.config/maio-stack/launchers/backup.sh) exactly because a bare launchd zsh lacks the removable-volume grant; the HA job runs /bin/zsh backup.sh directly.

Proof it is the launchd context and not the data: the same read works from an ordinary shell —

tar -czf /dev/null -C home-assistant/.work-2026-11-20 .   →  exit 0

Twenty nights of .work-* dirs are stacked in the tree (173 MB) because set -e aborts before the rm -rf "$WORK" cleanup. The house config (integrations, auth, automations) currently has no snapshot at all — it exists only inside the Colima VM, which is what this job was written to prevent.

3. Firefly III — a valid gzip of nothing, 12 nights, reported as success

~/AI Hub/firefly/backup.sh line 11:

if ! docker exec firefly-db sh -c 'mariadb-dump … firefly' 2>/dev/null | gzip -6 > "$TMP"; then …

The plist gives the job PATH=/usr/bin:/bin:/usr/sbin:/sbin; docker is at /opt/homebrew/bin/docker:

env -i PATH=/usr/bin:/bin:/usr/sbin:/sbin bash -c 'command -v docker'
→ DOCKER_NOT_IN_LAUNCHD_PATH

So docker exec fails, its stderr is thrown away by 2>/dev/null, gzip compresses the empty stream into a well-formed 20-byte archive, and without pipefail the pipeline's status is gzip's zero. Both guards (gzip -t, -s) pass on an empty gzip. The 02:45 job logs "backup ok" every night and the launchd job exits 0.

What I propose (Ricardo decides — nothing changed)

  3. Constellation: decide which database is production — constellation_dev (28 tables, empty) or constellation_fixture_preview (77 staff / 2,920 scores / 88 consents). If preview is real, the nightly target must move there and get a second target for the empty dev schema; the size floor will keep catching the mismatch until then. Keep the 2026-11-18 manual dump as the newest restorable copy.
  4. Disk: free space on the boot volume before it takes Docker down with it.
  5. Retention: make the purge path-scoped ($D/hindsight, $D/paperclip, …) so it rotates dailies without deleting deliberate archives.
