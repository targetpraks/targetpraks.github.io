1. What this version fixes

  • The Accounts section is a status card, not a dashboard. It reports reachability and the age of the newest database dump, then links out. It shows no money at all.
  • The cockpit has no summary anywhere. There is no net worth, no cash versus debt, no month income and spend, no spend by category.
  • The companion exposes no Firefly read API. The whole ledger is visible only inside Firefly's own web UI, which refuses to be framed.
  • Nothing tells Ricardo which bank statements never arrived. There is no bill monitor, no statement register and no coverage board, in the cockpit or in Firefly.
  • Firefly's own bill, budget, attachment and tag modules are empty, so no existing surface can answer what is missing.

2. Product in five lines

  • One Accounts page answers five questions: how much do I have, where does it sit, what did I spend, what is unpaid, which document is missing.
  • Every number is read from Firefly III over its own API on this Mac. Nothing is typed, estimated or restated from a previous session.
  • Every number carries the timestamp it was read and the account it came from, so a stale figure can never pass for a live one.
  • A coverage board names each monitored account and the exact statements that have not arrived, computed from the statement archive and corroborated against Firefly's last activity date.
  • The page is read-only. No cockpit control can create, edit, pay or delete anything.

5. Design

5.1 Read path

  • The browser never talks to Firefly. Firefly blocks frames and denies inline script, so a browser-side integration is impossible by design, and a token in the page would be a leak.
  • The companion reads the API server-side. A new helper fireflyRead(path, query) in companion/collectors.mjs reads the token from the environment variable FIREFLY_TOKEN and falls back to ~/AI Hub/firefly/.token. The token never enters a log line, a response body, an error string or the browser.
  • Requests are GET only, 6 s timeout, one retry on a socket error, and a 60 s in-process cache so a page refresh cannot hammer the ledger.
  • On failure the last good payload is served with readAt and a stale flag. The page never shows zeros in place of an unknown.
  • Endpoints sit behind the existing Host and Origin guards, the existing rolling rate limiter (per endpoint), and are declared in companion/openapi.mjs so the contract test covers them.

5.2 New endpoints

  • GET /api/firefly/health - reachable, version, latency ms, baseCurrency, tokenPresent.
  • GET /api/firefly/overview - currency, netWorth, cashTotal, debtTotal, ytd {spent, earned, net}, month {spent, earned, net}, accounts summary, readAt.
  • GET /api/firefly/accounts - one row per account: id, name, type, role, balance, currency, lastActivity, daysSinceActivity, coverageGap.
  • GET /api/firefly/activity?from=&to=&limit= - date, description, amount, category, account name. Default: last 30 days, 20 rows, capped at 100.
  • GET /api/firefly/breakdown?from=&to= - spend by category, amount, share of total, plus an "uncategorised" remainder.
  • GET /api/firefly/coverage - the statement board described in 5.4.

Every response carries readAt in ISO local time and source "firefly-api". Numbers are returned as strings with two decimals, unrounded integers kept server-side, so the browser cannot introduce float drift.

5.3 Accounts page layout, top to bottom

  1. Freshness strip: source, readAt, Firefly version, currency, stale badge when the last read failed.
  2. Summary band: net worth, cash, debt, month spend, month income, month net. Six figures, each with its own readAt inherited from the strip.
  3. Account cards: name and masked number, balance, last activity date, days since activity, statement gap count, and a link out to Firefly for any write.
  4. Spend by category, month to date: top eight categories plus an "other" remainder, with the uncategorised share stated explicitly.
  5. Recent activity: 20 rows, date, description, category, account, amount.
  6. Statement coverage board: one row per monitored account with state current, late or never received, and the missing months listed by name.
  7. Data quality notes: base currency mismatch (EUR default versus ZAR data), uncategorised share, backup age, and the count of accounts Firefly knows that the archive does not.
  8. The existing honest note about framing stays, shortened, because it explains why the page is a rendered dashboard and not an embedded Firefly.

5.4 Statement coverage engine

  • A config file companion/firefly-coverage.json holds one entry per monitored account: Firefly account id, display name, cadence (monthly), expected day of month, archive folder, filename pattern, and whether the account is monitored at all.
  • Expected periods are every month from the account's first received statement to the current month. Received periods are files in the archive that match the pattern and parse. Missing periods are the difference, listed by month.
  • State per account: current when the newest received period is the previous or current month, late when the current month has passed its expected day without a file, never received when the archive holds nothing.
  • Corroboration rule: when Firefly's lastActivity falls before the newest received period, the row is flagged "ledger behind archive" instead of "current". This catches the case where the PDF arrived but was never imported.
  • Accounts known to Firefly but configured unmonitored are listed separately as "no source", never silently omitted.
  • The board never claims a statement arrived because a transaction exists, and never infers a missing file from a balance change.

5.6 Failure and empty states

  • Firefly unreachable: strip shows the last readAt and a stale badge, all figures keep their last good values, coverage board still renders from the archive alone, and one line says which call failed and when it last succeeded.
  • Token absent: strip says the token is missing, summary and account panels are not rendered at all, coverage board still renders from the archive.
  • No bills configured: the unpaid line reads "no bills set up in Firefly" rather than 0.00, because zero would be a false statement about unknown debts.
  • No budgets: the budget surface is omitted, not shown empty, until budgets exist.

7. Guardrails

  • Read-only. No POST, PUT, PATCH or DELETE is ever sent to Firefly. The cockpit shows money; Firefly and Ricardo move it.
  • Money and legal stay with Ricardo. This PRD creates no payment, refund, filing or e-signature path, and the dashboard must not grow one.
  • No secret in the browser, in a log line, in an error body or in a published document. The token stays in the environment or in the 0600 file, read by the companion only.
  • No invented number. A failed read keeps the last good value with its readAt, or shows nothing. Zero is never used for unknown.
  • Currency correctness: report ZAR, state the EUR base-currency mismatch once in the data quality note, never sum across currencies.
  • The vault stays read-only. No statement file is moved, renamed or deleted by this work.
  • No new model, MCP server, channel or schedule. Coverage is computed on read, not by a new cron.
  • The repo check stays green: sh ops/check.sh must pass, and the trailing-whitespace finding in apps/top8/site/dist/section/carpet-cleaners.html:145 must be fixed or excluded before this work lands.
  • Work starts from a clean base. The current tree is on feat/esoteric-zone with modified top8 canonical files, so implementation begins in a fresh worktree from main.

11. Risks

  • Currency: Firefly's default currency is EUR while every account is ZAR. A careless use of summary/basic reports zeroes. Mitigation: request ZAR explicitly and assert no EUR keys reach the page (A7).
  • Stale-looking truth: balances from May and July 2026 are correct as last imported and wrong as "today". Mitigation: every figure carries readAt and the account's last activity date, and the coverage board states the gap.
  • API drift: Firefly 6.7.9 is the pinned version. Mitigation: the health endpoint reports the version, and the contract test pins the fields the page uses.
  • Token handling: a token read into a browser bundle would be a leak. Mitigation: server-side only, asserted by A6.
  • Archive naming drift: the archive already mixes "2026-05 - FNB - 62015686093.pdf" with "July 2026.pdf" and "Ricardo Maio 80204463071 June2026.pdf". Mitigation: per-account filename patterns in config, and an "unparsed" state that lists files rather than guessing.
  • Working tree already dirty on feat/esoteric-zone. Mitigation: fresh worktree from main.
