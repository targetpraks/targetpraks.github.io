Root cause: set -o pipefail + grep -q SIGPIPE, tripped by the database growing past 64 KiB

The dump itself is complete and valid, produced right now by the exact command the script runs:

$ docker exec constellation-dev-pg pg_dump -U owner -d constellation_dev --no-owner --no-privileges | gzip > probe.sql.gz
pg_status=0   size=9146   gzip -t OK
CREATE TABLE count: 32   COPY blocks: 32   \restrict/\unrestrict markers: 2   (footer intact)

The script's validation chain (backup.sh:85-86) is:

gzip -t "$CST_PARTIAL" && gzip -dc "$CST_PARTIAL" | head -c 400000 | grep -q "PostgreSQL database dump"

backup.sh:8 sets set -euo pipefail. grep -q exits the moment it matches — and it matches on line 3 of the dump. That closes the pipe under gzip -dc, which dies of SIGPIPE (141), and pipefail propagates 141, so the && chain reports failure. Reproduced exactly:

$ set -o pipefail; gzip -dc probe.sql.gz | head -c 400000 | grep -q "PostgreSQL database dump"
script_chain_exit=141
$ set +o pipefail; gzip -dc probe.sql.gz | head -c 400000 | grep -q "PostgreSQL database dump"
no_pipefail_exit=0

Why it started on 11-27 and not before — the dump crossed the 64 KiB pipe buffer:

Date Gzipped Decompressed Result
2026-11-25 5,647 B 57,418 B — fits in the 64 KiB buffer, gzip exits before grep quits PASSED
2026-11-28 9,146 B 77,472 B — gzip is still blocked when grep quits → SIGPIPE 141 FAILED

The database has simply grown past the point where this check works. It will fail every night from now on, and each night's rm -f "$CST_PARTIAL" (backup.sh:91) throws away a valid dump. Newest retained constellation dump: 2026-11-25 (5,647 B — and at 57 KB of SQL that one is itself a thin early copy).

Constellation is the Infinity Brands staff-assessment database — 45 staff, 94 consents, 1,300+ scores, encrypted esoteric payloads. Its restore point is now three days old and ageing.
