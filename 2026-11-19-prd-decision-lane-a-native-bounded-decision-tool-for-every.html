Decision lane — a native bounded-decision tool for every AgenticOS bot

What v1.1 changes

The external review returned v1.0 as not-ready with seven blocking findings. v1.0's central mistake was saying "reuse the engine, don't fork it" without checking whether the engine could run outside a workflow. It cannot, today. Every blocker is answered below:

Why this PRD

Ricardo's §8 gates run on his own Mac, at 127.0.0.1:8792, for his own agents. That stays personal. What Infinity Brands needs is the same capability inside the work platform — a cheap, typed answer to a bounded question ("is this a work request or a personal one?", "does this credit note go to Finance or EXCO?") without spending a conversational turn on it.

The platform already has most of it:

File Lines What it is
_decide.py 326 Engine: profile resolution, typed question, provider call, confidence, budget hooks
decide_yes_no/_handler.py 54 Yes/no with an unsure port
decide_choose/_handler.py 94 One of 2–255 values
decide_score/_handler.py 70 A rubric score

The capability exists — only inside a workflow. A bot cannot call it mid-conversation, there is no org-level definition of what a gate is, and nothing is logged where an operator can read it.

Product in five lines

  1. One native tool — decide — that any provisioned bot can call inside a turn.
  2. Five gates defined once per organization, versioned, with thresholds and an unsure action.
  3. The answer is a label and a confidence, in about a second.
  4. Below the threshold the answer is unsure and the caller escalates — never a guess dressed as a decision.
  5. Every call is logged once, with cost settled, so the lane can be measured and tuned.

Build plan — the shared service first

This is the finding that changes the shape of the work. The engine is workflow-coupled:

  • decide(config, text, answer) calls context.current() before its try block (D3 in the review proved this by executing the accessor alone: RuntimeError: No workflow dispatch context is active).
  • DispatchContext structurally requires workflow run, node run, node instance and attempt ids, plus an auth context and a dispatcher that settles the cost outbox.
  • A conversation has agent run, org, user and conversation ids — not workflow ids.

Slice 1 — extract a service, keep the nodes as adapters.

DecisionService.decide(
    *, org_id, auth, agent_id | None, run_id | None,
    gate: GateRevision, text: str, answer: dict,
    profile: ResolvedProfile, limits: DecisionLimits,
    spend: CostSink, on_unsure: str
) -> DecisionResult
  • Workflow nodes become thin adapters that build the same inputs from DispatchContext and receive the same result. Their routing, error types and cost reporting are regression-tested unchanged. Legacy node configs keep working: an adapter that receives a boolean/255-option/ten-level node with no gate_revision synthesizes an ephemeral, non-persisted gate revision from the node's own question and options, and the log records gate_key = 'workflow:<node_type>' so history stays readable without inventing a registry row.
  • Guardrail checks and error types are made independent of Failed / WorkflowError at this seam.
  • A conversational adapter supplies attribution and settles cost through the host ledger, not the dispatcher.
  • Do not copy the engine, and do not fabricate workflow ids to satisfy a ContextVar.

Slice 2 — redaction. Slice 3 — gates. Slice 4 — the tool. Slice 5 — log and Monitoring. (See §Build order.)

Redaction — a built component, at two boundaries

v1.0 pointed at a URL validator and called it redaction. Corrected:

  • A versioned detector policy for credentials, card numbers, ID numbers and health data, applied to state, options, question and context_label before provider dispatch.
  • The same policy applied before persistence at every surface that stores or replays text: tool-call arguments, approval payloads, conversation transcripts, replay records and traces. A redactor only inside the new tool would be too late — the host runner stores arguments before the tool is called (E11).
  • A request that still looks like a credential after redaction is refused, not sent, and the refusal is logged with no excerpt. There is no "send the sanitized version anyway" path: a detector hit either redacts a whole field to a placeholder (and the call proceeds) or refuses the call. Which of the two applies is fixed per detector in the policy, and the acceptance criteria test exactly that.
  • Hashing: the log stores a keyed digest of the normalized, approved representation, not a plain hash — a plain digest of low-entropy input (a name, an amount) is reversible by enumeration.
  • Honesty clause: if the caller's own conversation already contained the source text, this lane cannot remove it. The PRD says so; it does not promise erasure it cannot deliver.
  • Proven with synthetic canaries across every retention surface, not by inspection.

Cost — a real booking contract

  • One logical call row per invocation; one or more attempt rows beneath it. Logical call ≠ attempt.
  • Fees booked exactly once to an identity the existing monthly aggregation sees: org + agent + run + call. Decision-log cost and host-ledger cost must reconcile to the same number — no double counting. Owner of the booking is the new service, not the workflow dispatcher: the service writes the ledger entry in the same transaction that closes the attempt, and the dispatcher's own report is suppressed for decisions so a workflow run cannot book the same fee twice.
  • Failed, cancelled and timed-out attempts are included, with cost_state in {settled, partial, unknown}.
  • Unknown price is recorded as a floor and flagged, never silently zero.
  • Concurrency: either a reservation (known upper-bound price held before dispatch) or an explicitly accepted overshoot contract. Choose one and write it down; v1.0 implied neither.
  • When the org cannot afford the call: zero dispatch, a structured error, and a deterministic handoff that does not require another paid chat turn. "Run continues and asks a human" was not a mechanism.

Gate registry

New table decision_gates (org-scoped, versioned):

Column Rule
organization_id, key unique per org. Company set (D2): routing, triage, escalation, data_sensitivity, spend — the doctrine's memory gate is replaced because retaining facts is a platform concern here, not a bot decision
title, question question 1–2,000 chars, phrased as a person would ask it
options 2–8 labels, unique, unsure reserved and rejected as a label
threshold finite, 0–1
on_unsure escalate | refuse | ask_human
escalate_to a platform entity (user id or group id), not free text
model_profile_id FK to model_profiles, with an org-level default — so "swap the profile" is real
max_state_chars per-gate, 1–100,000, default 8,000
revision integer; every edit creates a revision, the audit record names the revision used, and uniqueness is (organization_id, key, revision) with exactly one active revision per key — the key itself is not unique
is_enabled kill switch per gate
  • Disabled or missing gate: the tool refuses with a typed error and logs it; it never falls back to a default gate.
  • Caller overrides: v1 forbids replacing gate labels. A caller may pass options only as a subset of the gate's approved labels, validated server-side.
  • Attribution is server-derived: agent, run, user and org come from the authenticated call, never from model input.

Response contract

  • Engine result → tool result mapping is explicit: Answered.answer → label; confidence validated finite and inside 0–1 (the engine defaults missing metadata to zero); label must be a member of the effective set.
  • Below threshold: the label is suppressed and the tool returns unsure plus the gate's on_unsure action. Equality with the threshold is accepted — confidence >= threshold is a decision.
  • reason is removed from v1. The native endpoints do not return one; synthesizing one from probabilities would be an invented justification. If Monitoring must show reasons later, that is a separate scoped, priced feature with its own provider capability check.
  • Malformed or missing provider metadata → unsure with status = provider_metadata_missing, never a crash.

Provisioning and access

  • Platform binding: the decide tool lives in the platform MCP toolset. A bot reaches it only if it holds a platform binding — which is independent of the ClickUp work and must be migrated per pilot bot explicitly. Seventeen bots currently have no platform binding at all.
  • Not in PLATFORM_UNGATED_TOOLS: that set is an approval exception, not an access gate. Access is the binding plus agents:run.
  • Approval: a paid label call is annotated writes: true so an org that gates writes parks it. Whether that is wanted for a one-second decision is D4.
  • Public / embed / anonymous: denied server-side and tested directly (AC9). A public-origin workflow with a principal is a case to settle, not to assume.
  • Rate limits and budget: per-bot and per-org caps on decisions per run and per hour, enforced before dispatch.

Decision log

decision_log, with the fields the acceptance criteria actually need:

id, organization_id, gate_key, gate_revision, agent_id, run_id, conversation_id, user_id, caller_kind, workflow_run_id (nullable), workflow_node_run_id (nullable), effective_options (jsonb), attempt_count, idempotency_key (unique), status, decision, confidence, on_unsure, state_digest (keyed), state_excerpt (redacted, ≤500, nullable), model_profile_id (nullable), latency_ms, cost, cost_state, error_code (sanitized), created_at.

decision_attempts: id, decision_id, attempt_no, dispatched_at, status, latency_ms, cost, cost_state, error_code.

  • Status vocabulary: decided, unsure, refused, disabled, missing_gate, budget_refused, provider_error, provider_metadata_missing, timeout, cancelled, outcome_unknown. A status outside this set is a defect, not a new value. Pre-resolution refusals leave profile/confidence/cost null.
  • Idempotency: a replayed call id neither rebills nor creates a second logical row.
  • Retention: follows the org's retention defaults, with a purge job and a floor from the audit settings.
  • Access: gate authors (D5) read/write gates; only owner/admin read the log; bots never read it.
  • Migration: FKs, the unique idempotency index, and a partial index on (organization_id, gate_key, created_at) for the Monitoring queries.

Operator surface

Monitoring → Decisions: per gate and per bot — volume, unsure rate (with the denominator stated), p50 and p95 latency, spend with partial-cost flags, and status breakdown. No reasons in v1.

Acceptance criteria

Every state-changing case runs against an isolated fixture or fake provider. SELECT and source reads inspect the stored evidence; wrappers alone cannot prove external non-dispatch without instrumentation.

# Criterion
AC1 An authorized native decision profile validates and executes a fixture decision through both adapters (workflow node and tool) with typed output. Negative cases retained: a chat profile is refused, an unsupported transport is refused, a missing/unusable credential is refused.
AC2 With explicit platform bindings, FIN and SAL: the effective manifest contains decide; a call succeeds with no workflow dispatch context; the result carries source attribution; exactly one logical log row; cost booked exactly once and reconciled against the org total.
AC3 Latency benchmarked over ≥100 fixed 2,000-character cases on the named route, warm and cold, with concurrency stated: report p50/p95, timeouts and errors, with an explicit rule for including failed calls. Unverified until measured.
AC4 Canary patterns only: zero provider-dispatch events, a structured refused status, and no canary in tool args, results, approval payloads, replay, log, error or trace stores. The excerpt and digest behave as specified.
AC5 With a fixture price and headroom: an exhausted budget causes zero dispatch; failed/cancelled/timed-out attempts settle attributable fees once; concurrent attempts respect the chosen reservation or overshoot contract; the handoff is deterministic and needs no further paid chat turn; SQL reconciles the ledger.
AC6 Inject provider confidences below, equal to and above the threshold, plus missing, non-finite and out-of-range values, and an invalid label. Below → unsure + on_unsure only; equal and above → an allowed label; malformed → provider_metadata_missing.
AC7 One logical row for every outcome — decided, unsure, refused, disabled, missing gate, budget, provider error, timeout, cancel — with nullable fields null where resolution never happened. A replayed call id neither rebills nor duplicates. No raw state on any surface.
AC8 For a fixed org, gate and agent over a half-open UTC window, Monitoring counts (status-inclusive, unsure denominator stated), p50 and spend match SQL; tenant isolation and the retention purge are verified.
AC9 Public, embed and anonymous callers are denied server-side with evidence, not inferred from a set name. An external-MCP caller is denied or permitted by an explicit, tested rule.
AC10 Kill switch: disabling a gate refuses immediately with disabled; re-enabling restores service without a deploy. Rollback to the previous gate revision is exercised and the audit names the revision used.

Non-goals

  • Not a memory. Nothing is written back as a fact; the knowledge bases are the memory.
  • Does not execute business actions and does not replace approvals. It creates and updates its own gate and log rows and charges spend — so "not a write path" would be false; this is the accurate claim.
  • Not connected to Ricardo's personal gate. Reaching :8792, or any personal fleet endpoint, is a defect.

Failure Detection Response

Self-hosted route C underperforms side-by-side on one gate for a week keep both profiles, switch by FK, no code change

Security, permissions, audit

  • Server-derived attribution only; no identity accepted from model input.
  • Redaction before dispatch and before persistence; keyed digests, not plain hashes.
  • The log records who asked (org/agent/run/user), the gate revision, the label and the cost — never the raw text, and no reasons in v1.
  • Spend settles through the existing aggregation so the lane cannot hide vendor cost.

Build order

  1. DecisionPort seam — a provider-neutral interface in front of the lane. No vendor, no spend, and it is the same work whichever route wins.
  2. Volume × quote — measure expected decision volume from the two pilot bots, obtain a Jev quote with a price cap, and compare against the fully-loaded cost of self-hosting. This number decides whether step 3 is funded at all.
  3. Route D profile — done: clef:cloud on the existing company key, profile 736b771a. Rate limits and a per-bot budget cap are the only remaining configuration.
  4. Slice 1 — shared service extraction, workflow nodes converted to adapters, regression tests proving unchanged workflow routing, errors and cost.
  5. Slice 2 — redaction component + canary tests across every store.
  6. Slice 3 — decision_gates migration, revisions, admin CRUD, org default profile, the five company gates.
  7. Slice 4 — decide tool on top of the service, platform binding, rate limits, public denial.
  8. Slice 5 — decision_log + decision_attempts + Monitoring → Decisions.
  9. Pilot: routing and triage on FIN and SAL for two weeks before any other gate.
  10. Route C or A, only if clef disappoints — a DecisionPort adapter swap, not a rebuild. Exit gates for any self-hosted option: quality on a golden set, p95 latency under load, TLS/auth, patch, backup/restore, load-shedding survival, a named operator and deputy, and a security review. A demo on idle office hardware is not production evidence.
