Decision lane — a native bounded-decision tool for every AgenticOS bot

Why this PRD

Ricardo's §8 gates run on his own Mac, at 127.0.0.1:8792, for his own agents. That is personal infrastructure and it stays personal. What Infinity Brands needs is the same capability inside the work platform, available to all thirteen departmental bots and the four report bots — a cheap, typed answer to a bounded question ("is this inbound message a work request or a personal one?", "does this invoice need to go to Finance or to EXCO?") without burning a conversational model turn on it.

The platform already has most of it and nobody knows. There is a native decision lane in app/workflows/nodes/:

File Lines What it is
_decide.py 326 Shared engine: profile resolution, typed question, confidence floor, unsure path, budget guard
decide_yes_no/_handler.py 54 Yes/no with an unsure port
decide_choose/_handler.py 94 One of a short list
decide_score/_handler.py 70 A rubric score

Its own docstring: "Typed decision steps using a native decision model profile … Below min_confidence the step follows its unsure port rather than treating uncertainty as a provider failure."

So the capability exists — but only inside a workflow. A bot cannot call it mid-conversation, there is no org-level definition of what a gate is, and nothing is logged in a place an operator can read. This PRD closes those three gaps.

Product in five lines

  1. One native tool — decide — that any published bot can call inside a turn.
  2. Five gates defined once for the organization, with thresholds and an escalation target.
  3. The answer is a label plus a confidence plus a one-line reason, in about a second.
  4. Below the threshold the answer is unsure and the caller escalates — never a guess dressed as a decision.
  5. Every decision is logged (gate, bot, label, latency, spend) so the lane can be measured and tuned.

The one hard constraint: a decision model is not a chat model

is_decision_api (app/agents/model_resolver.py:627) refuses a conversational endpoint for decision work, and the model-profile resolver does the same (_decide.py:172 — "Select a native decision API profile"). Ollama is a chat provider. The company Ollama key cannot serve this lane, and no amount of configuration changes that.

Three routes, and this is the money decision in this PRD:

Route What it costs State today
A. TypeSafe Jev — the vendor this platform's lane was built around per-call vendor spend; a key we do not hold catalogue-ready, no credential
B. OpenAI gpt-6-luna decisions / Google gemini-decision-1 per-call vendor spend on a vendor account catalogue-ready, no credential. Google is a poor fit — we do not use Google for work
C. Self-hosted SystemOne-compatible endpoint on office hardware hardware we already own; no vendor unverified — the resolver accepts provider system-one with a base_url, but the catalog does not list it. Needs a one-day spike before it can be promised

Recommendation: spike C first, fall back to A. C keeps the company's decision traffic on company hardware and matches the "no new vendor" instinct; A is the shortest path to a working lane and can be swapped out later because the profile indirection already exists.

Design

1. Gate registry — a table, not code per bot

New table decision_gates, org-scoped:

Column Purpose
organization_id, key unique per org — money_legal, memory, escalation, routing, triage
title, question the question asked of the model, phrased as a person would ask it
options jsonb list, 2–8 labels
threshold confidence below which the answer is unsure
on_unsure what the caller must do (escalate, refuse, ask_human)
escalate_to free text: who receives it when unsure
max_state_chars per-gate cap, default 8,000
is_enabled kill switch per gate

Seeded with the five gates as Infinity Brands' gates, with thresholds set by this organization. The platform's copy is not a mirror of Ricardo's personal lane; it is the company's own instrument.

2. The tool — decide

Registered in the platform MCP toolset beside the other platform tools, not in PLATFORM_UNGATED_TOOLS — it spends money, so it is reachable only by an agent that holds the tool.

Input

{
  "gate": "routing",
  "state": "The client says the invoice is wrong and asks for a credit note before month end.",
  "options": ["finance", "exco", "sales", "none"],
  "context_label": "inbound email triage"
}

Output

{
  "decision": "finance",
  "confidence": 0.91,
  "reason": "Credit note and month-end deadline are Finance's remit.",
  "gate": "routing",
  "decision_id": "…",
  "latency_ms": 840
}
  • state is capped per gate (default 8,000 chars, engine maximum 100,000) and is redacted before it leaves the platform — secrets, tokens and card numbers are stripped, and a request that still looks like a credential is refused rather than sent.
  • options is optional; when omitted the gate's own options are used. Maximum eight labels.
  • Below threshold: decision: "unsure", on_unsure returned verbatim, no invented label.

3. Decision log

New table decision_log: id, organization_id, gate_key, agent_id, run_id, conversation_id, state_hash, state_excerpt (redacted, ≤500 chars), decision, confidence, model_profile_id, latency_ms, cost, created_at. Retention follows the org's retention_defaults. The raw state is never stored — the hash and the excerpt are what an auditor needs and all they get.

4. Operator surface

A Monitoring → Decisions page: per gate, per bot — volume, unsure rate, p50 latency, spend to date, and the top reasons. This is the page that answers "is the lane deciding well?" without reading logs.

Acceptance criteria

  1. A decision model profile exists and passes resolution: creating a workflow decision node with it validates instead of returning DECISION_MODEL_REQUIRED.
  2. A bot calls decide mid-conversation and gets a label back — no workflow involved. Evidence: the run's tool-call record names the tool and its latency.
  3. Latency p50 under 2 s for a 2,000-character state on the chosen route.
  4. A state containing a credential-shaped string is refused, and the refusal is logged as refused, not sent to the provider.
  5. A decision that would exceed the org budget is refused with the budget error, and the run continues — the bot degrades to asking a human.
  6. A nonsense question scores below threshold and returns unsure with the gate's on_unsure text.
  7. decision_log has one row per call with a null-free state_hash and no raw state.
  8. The Monitoring page shows the same counts as a direct SQL query for the same window.

Non-goals

  • Not a memory. The lane retains nothing beyond the log excerpt; the 22 knowledge bases are the memory. No decision is written back as a fact.
  • Not a write path. It returns a label. It never mutates Zoho, ClickUp or the platform.
  • Not an approval system. Human approval for tool writes is a separate, existing mechanism.
  • Not connected to Ricardo's personal gate. The :8792 endpoint on his Mac mini is out of scope by design, and this PRD treats reaching it as a defect.

Failure modes

Failure Detection Response
Decision endpoint down tool error, provider non-200 bot falls back to on_unsure; no retry storm (single attempt, logged)
Vendor key expires 401 on every call alert on the gate's error rate; profile swap is one field
Confidence drift — everything comes back unsure unsure rate on the Monitoring page re-tune threshold or question; the page exists for this
A bot sends health or identity data in state redaction refuses, logged that is the guard working; review the bot's instructions
Self-hosted route C performs worse than the vendor side-by-side on the same gate for a week keep both profiles, switch the gate, no code change

Security, permissions, audit

  • Gated on agents:run; the tool is not ungated and cannot be reached by a public embed.
  • Inputs are redacted before leaving the platform; secrets never enter the state (app/core/sanitize.py).
  • The decision log records who asked, which gate and what label — never the raw text.
  • Spend is charged through the existing SpendLedger / BudgetGuard, so a decision lane cannot hide vendor cost from the org's budget.

Build order

  1. Spike route C (self-hosted SystemOne-compatible endpoint) — one day, on office hardware, no vendor. Outcome: verified or dropped. Gate: Ricardo, if it fails.
  2. Credential — whichever route survives step 1. Gate: Ricardo — money/legal.
  3. Gate registry table, migration, the five gates seeded, admin CRUD.
  4. decide platform tool on top of _decide.py — reuse the engine, do not fork it.
  5. decision_log + redaction + budget charge.
  6. Monitoring → Decisions page.
  7. Pilot: routing and triage on the FIN and SAL bots for two weeks before any other gate.
