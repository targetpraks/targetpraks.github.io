2. Home Assistant — the capture works, the archive write never does (23 nights)

~/.config/maio-stack/home-assistant/backup.sh docker cps /config/. into .work-<date>/ (that step is fine — tonight's dir has the 7.3 MB SQLite db, its 4.1 MB WAL and the 11 MB log), then tar -czf the result. The tar step is denied:

tar: Failed to open '/Volumes/Hiksemi 1TB/AI-Drive/backups/home-assistant/home-assistant-config-2026-11-23.tar.gz'

Two defects in that one line:

  • the path is spelled backups, not Backups. The real tree is AI-Drive/Backups. APFS resolves it case-insensitively, but TCC grants match per path string, so the removable-volume grant held for Backups does not cover backups.
  • the job has no TCC wrapper. com.maio.backup runs through the osascript shim (~/.config/maio-stack/launchers/backup.sh → /usr/bin/osascript) precisely because a bare launchd zsh lacks the removable-volume grant; this job runs /bin/zsh backup.sh directly.

Proof it is the launchd context and not the data — same read, ordinary shell, just now:

cd .work-2026-11-23 && tar -czf /dev/null -C . .   →  exit 0, 0.686 s

backup.log holds 23 Failed to open lines, oldest 2026-10-30, and zero backup ok lines. There are 23 stacked .work-* dirs (218 MB) because set -e aborts before the rm -rf "$WORK" cleanup. The house config — integrations, auth, automations — still has no snapshot at all; it exists only inside the Colima VM.

3. Firefly III — a valid gzip of nothing, 15th night, reported as success

~/AI Hub/firefly/backup.sh line 11 (unchanged since the last report):

if ! docker exec firefly-db sh -c 'mariadb-dump … firefly' 2>/dev/null | gzip -6 > "$TMP"; then …

The plist gives the job PATH=/usr/bin:/bin:/usr/sbin:/sbin and docker is at /opt/homebrew/bin/docker:

env -i PATH=/usr/bin:/bin:/usr/sbin:/sbin bash -c 'command -v docker'
→ DOCKER_NOT_IN_LAUNCHD_PATH

docker exec therefore fails, its stderr is discarded, gzip compresses the empty stream into a well-formed 20-byte archive, and without pipefail the pipeline status is gzip's zero. The one guard in the script, gzip -t, passes on an empty gzip. Result: firefly-2026-11-23.sql.gz is 20 bytes and decompresses to 0 bytes, while the job logs a cheerful 4.0K -> … line and launchd exits 0.

The source is healthy — firefly-db up (healthy), 81 tables in schema firefly. Last real dump: firefly-2026-11-08.sql.gz (2,282,073 bytes). Every file from 2026-11-09 to 2026-11-23 is 20 bytes. These sit on the boot disk, not the Hiksemi drive, so they also share the 96%-full internal volume.
