Summary

The Zoho MCP console today holds 22 servers. Twenty of them answer, and between them they carry 5,566 tool slots holding only 4,152 distinct tools — 1,414 slots, a quarter of the fleet, are duplicates. Worse, they are not organised by application: the server named zoho-calendar contains Calendar, Show, Notebook, Survey, Forms, Assist, Meeting, Webinar, Lens, Bookings and Social, and zero tools that exist nowhere else. The server named zoho-sign is 90% other apps' tools.

That is what a fill-to-the-cap build looks like. Eleven servers sit at exactly 285 tools, which is not a fact about Zoho's apps — it is the point where an automated fill stopped. So nobody currently knows how many actions Zoho People actually has, or whether Cliq is complete.

This PRD replaces the fleet with a designed one: one application per server, no mixing, shards numbered when the app needs more than one, and a coverage ledger that names the server for every single tool. Sharding is not optional — Zoho Inventory alone measured 394 distinct tools across the two servers that carry it, which proves a single app can exceed one server.

The one-line version

We are not adding servers. We are building a manifest that proves every Zoho action in the org lives on exactly one server, and that nothing else is exposed.

Four failures, in order of damage.

Fail 1 — the servers are not per-application. zoho-calendar carries twelve different apps and no unique tool. zoho-sign carries thirteen apps; only 29 of its 285 tools are actually Zoho Sign. An agent asking for "signing" lands on a server that is 90% noise, and the model has to discriminate 285 tools to find the 29 that matter.

Fail 2 — a quarter of the fleet is duplicated. The same tool sits on two or more servers 1,414 times. Two servers with different names can return different tool lists for the same call, so a "fix" applied to one looks broken from the other.

Fail 3 — nothing is complete. Eleven servers stop dead at 285. Across eleven different apps that is not a coincidence of catalogue sizes; it is a fill ceiling. Which means zoho-people at 285 is a slice of People, not People. You told me People has more than 300 tools — the fleet has no way to confirm or refute that today.

Fail 4 — one app demonstrably needs two servers already. Zoho Inventory measures 394 distinct tools across zoho-inventory and zoho-procurement. The 300 cap is real and it bites. The console states it plainly: "Only 300 native actions can be configured per MCP server."

And underneath all of it: the MetaMCP layer that fans these servers out to the agents is crash-looping right now — password authentication failed for user "metamcp_user". Nothing reaches a profile namespace until that is repaired.

3. Target architecture

Rule 1 — one application per server. A server carries its own app's tools and nothing else. Name matches the app: zoho-people, zoho-books.

Rule 2 — shard by function, never by alphabet. When an app exceeds 300 tools it gets -2, -3. The split is by functional cluster so that a task's tools travel together: for People, shard one carries core HR (employees, departments, designations, org structure) and shard two carries time and talent (attendance, leave, shifts, recruitment, performance, benefits). An alphabetical split puts getEmployee and updateEmployee on different servers — that is how a rebuild fails in a month.

Rule 3 — an app's shard count comes from its measured catalogue, ceil(tools / 300), then adjusted by hand so no shard is at 299 with a cluster split across the line.

Rule 4 — the coverage ledger is the product. A generated zoho-mcp-manifest.json maps every tool name to exactly one server, with the build timestamp and a hash. It is how we prove no duplicates and no gaps, and how a future agent finds a tool without guessing a shard. Regenerating it is a cheap daily check.

Rule 5 — auth via Connection, not per-user consent. Authorization on Demand means every user consents per app, and each re-consent burns one of the twenty refresh tokens a client may hold per user. Authorization via Connection shares the Super Admin's grant, and the documented position is that there is no threshold on how many MCP servers may be created.

Rule 6 — read by default, write by allowlist. Attaching a server to a MetaMCP namespace activates every tool on it, including delete, send, share and sign. Every namespace gets a lockdown pass after attach; write tools are enabled per role, deliberately, by name.

4. Build stages and exit tests

No calendar. Each stage ends on a boolean, and the next door does not open until it is true.

Stage Work Exit condition (boolean)
0 · Repair Fix the MetaMCP Postgres auth mismatch; bring the container up; confirm the stack stays up metamcp container Up without restarts for 10 minutes and a tools/list through metamcp/batman/mcp returns 200
1 · Discover Logged-in console session; enumerate every app in the plan and every tool in each, into catalogue.json Every in-scope app has a count > 0, the file is saved, and each count is read from the console — not inferred
2 · Plan Compute shards from the catalogue with the functional-cluster rule; generate names; you approve count and names Plan covers every catalogue tool exactly once; you have said go
3 · Build Create each server, add its tools, set auth via Connection, complete consent, record its URL For every server: tools/list count equals its plan count and one real tools/call succeeds
4 · Prove Regenerate the manifest from the live endpoints and diff it against the catalogue Zero tools on two servers; union equals catalogue; both diffs empty
5 · Wire Attach servers to namespaces, lockdown each, set write allowlists per role Each profile's namespace exposes exactly its expected read set, and a blocked write returns an error rather than succeeding
6 · Retire Point every config at the new URLs; disable the 22 legacy servers No config or skill references a legacy URL; you have signed the disable list
7 · Handover Skill update, secrets registry, runbook, manifest check as a cron job A fresh agent can find any tool from the manifest alone, with no console access

Stage 0 is deliberately first and cheap: while MetaMCP is down, every downstream proof is unobservable.

5. Verification — what proof looks like

Four checks, all of them mechanical, all of them run before I say a stage is done.

  1. Count match. For each server, tools/list length equals the shard's planned length. A short server is a failed build, not a rounding error.
  2. A real call per shard. The console showing "Authorized" is not proof — the fleet already learned that lesson: a green server can fail every call. One genuine tools/call per shard, with the response recorded.
  3. Manifest diff. Union of all servers equals the catalogue, with no overlap. Two empty diffs, or the build is not finished.
  4. Namespace audit. Per profile: count the tools the namespace actually exposes, and confirm the write set is empty except where a role was granted one by name.

6. Risks, and the answer to each

Risk What it does Answer
Consent rate limiting Console refuses consent for 15–25 minutes after a burst Pace the build; batch consent, then verify in a pause
20 refresh tokens per client per user Re-consenting rotates grants and can invalidate a live server Authorization via Connection, Super Admin grant shared once
URL rotates on auth switch Any stored URL silently starts returning Invalid API Key Write the new URL into the ledger the moment it rotates; never hand-copy
Stale grant Server reads "via Connection" and still refuses calls Toggle via Connection → On Demand → via Connection to force a fresh grant
Write tools auto-activate Attaching a server exposes delete / send / sign / share Lockdown pass on every attach; write allowlist by name, per role
Plan gating Some suites cannot be granted at all — Zoho Verticals failed outright Record as out of scope with the console's own error, do not fight it
300-tool cap An app's catalogue can exceed one server Shard by function; the cap is designed around, not worked around
Legacy cutover Old and new fleets answering at once confuses agents Retire only after Stage 4 passes; disabling is your signature, not mine

7. What I need from you

Five decisions. Four have a recommendation; I need a yes or a change.

  1. Scope. All apps in the Zoho One plan, discovered in Stage 1 — or business-critical first? Recommendation: all, in dependency order, because a partial fleet means a second cutover later.
  2. Write access. Read-only namespaces by default, with write tools granted per role by name — or no write tools at all in this rebuild? Recommendation: default read-only, plus an explicit allowlist for the seats that already write today.
  3. Legacy servers. After Stage 4 passes, disable the 22 legacy servers (not delete). Needs your sign. Recommendation: disable, keep for 30 days of audit trail.
  4. Console session. I hit the login wall. Log into mcp.zoho.com in the browser window I have open, or tell me which profile already holds a live session, and Stage 1 starts immediately.
  5. The adjacent suites. Site24x7, MDM, Endpoint Central, Log360, Cloud Spend, Qntrl, SDP, Bigin, Catalyst — same fleet, or a separate one? Recommendation: separate fleet, same pattern; they are not Zoho One and they will triple the server count.
