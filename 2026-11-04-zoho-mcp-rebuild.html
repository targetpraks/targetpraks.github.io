Summary

The Zoho MCP console today holds 22 servers. Twenty of them answer, and between them they carry 5,566 tool slots holding only 4,152 distinct tools — 1,414 slots, a quarter of the fleet, are duplicates. Worse, they are not organised by application: the server named zoho-calendar contains Calendar, Show, Notebook, Survey, Forms, Assist, Meeting, Webinar, Lens, Bookings and Social, and zero tools that exist nowhere else. The server named zoho-sign is 90% other apps' tools.

That is what a fill-to-the-cap build looks like. Eleven servers sit at exactly 285 tools, which is not a fact about Zoho's apps — it is the point where an automated fill stopped. Until this morning nobody knew how many actions Zoho People actually has. Now the console's own API answers: 384 actions, and Cliq's 303.

This PRD replaces the fleet with a designed one: one application per server, no mixing, shards numbered when the app needs more than one, and a coverage ledger that names the server for every single tool. Sharding is not a nicety: the console's own catalogue is 14,550 actions across 69 apps, and fifteen apps exceed the 300-action cap — Zoho CRM alone needs five servers, Zoho People exactly two.

The one-line version

We are not adding servers. We are building a manifest that proves every Zoho action in the org lives on exactly one server, and that nothing else is exposed.

Four failures, in order of damage.

Fail 1 — the servers are not per-application. zoho-calendar carries twelve different apps and no unique tool. zoho-sign carries thirteen apps; only 29 of its 285 tools are actually Zoho Sign. An agent asking for "signing" lands on a server that is 90% noise, and the model has to discriminate 285 tools to find the 29 that matter.

Fail 2 — a quarter of the fleet is duplicated. The same tool sits on two or more servers 1,414 times. Two servers with different names can return different tool lists for the same call, so a "fix" applied to one looks broken from the other.

Fail 3 — nothing is complete. Eleven servers stop dead at 285. Across eleven different apps that is not a coincidence of catalogue sizes; it is a fill ceiling. Which means zoho-people at 285 is a slice of People, not People. You told me People has more than 300 tools — the fleet has no way to confirm or refute that today.

Fail 4 — one app demonstrably needs two servers already. Zoho Inventory measures 394 distinct tools across zoho-inventory and zoho-procurement. The 300 cap is real and it bites. The console states it plainly: "Only 300 native actions can be configured per MCP server."

And underneath all of it: the MetaMCP layer that fans these servers out to the agents was crash-looping — password authentication failed for user "metamcp_user". Nothing reached a profile namespace while it was down.

Status: repaired 2026-11-04, 08:12. The container is healthy and the batman namespace answers with 1,045 tools, 593 of them Zoho — so Stage 0's exit condition is met before the build starts.

3. Target architecture

Rule 1 — one application per server. A server carries its own app's tools and nothing else. Name matches the app: zoho-people, zoho-books.

Rule 2 — shard by function, never by alphabet. When an app exceeds 300 tools it gets -2, -3. The split follows the console's own functional groups and a group is never divided between two servers. People lands at 192 + 192: attendance, compensation and engagement on one, employees, approvals and benefits on the other. An alphabetical split would put getEmployee and updateEmployee on different servers, which is how a rebuild fails a month later.

Rule 2b — the number is not a hierarchy. zoho-people-2 is not the lesser server; it is the other half of one app. Nothing in a suffix tells an agent what lives there — which is precisely why the manifest exists, and why an agent resolves a tool through the manifest instead of guessing.

Rule 3 — an app's shard count comes from its measured catalogue, ceil(tools / 300), then packed by functional group with balanced fill, so no shard is a 297-tool slab beside a 3-tool orphan.

Rule 4 — the coverage ledger is the product. A generated zoho-mcp-manifest.json maps every tool name to exactly one server, with the build timestamp and a hash. It is how we prove no duplicates and no gaps, and how a future agent finds a tool without guessing a shard. Regenerating it is a cheap daily check.

Rule 5 — every server is authorized via Connection, and completed, not just toggled. Authorization on Demand means every user consents per app, and each re-consent burns one of the twenty refresh tokens a client may hold per user. Authorization via Connection shares the Super Admin's grant, and there is no documented threshold on how many servers may be created. Per server, in this order:

  1. Open the server → Connection in the left rail → Change beside Configure Authorization Type.
  2. Select Authorization via Connection and save. The section now reads Enabled.
  3. The Authorized Tools table appears with Native Connection · Authorized By – · Service Name – · Status Not yet connected in red. This is the trap: the toggle is on and the server is still unusable.
  4. Complete that connection until the row reports connected and the authorizer is named. tools/list answers without it; every tools/call fails.
  5. Only then copy the URL from Connect — it rotates when auth changes, so it is written into the ledger at the moment it is read, never hand-carried.

A server that fails step 4 is not built, whatever the Tools tab says. This is the same class of failure as the September fleet's "Authorized" lie, one layer deeper.

Rule 6 — read by default, write by allowlist. Attaching a server to a MetaMCP namespace activates every tool on it, including delete, send, share and sign. Every namespace gets a lockdown pass after attach; write tools are enabled per role, deliberately, by name.

Rule 7 — every client gets the same recipe, recorded once. The console's Connect tab is the single source for how a client attaches: the server URL, transport HTTP / Streamable HTTP, and the JSON block

{ "mcpServers": { "ZohoMCP": { "command": "npx",
  "args": ["mcp-remote", "https://<server>-<client-id>.zohomcp.com/mcp/<api-key>/message",
           "--transport", "http-only"] } } }

Claude, Cursor, Devin Desktop and VS Code each have a tab there; anything else uses the same URL with transport HTTP. The URL is a password — it triggers tools against the org — so it never goes into a note, a ticket, chat, git or this PRD. The registry is ~/.config/maio-stack/secrets.env (ZOHO_MCP_<PRODUCT>_URL), and the Apple note Zoho MCP — client connection details holds the recipe with the key masked. Regenerate API Key invalidates every client holding the old URL, so regeneration is a fleet event, not a per-server convenience.

4. Build stages and exit tests

No calendar. Each stage ends on a boolean, and the next door does not open until it is true.

Stage Work Exit condition (boolean)
0 · Repair Fix the MetaMCP Postgres auth mismatch; bring the container up; confirm the stack stays up metamcp container Up without restarts for 10 minutes and a tools/list through metamcp/batman/mcp returns 200
1 · Discover Logged-in console session; enumerate every app in the plan and every tool in each, into catalogue.json MET 2026-11-04 — 69 apps, 14,550 actions, every count read from the console API
2 · Plan Compute shards from the catalogue with the functional-cluster rule; generate names; you approve count and names BUILT, awaiting your go — shard_plan.json covers 14,550 actions exactly once across 95 servers, no shard over 300
3 · Build Create each server, add its tools, set Authorization via Connection, complete the Native Connection (not just the toggle), copy its URL from Connect For every server: the Connection row reads connected with an authorizer named, tools/list count equals its plan count, and one real tools/call succeeds
4 · Prove Regenerate the manifest from the live endpoints and diff it against the catalogue Zero tools on two servers; union equals catalogue; both diffs empty
5 · Wire Attach servers to namespaces, lockdown each, set write allowlists per role Each profile's namespace exposes exactly its expected read set, and a blocked write returns an error rather than succeeding
6 · Retire Point every config at the new URLs; disable the 22 legacy servers No config or skill references a legacy URL; you have signed the disable list
7 · Handover Skill update, secrets registry, runbook, manifest check as a cron job A fresh agent can find any tool from the manifest alone, with no console access

Stage 0 is deliberately first and cheap: while MetaMCP is down, every downstream proof is unobservable.

5. Verification — what proof looks like

Four checks, all of them mechanical, all of them run before I say a stage is done.

  1. Count match. For each server, tools/list length equals the shard's planned length. A short server is a failed build, not a rounding error.
  2. A real call per shard. The console showing "Authorized" is not proof — the fleet already learned that lesson: a green server can fail every call. One genuine tools/call per shard, with the response recorded.
  3. Manifest diff. Union of all servers equals the catalogue, with no overlap. Two empty diffs, or the build is not finished.
  4. Connection audit. Per server, the Authorized Tools row reads connected with an authorizer named. Authorization via Connection switched to Enabled while the row still says Not yet connected is the fleet's most expensive silent failure: tools/list passes, every real call fails.
  5. Namespace audit. Per profile: count the tools the namespace actually exposes, and confirm the write set is empty except where a role was granted one by name.

Risk What it does Answer
Consent rate limiting Console refuses consent for 15–25 minutes after a burst Pace the build; batch consent, then verify in a pause
Toggle on, connection not made Authorization via Connection reads Enabled while the row says Not yet connected; every call fails and the Tools tab still looks healthy Complete the Native Connection per server and audit the row; a server with a red row is unbuilt
Client URL treated as documentation The server URL carries the API key; pasting it into a note, ticket or repo hands over the org's tools Note holds the recipe with the key masked; the value lives only in secrets.env
Key regeneration Regenerate API Key silently breaks every attached client Treat as a fleet event: rotate, then rewrite every registry entry and re-verify one call per server
20 refresh tokens per client per user Re-consenting rotates grants and can invalidate a live server Authorization via Connection, Super Admin grant shared once
URL rotates on auth switch Any stored URL silently starts returning Invalid API Key Write the new URL into the ledger the moment it rotates; never hand-copy
Stale grant Server reads "via Connection" and still refuses calls Toggle via Connection → On Demand → via Connection to force a fresh grant
Write tools auto-activate Attaching a server exposes delete / send / sign / share Lockdown pass on every attach; write allowlist by name, per role

7. What I need from you

Five decisions. The fourth is now closed; four remain, each with a recommendation.

  1. Scope. Core Zoho only (50 apps, 69 servers) or everything in the console (69 apps, 95 servers)? Recommendation: build the 69 core servers first, 26 adjacent servers in a second wave once the pattern is proven on real apps.
  2. Write access. Read-only namespaces by default, with write tools granted per role by name — or no write tools at all in this rebuild? Recommendation: default read-only, plus an explicit allowlist for the seats that already write today.
  3. Legacy servers. After Stage 4 passes, disable the 22 legacy servers (not delete). Needs your sign. Recommendation: disable, keep for 30 days of audit trail.
  4. Console session. Done — you logged in, and I read the console's own API from that session. Keep that Chrome window open until the build ends; it is the live grant.
  5. The adjacent suites. 19 apps, 3,938 actions, 26 servers — Site24x7, MDM, Endpoint Central, Log360, Cloud Spend, Qntrl, SDP, Bigin, Catalyst, Vaniby, Solopreneur, Verticals, TrainerCentral, Analytics Plus, Zia, SaaSMP. Same fleet, or a second wave? Recommendation: second wave, same pattern — they are not Zoho One, and they add 26 servers to the 69.
