MAIO-2 — Health probe for Multica in Maio OS

Issue: MAIO-2 · Health probe for Multica in Maio OS (project AI Stack) Step: Spec → Build · Author: Adrianna A · Date: 2026-11-23 Target repo: targetpraks/maio-os (clone /Volumes/Hiksemi 1TB/DevMini/maio-os, app files at repo root)

1. Problem

Maio OS System ▸ Stack is the surface Ricardo uses to answer "is everything up?". It already carries the local stack (snapshot probes), legacy dev hosts, the machine snapshot and the gated service-control card — but Multica, the platform this workspace runs on, is invisible there. When the Multica backend, its web app or the local daemon stops, nothing on the cockpit says so; the only way to find out is to run multica daemon status in a terminal or notice tasks quietly stop being picked up.

The issue asks for a Multica row in System ▸ Stack covering three things: backend /healthz, web /, daemon status — with live state, and red when down.

2. What is actually there (verified 2026-11-23, 07:20 SAST)

All three probes were exercised for real before this spec was written:

Probe Endpoint Verified answer
Backend health http://localhost:8080/healthz 200 · {"status":"ok","checks":{"db":"ok","migrations":"ok"}}
Web app http://localhost:3000/ 200 · text/html · 403,496 bytes (Next.js shell)
Local daemon http://127.0.0.1:19514/health 200 · {"status":"running","pid":9747,"uptime":"11m27s","running_task_count":3,…}

Facts that shape the design:

  • Both 8080 and 3000 are SSH port-forwards, not local servers. lsof -nP -iTCP:8080 -sTCP:LISTEN and the same for 3000 both name ssh (PID 10959). A dead tunnel therefore looks exactly like a dead backend — the card must say "not answering", it must not guess which half failed.
  • The daemon is local and self-reports its port: ~/.multica/daemon.port = {"port":19514,"pid":9747}. The port moves between daemon restarts, so it is read, never hardcoded.
  • The URLs are configuration, not constants: ~/.multica/config.json holds server_url, app_url, workspace_id — and the API token (mul_…). The token must never be read into the payload, the fix log or data.js.
  • multica daemon status --output json is the CLI equivalent of the daemon probe; it is the fallback when daemon.port is missing or stale.
  • Maio OS's Stack section draws snapshot rows from DATA.stack (generator, 4× daily) and its live service card from /local.js. A snapshot row cannot satisfy "red when down" — it would be hours stale. This is a companion (live) collector, like firefly.

3. Scope

In scope

  1. companion/collectors.mjs — new collectMultica().
    • Reads MULTICA_CONFIG (default ~/.multica/config.json) for server_url and app_url, and ~/.multica/daemon.port for {port,pid}. Whitelists the fields it needs (JSON.parse then pick server_url/app_url); it never stringifies the whole file.
    • Three probes, run in parallel, each with its own try/catch and AbortSignal.timeout(2500) (same discipline as collectFirefly), so one dead endpoint never hides the other two:
      • backend — GET {server_url}/healthz → up when HTTP 200 and body status === "ok"; carries db and migrations sub-checks and the latency.
      • web — GET {app_url}/ → up when 2xx and an HTML content type.
      • daemon — GET http://127.0.0.1:{port}/health → up when 200 and body status === "running"; carries pid, uptime, running_task_count. If daemon.port is missing/unreadable, fall back to multica daemon status --output json; if the reported pid no longer matches the process in daemon.port, report warn with the mismatch named, never a silent green.
    • Returns { ok, generatedAt, backend, web, daemon }; ok is true only when all three are up. Every failure path returns a short, honest error string (connection refused, timeout, code, body mismatch) — never a fabricated state.
    • Registered in collectAll() as safe('multica', collectMultica) so a thrown probe cannot take the payload hostage.
    • Env overrides for QA: MULTICA_CONFIG, MULTICA_SERVER_URL, MULTICA_APP_URL, MULTICA_DAEMON_PORT (and optionally MULTICA_DAEMON_HEALTH). This is what makes the "red when down" test non-destructive.
  2. index.html — a Multica card in renderStack().
    • New multicaCard() placed with the other live cards (after stackServicesCard()).
    • Heading "Multica — workspace runtime" plus the local badge, then three rows matching the issue's wording: Backend /healthz, Web /, Daemon status.
    • Each row: name · endpoint/latency detail · a pill. Up = pill ok, down = pill bad (red), degraded = pill warn. The daemon row shows pid · uptime · N running.
    • Values match the ground truth in §2 (pid reads as 9747 when ~/.multica/daemon.pid says so).
    • Honest degradation: with no /local.js, the card renders the same "needs the local companion (127.0.0.1:9111)" note the service card uses — never a green row.
  3. VIEW_SIGS.stack (index.html ≈ line 717) gains the multica key so the section repaints when a probe changes state (today it only watches services.items); without this the row would be correct in the DOM and stale on screen.
  4. ops/deploy.sh payload install — companion/collectors.mjs is already in the payload map; no new file, so the deploy path is unchanged: ./ops/deploy.sh then ./ops/deploy.sh --check.

Out of scope (deliberate)

  • No restart/fix action for Multica (no launchctl kick, no multica daemon restart button). This is a read-only health row; two-way actions need their own guard rails and a separate go.
  • No changes to generator/maio_os_gen.py / data.js — the row is live-only by design.
  • No tailnet exposure, no auth/token work, no alerting or paging. The token is a hazard to avoid, not a feature to add.
  • No changes to Multica itself or to the SSH tunnels.

4. Acceptance criteria

  1. Shape — System ▸ Stack shows a card titled "Multica — workspace runtime" with exactly three rows: Backend /healthz, Web /, Daemon status.
  2. Live — with the stack up, all three rows are green and their values agree with the endpoints in §2 (backend 200 + db/migrations ok; web 200 HTML; daemon running, pid equal to ~/.multica/daemon.pid).
  3. Red when down — pointing any probe at a dead endpoint makes that row red within one refresh cycle (≤30 s), carrying the real error text; the page never renders green for an endpoint that did not answer.
  4. Isolation — a single dead probe does not blank the other two rows.
  5. Honest absence — served without the companion, the card says the action/probe lane is unavailable instead of showing green.
  6. No secret — the mul_… token never appears in /local.js, /api/fix/log, data.js, or any collector log line.
  7. No regression — the existing snapshot rows, legacy-hosts block, machine snapshot and service card are unchanged; node --check passes on index.html's inline script and companion/collectors.mjs; ops/deploy.sh --check reports in sync.

5. The exact test that proves it

Run from the repo (work in a worktree, never the base checkout that 9111 serves).

T1 — live payload carries all three probes

curl -s http://127.0.0.1:9111/local.js | python3 -c '
import sys, json, re
d = json.loads(re.search(r"=\s*(\{.*\});?\s*$", sys.stdin.read(), re.S).group(1))
m = d["multica"]; print(json.dumps(m, indent=1))
assert m["backend"]["ok"] is True and m["backend"].get("status") == 200
assert m["web"]["ok"] is True
assert m["daemon"]["ok"] is True
assert str(m["daemon"]["pid"]) == open("/Users/ricardomaio/.multica/daemon.pid").read().strip()
print("T1 PASS")'

Expected: T1 PASS, backend body shows db: ok, migrations: ok.

T2 — red when down, without touching the real tunnels (QA companion on 9130, every probe pointed at a dead port)

WT=/tmp/maio-os-qa-multica          # worktree path
(cd "$WT/companion" && MAIO_OS_ROOT="$WT" MULTICA_SERVER_URL=http://127.0.0.1:9 \
   MULTICA_APP_URL=http://127.0.0.1:9 MULTICA_DAEMON_PORT=9 node server.mjs --port 9130 &)
sleep 2
curl -s http://127.0.0.1:9130/local.js | python3 -c '
import sys, json, re
d = json.loads(re.search(r"=\s*(\{.*\});?\s*$", sys.stdin.read(), re.S).group(1))["multica"]
assert d["ok"] is False
assert d["backend"]["ok"] is False and d["backend"]["error"]
assert d["web"]["ok"] is False     and d["web"]["error"]
assert d["daemon"]["ok"] is False  and d["daemon"]["error"]
print("T2 PASS", d["backend"]["error"])'

Then in a browser open http://127.0.0.1:9130/?v=1#stack (fresh query — a hash-only change does not reload) and assert the three rows carry the red pill class and no green pill:

[...document.querySelectorAll('.multica-row .pill')].map(p => p.className)
// => ["pill bad","pill bad","pill bad"]

T3 — isolation — restart the 9130 QA instance with only MULTICA_DAEMON_PORT=9; expect daemon red, backend + web green. Proves the probes are independent.

T4 — no secret

curl -s http://127.0.0.1:9111/local.js | grep -c 'mul_'   # must print 0

T5 — live browser check — http://127.0.0.1:9111/?v=N#stack: three green rows whose pid/uptime match T1's payload. Read geometry/classes from the live DOM, not a headless screenshot.

6. Implementation notes for Build

  • collectFirefly in companion/collectors.mjs (~line 895) is the pattern to copy: origin constant from env, AbortSignal.timeout, honest error string, generatedAt at the end.
  • collectAll() (~line 1244) destructures results in a fixed order — add multica to the Promise.all list and to the returned object, in the same edit.
  • stackServicesCard() (~line 2361) shows the exact "needs the local companion" notebox to reuse.
  • The section is served from the base checkout's working tree while the companion runs installed copies: after editing collectors.mjs, kick com.maio.maio-os-local (it imports collectors at boot) or the row will look unchanged.
  • Keep data.js out of the diff; the refresh job owns it.
