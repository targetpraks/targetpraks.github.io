0. One-line summary

Find the ten best free computer-control / browser-agent projects on the market today, actually install and run each one on this Mac against a fixed, offline, ground-truthed task suite, and report speed + accuracy per engine on Dia vs Google Chrome vs Firefox, with reproducible evidence (raw JSON per run, not opinions).

1. Vision & problem

Ricardo wants to hand real work to a computer-control agent. The market is loud: 100k-star browser agents, "OSWorld SOTA" desktop agents, Chrome extensions, vision models. Almost every comparison online is written by a vendor about itself (Skyvern's blog ranking Skyvern first), or quotes a benchmark score from a paper that nobody re-ran on a normal Mac.

The three questions that actually decide the choice are unanswered by marketing pages:

  1. Which of these run on this machine, today, for free (no per-seat SaaS, model calls on the existing Ollama Cloud subscription)?
  2. How fast and how accurate are they on the same tasks — not on OSWorld, on ordinary work?
  3. Which browser should they drive: Dia, Chrome, Firefox? Does the answer change per engine?

The deliverable answers those with measured numbers, and states plainly what failed and why.

5. Feature list (P0 / P1) with acceptance criteria

P0-1 — Deterministic offline task suite

A local static site (127.0.0.1:8811, served by python -m http.server) with 6 browser tasks and 3 desktop tasks, each with a machine-checkable ground truth.

ID Task Ground truth (checked programmatically)
B1 Fill a 5-field signup form from given values and submit server log line / page text contains exact values
B2 Find the price of a named SKU in a 12-row table exact string "R 1 249.00"
B3 Search a list, open the 3rd result, read its order id exact id
B4 Multi-step checkout (cart → address → confirm) page shows "ORDER- CONFIRMED"
B5 Extract all 4 rows of a table into a list exact 4-tuple set
B6 Two-tab task: copy a code from tab A into a form on tab B submitted code equals generated code
D1 Open TextEdit, type a given sentence, save to a given path file exists with exact content
D2 Use Calculator for 47×19 display reads 893
D3 Close the frontmost window of a named app window count drops by 1

Acceptance: each task's checker returns PASS/FAIL with no human judgement; the suite runs end-to-end with make bench in under 20 minutes for the browser lane.

P0-2 — Adapters, one per engine

Uniform Python interface so the harness never contains engine-specific logic:

class Engine:
    name: str
    def setup(self) -> None            # idempotent: install/binary check
    def run(self, task: Task, browser: str, model: str) -> RunResult

RunResult = {task, engine, browser, ok, seconds, steps, llm_calls, tokens, error, transcript_path}

Each engine writes its raw transcript to results/raw/<engine>/<task>-<browser>.log so any claim in the report can be traced to a real log line.

P0-3 — Runner + result store

  • Runs the matrix engines × tasks × browsers, one task per subprocess with a hard timeout (default 180 s), so one hung agent never kills the suite.
  • Appends every run to results/runs.jsonl (append-only, crash-safe).
  • Prints a per-engine table (success %, median seconds, p95) and writes results/summary.json.

P0-4 — The report

Markdown + published HTML: ranking, per-engine accuracy, speed, browser verdict, install friction, licence flags, and a "failed to run, here's the error" section that is never empty if something genuinely failed.

P1-1 — Cost line

Tokens per task from each engine's own accounting where available; else n/a (never estimated).

P1-2 — Reproducibility

make all reproduces the whole table on this machine; versions pinned in requirements.txt and package.json.

Data model: Run(engine, task, browser, model, ok, seconds, steps, error) — one JSON object per line in runs.jsonl. Aggregation is done in code (Python), never by eye: counts, medians and success rates are computed, and the reported N is asserted against the number of rows.

Tool contract (this product has no screen): runner.py is the interface — python -m bench.runner --engines browser_use,midscene --browsers chrome,dia --tasks B1,B2 --model glm-5.3-flash; it prints one table and exits non-zero if any P0 checker fails to run at all. The screen we are deliberately not building: a dashboard. The report page is the reading surface; a live control panel would be a second product to maintain.

7. Non-functional requirements

  • Determinism: tasks run against localhost only; no third-party site in the scored set, so network flake cannot be mistaken for agent error.
  • Isolation: every browser run uses its own --user-data-dir under scratch/; never Ricardo's logged-in profile.
  • No secrets in results: the Ollama key is read from the environment only and never written into runs.jsonl, logs or the report.
  • Time cap: one task ≤ 180 s, hard kill; the runner records error=timeout rather than dropping the row.
  • Disk: < 5 GB added; installs are uv-isolated venvs under ~/AI Hub (rule 5), no Homebrew changes, nothing global.

8. Testing strategy

  • Suite self-test: python -m bench.selftest drives every checker to PASS with a Playwright scripted solution and to FAIL with a wrong answer — proving the ground truth is correct before any agent runs. An agent cannot beat a broken checker into a good score.
  • Gate rows: every bounded judgement (scoring weights, engine shortlist, "is this failure an environment fault or an engine fault") goes through the local decision gate and is logged to gates.csv.
  • Evidence rules: no number in the report without a JSONL row behind it; any engine that can't be made to run is reported with its exact error string.

9. Out of scope / assumptions / risks

  • Out: buying any SaaS or credits; OSWorld-scale replication (369 tasks); Windows/Linux results; training or fine-tuning any model; GUI-agent leaderboard claims re-verified.
  • Assumption: Ollama Cloud models are reachable and are the only model route (per standing rule). A vision-capable cloud model is required for screenshot engines; if none of the available models accept images, desktop engines 2/5/9/10 are reported as blocked on model, not as failures of the software.
  • Risk: several engines need a strong VLM to work at all — a weak local model will make them look bad for reasons unrelated to their code. Mitigation: run the browser lane on a text model, report the desktop lane separately, and label model-dependent results as such.
  • Risk: AGPL (Skyvern) and archived repos (UI-TARS) are recorded as adoption flags, not hidden.
