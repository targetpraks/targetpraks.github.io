01Where the product actually stands

two documents and one broken working copy

Constellation is the assessment platform Infinity Brands runs on its own people: staff sit sectioned psychometric assessments, managers read placement and team analytics, and the reports answer where a person fits, how a team is composed and what a company's shape looks like. It is in production use — at the time of the audit the database held 45 staff, 39 active, 35 assessed, 37 completed sessions and 2 in progress, across 5 admin and 38 staff accounts. This is not a demo that is being polished; it is a live system holding real people's assessment data.

The application cannot be built on, audited again, or released from an unversioned directory. Nothing else in this PRD can be judged until that is fixed.

02The gate everything else waits behind

C0 — restore the source of record

This is one requirement, it is first, and it is not engineering — it is restoration. Until a verified clone exists at a canonical path and a database dump has been restored once, every other item on this list is a claim about a file set nobody can diff.

C0

A working, verified clone at a canonical path

GATE

Re-establish the repository where the fleet expects it, at or after the audit baseline, with a clean git fsck, a named remote, and the three stage-1 branches accounted for. Convert constellation-demo from a broken worktree back into a normal checkout or delete it — a pointer to a missing git directory is worse than no checkout, because it looks like one.

Done when

  • git log -1 returns a commit at the canonical path, and git fsck --no-progress is clean
  • HEAD is the audit baseline 0c47ddfa or a documented descendant, and the difference is explained
  • git status is clean apart from named local changes
  • The stage-1 commits exist and are reachable — 1620a87 (CN-01), 695d2a7 (CN-02), e140ec0 + 9ebc844 (CN-03)
  • A dump from AI-Drive/Backups/constellation restores into a scratch database and the staff and session row counts match the audit's 45 / 37+2

03Phase 1 — containment

the six that can hurt people or erase data

These are the findings where the failure mode is irreversible: staff erased, consent bypassed, a session that cannot be revoked, a result overwritten. They ship first and they ship alone.

C1

Least privilege, and destructive paths that cannot fire by accident

P0

A01. The application's database role is a PostgreSQL superuser with create-role and create-database privileges. db:reset forces a migration reset; verify invokes it twice; seed truncates Organization, AuditLog and User with CASCADE. Split the roles: a runtime role with no DDL and no create-privileges, and a separate migration role used only by an explicit command.

Done when

  • The runtime connection cannot create a database, create a role or drop a table — demonstrated by attempting each and being refused
  • db:reset and seed refuse to run against a database whose name or host is not explicitly marked as disposable
  • No verification script resets anything; verify is read-only against its target
  • A restore from the most recent dump is performed once, timed and recorded

Evidence A01 — database role verified, destructive paths source-confirmed

C2

Consent and enabled-bank restrictions survive a save

P0

A02. Answer saves bypass the consent check and the enabled-bank restriction, so a section can be written that the subject never agreed to and that the organisation has switched off. Enforce both at the write path, not only at the read path.

Done when

  • A save against an area with no consent grant is refused with a visible reason and writes nothing
  • A save against a disabled bank is refused, including when the payload is replayed directly against the action
  • Both refusals are covered by a test that fails on the pre-fix code

Logout revokes the session, not just the cookie

P0

A03. A copied session token continues to work after the user signs out. Introduce server-side session revocation keyed to the token's identity and check it on every authenticated request.

Done when

C7

Norm transitions are atomic and resumable

P0

A07. A failed norm transition is not resumed on retry, so a cohort can sit half-normalised. Make the transition a single transaction with a recorded checkpoint, and make retry resume from that checkpoint rather than restart.

Done when

  • Nothing is applied twice on a retry

C8

Birth time and password bytes

P1

A08 and A09. Birth-time conversion depends on the server's timezone, so the same input produces different charts on different hosts — fix by converting in the subject's stated zone, always. The password policy permits inputs longer than bcrypt's 72-byte limit, so two distinct passwords can collide — enforce a byte limit and reject rather than truncate.

05Phase 3 — deployment and access

the medium findings that are cheap now and expensive later

C10

Immutable deployment identity, honest proxy redirects

P1

A10 and A11. Fresh builds emit mismatched client and server deployment identifiers, and proxy-facing signed-out redirects point at localhost. Expose one build identity that both sides share, and derive redirect origins from the request's forwarded headers.

Done when

  • A build from scratch reports one identifier on the client and the server
  • Signing out behind the reverse proxy lands on the public host, never on localhost
  • The deployed SHA is readable from the running service — today it is not

Evidence A10 and A11 — both reproduced

C11

Named reflective access, one policy

P1

A12 and A19. Named reflective access differs across report surfaces, and the company's reflective-off switch is not enforced by the detailed reading path — so switching it off does not switch it off everywhere. Put both behind one policy function and call it from every read path.

Done when

  • With the company switch off, the detailed reading path refuses exactly as the summary path does
  • One table lists every report surface and the audience it resolves to; no surface is unaccounted for
  • A fixture with a manager and a staff viewer proves both answers

C12

No secrets in logs, and throttling that holds

P1

A13 and A14. Platform bootstrap logs a password-setting bearer link, and authentication throttling has timing, concurrency and configuration gaps. Redact the link at source, and move throttling to a store that is atomic across concurrent requests and configurable per environment.

Done when

  • A bootstrap run writes no usable credential to any log, file or console
  • Parallel sign-in attempts against one account are counted atomically — no bypass under concurrency
  • Throttle thresholds are configurable and the default is stated in the README

06Phase 4 — the twelve changes already agreed

the brief's stages 2 to 4, unchanged

The change brief stands as written; this PRD does not re-derive it. Stage 1 is built and verified on branches: CN-01 all-departments switcher (1620a87), CN-02 constellation map axes (695d2a7), CN-03 company-wide placement (e140ec0, 9ebc844). What remains is stages 2 to 4, and one number explains most of what Ricardo has been seeing.

The threshold, not the app

The privacy rule is MIN_GROUP = 5 — one pure module, ten call sites, one pinned sentence, asserted in e2e/privacy.spec.ts and e2e/hr-tools.spec.ts. The demo seats 24 people across six departments of four, so every department sits below the line and nearly every screen suppresses. That is one threshold meeting one fixture. Re-seeding the demo to departments of six (D-07) shows the reports working with the rule untouched — and is the cheapest honest way to know whether the rule is actually the problem.

The export side channel is not on the list and belongs in the release

lib/hr/export.ts, app/insights/export/staff/route.ts and app/insights/export/placement/route.ts carry no suppression logic at all, and the first emits one named row per person. Anyone with export rights already reads what ten screens withhold — so a release that debates the size rule while leaving the exports open has fixed the appearance and not the thing. This PRD requires the exports to obey the same policy as the screens.

07The release gate

pass or fail, on evidence

v1.1 is not 'all findings closed'. It is a release that can be shown to be safe on a defined surface. The gate below is the whole of the acceptance criteria.

  1. Every P0 requirement is closed with a test that fails on the pre-fix code. Not a passing test — a test that was red before the change.
  2. The audit is re-run against the release commit by the same harness, and reports zero critical-impact and zero high findings open. Mediums may be open only with a named owner and a date.
  3. The end-to-end suites run in fixtures, not on live data — the one-person team, the three-person and five-person departments as a boundary pair, a no-grant and a partial-grant staff member, a complete and a partial round, and a manager scoped to one department against a second department with visibly different data.
  4. A restore drill has been performed from a dated dump and recorded with its duration and row counts.
  5. One real staff member completes an assessment end to end on the release build in staging, with consent granted normally, and their report opens.
  6. The privacy rule is either unchanged and demonstrated working on a fixture above the line, or changed and the change is written down with its date.

What the gate deliberately does not certify

It is not legal-compliance certification, not a penetration test, not an accessibility conformance audit, and not proof of tenant isolation — the live dataset at audit time had one organisation and no manager or superadmin account, so multi-tenant behaviour remains unexercised. Those limits were true of the audit and they stay true of this release.

08Seven decisions only Ricardo can take

carried forward from 17 October, still open

These were open when the brief was written and no evidence has been found that any was answered. They are not blocked on engineering and they are not mine to guess — two of them decide what the privacy rule means, and one decides whether the rule is the problem at all.

#DecisionRecommendation
D-01Who may see that a named person has not granted consent — the manager who benefits from the grant, or admin only?Admin only. A visible 'has not granted' flag turns consent into something given under observation, and the grant stops being free.
D-02Does removing the size rule apply to staff-facing screens too, or only managers and admins?Managers and admins only. Staff-facing suppression protects the individual; manager-facing suppression only blinds the manager.
D-03May a manager choose a company-wide placement or team view, or is that admin-only?Manager, scoped to the departments they can already see — CN-01 already established that pattern and the visibility check stays.
D-04Are the two constellation-map axes the metrics you expect, and who signs off the plain-language wording for the esoteric figures?Needs a content owner, not a decision. Name one person; wording reviewed by that person before CN-02 ships.
D-05Does 'completed part of the tests' mean any section submitted, or a threshold share?Any section submitted, labelled with the count — it is a progress signal, not a verdict.
D-06Which surface is the full individual report — /reports/individual/&lt;id&gt; or /people/&lt;id&gt;/report — and does the other stay light?/reports/individual is the full reading; /people/&lt;id&gt;/report stays light by design.
D-07Do we fix the demo data instead of the rule?Yes, and first. Departments of six. It costs one seed change and it tells you whether the rule was ever the problem.

09Non-goals and risks

what this release does not do

  • No new features beyond CN-01 … CN-12. The brief is the scope; an audit closure is not an opportunity for a redesign.
  • No live profile application. v3 acceptance must complete and be approved separately before any profile set is applied to real staff.
  • No change to the privacy floor without D-01 and D-02. The rule moves once, in one release, with its sentence, its README and both suites.
  • No new integrations. Campaigns and the performance loop exist; no outbound provider is configured in this release.
  • No rebuild. The application inventory (43 page templates, 10 route handlers, 23 action modules) is not being re-architected.
