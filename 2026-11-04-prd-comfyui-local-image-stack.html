PRD — ComfyUI Local Image Stack (Maio fleet)

Version: 1.1 · Date: 2026-11-04 · Owner: Adrianna A (AI-stack family) · Approver: Ricardo (money, legal, external publication) Status: P0 delivered and verified on this Mac, including the cloud lane; P1 gated.

1. Vision and problem

Ricardo's words: "comfy ui, please make sure it installed locally, full detailed plans and workflows and templates. I want it to be installed and working with hermes and deepseek harness and omp."

Today this Mac can analyse and write, but it cannot make a picture. Every agent in the fleet — Hermes, the DeepSeek Harness, omp — has to reach a cloud image service (per-image cost, content leaving the machine) or come back empty. Brand and marketing work (campaign stills, social assets, concept frames, mock-up backgrounds) stalls at "we need an image".

Goal: one local image engine on this Mac, reachable as ordinary tools from all three harnesses, with templates that behave the same everywhere, and no per-image cost.

Success in one line: any of the three harnesses can be asked for an image in plain English and returns a real PNG path on AI-Drive in under 20 seconds (SD1.5) without a human touching a UI.

2. Users and jobs-to-be-done

User Job Success looks like
Ricardo (operator) "Make me a concept image / social asset" from Discord or a terminal image on AI-Drive within a minute, no UI fiddling

Non-user: nobody external. The server is loopback-only.

4. Application structure

Architecture at a glance

Harness layer      Hermes Agent      dsh (7 profiles)      omp
                        │                  │                 │
                        └──────── stdio JSON-RPC ────────────┘
                                         │
Tool layer         ~/AI Hub/comfyui-ops/comfy_mcp.py  (stdlib, 10 tools)
                        │  reads templates, stages inputs, polls history
Template layer     workflows/{sd15,sdxl}_txt2img.json
                            sd15_img2img.json · upscale_4x.json
                                         │
Engine             ComfyUI 0.44.0 @ 127.0.0.1:8188  (POST /prompt, GET /history, /view)
                                         │
Model layer        ~/AI Hub/models (canonical)  ← extra_model_paths.yaml → cold store on SSD
                                         │
Output             /Volumes/Hiksemi 1TB/AI-Drive/Agent-Output/comfyui/images

Data model (files, not tables). A render is {prompt_id, status, seconds, images[]} where each image is {filename, subfolder, path, exists, dims, url}. prompt_id is ComfyUI's UUID and the only join key an agent needs between comfy_submit and comfy_result.

Integration boundaries.

  • Harness → MCP: newline-delimited JSON-RPC on stdio, protocol 2024-11-05.
  • MCP → ComfyUI: HTTP on loopback, no auth, no retries beyond the caller's.
  • MCP → disk: reads templates and models; writes only staged inputs under ComfyUI/input and never outside the configured output root.

Seams (where this is meant to change). New capability = new template file + one profile line. New harness = one config entry pointing at the same script. New model = a file in the canonical store.

5. UX flows

The product has two faces: the agent surface (tool calls) and the human surface (ComfyUI's own web UI, unchanged).

F1 — Ask an agent for an image (primary).

  1. User: "render a hero image of a brass diving helmet on a workbench".
  2. Harness picks comfy_generate with profile: sd15 (or sdxl for a final).
  3. Server builds the graph from the template, submits, waits up to wait_s.
  4. Returns status: success, seconds, and an absolute path.
  5. Harness embeds the path or files the image with the document.

F2 — Render outlives the tool timeout. comfy_generate returns status: running + prompt_id → harness calls comfy_result once → path. (This is why no harness needs a raised timeout.)

F3 — Improve an existing picture. comfy_img2img with denoise 0.3–0.5 keeps composition; 0.7–0.9 reimagines. Then comfy_upscale for print size.

F4 — Something is wrong. comfy_status separates "server down" (with the exact start command) from "bad workflow" (ComfyUI's node-level rejection text passed through verbatim).

Screen inventory. Human surface is the stock ComfyUI graph editor and template library at 127.0.0.1:8188 — no custom screens, deliberately: building a second UI would be a second product to maintain. Agent surface has no screens; its "interface" is the tool schema set in §6.

Error and empty states (agent surface).

  • Server down: ComfyUI is not answering at http://127.0.0.1:8188 (…). Start it with: bash '…/start-comfyui.sh'.
  • Bad model name: ComfyUI's value_not_in_list detail, naming the field and the file.
  • No upscale model installed: no upscale model installed under ~/AI Hub/models/upscale_models.
  • Nothing queued: comfy_queue returns depth: 0, not an error.

6. Interface design (the agent-facing "UI system")

For an infrastructure product the design system is the tool contract: names, schemas, defaults, return shapes and error voice. Rules applied:

  • Names are verbs on an object — comfy_generate, comfy_upscale, comfy_result.
  • Defaults are safe and fast — profile: sd15, wait_s: 30, seed: -1 (random), a house negative prompt; a caller who says nothing gets a usable image in ~15 s.
  • Every schema is closed — additionalProperties: false, enums for profiles, ranges on width/height/steps/cfg. A model cannot invent an argument that silently does nothing.
  • Returns are one JSON object as text — no images inline, no binary over stdio; paths and dimensions instead.
  • Errors are sentences with the next action, and they say who is down and what command fixes it.
  • Two-step escape hatch is first class — comfy_submit/comfy_result for long renders.
  • Voice: house English, no exclamation, no emoji, no "Oops".

Browser UI: stock ComfyUI (dark, node graph). No theming work; the tokens of this product are the JSON above.

8. Testing strategy

  1. Direct API smoke (tests/smoke.py) — builds the graph, POSTs /prompt, polls /history, prints the image name. Proves the engine, not the wrapper.
  2. MCP acceptance (tests/mcp_acceptance.py) — handshake, tools/list, comfy_status, comfy_generate, comfy_outputs; exits non-zero on failure. This is the contract test every harness change must keep green.
  3. Per-harness live runs — one real prompt through Hermes, dsh and omp, each required to return a path that exists on disk. Registration alone is not green.
  4. Recovery test — kill the server, run the keepalive, require /system_stats 200 and the correct device afterwards.
  5. Regression rule — a template change re-runs (2) and the affected harness run before it is called done.

Not tested here: visual quality scoring (a human judgement), and multi-user concurrency (single user by design).

9. Out of scope, assumptions, risks

Out of scope now: Flux/video weights (disk), ComfyUI custom-node marketplace installs, a second custom UI, tailnet/public exposure, automatic image deletion, training a LoRA on Ricardo's own images.

Assumptions: macOS 27.2 on Apple silicon with MPS (true here); the Hiksemi SSD is usually mounted; one person uses the Mac at a time; uv available for future Python work.
