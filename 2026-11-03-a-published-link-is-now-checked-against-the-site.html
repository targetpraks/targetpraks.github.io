A published link is now checked against the site

a page still building is reported as building, never as a dead link GitHub checks both rules on every merge, including merges made on the web

What happened

Two Read the HTML links dead-ended on a 404 this week. They looked like one bug and were two different ones — which is why fixing only the publish tool would have left one of them alive.

The free-LLM edition was never broken. Its page was pushed to the site at 10:23 and GitHub Pages finished building it at 10:27:13 — three minutes and thirty-five seconds later. Anyone who opened the link inside that window got a 404, and the report repeated it. The page is live: Free LLM tier — NVIDIA · OpenRouter · OpenCode. A slow build had been mistaken for a failed publish, and nothing in the tool knew the difference.

The AAC edition was genuinely renamed away. It was published on 2 November at 23:12:56 under one name, and 73 seconds later a pull request merged on github.com (83d1afda) renamed it to 2026-11-02-aac-wall-system-business-model-south-africa.html — and rewrote its ledger row in the same commit. So the record of published pages still looked complete while the address in your vault note and on the jump page had stopped existing. The guard built last week cannot see this: it runs in this Mac's git hooks, and a merge on the web never touches this Mac.

Both addresses work now: the note's link → the current edition.

What changed

A URL is a promise only once the site serves it. publish-document no longer hands back an address because it wrote a file. After the push it checks that the page is really on the site and asks the site for it. Until the answer is a 200, the URL is either withheld — if the page never reached the site, you get a warning instead of a link that will 404 for as long as it is quoted — or labelled for what it is:

Pages: serving  — https://targetpraks.github.io/… (HTTP 200)
Pages: building — https://targetpraks.github.io/… (GitHub Pages needs 1–4 minutes)

A page that is still building is building, not broken, and the publish never waits forever: past the timeout it says so and still delivers the document, its AI-Drive copy and its Discord post. A slow build must not cost you a document.

A name once published stays published. If a page is renamed or moved, the old address becomes a small forwarding page — the same title, a canonical link and a real link to the current edition — so the link in your note keeps working forever. Three were created today: both AAC addresses your notes quote, and papa-pasta-leverage-2026-10.html, which a vault note quotes and which had also been retired.

A check runs where the merge happens. The pages repository now has its own GitHub workflow (run), and it holds both rules: every published URL must answer 200, and every name that was ever published must still exist. It runs on every push and once a day, in fifteen seconds, and it cannot be bypassed by merging on the web — which is exactly how the AAC link died. This Mac also has a daily audit that includes the links quoted inside your vault, the one surface GitHub cannot see.

What it means for you

Nothing to do, and nothing new to remember. The two links you were sent work. When a page is genuinely renamed, the old address keeps answering instead of dead-ending. And the next time a page does go missing, the build goes red within a minute instead of you finding it first.
