Why these two

The benchmark put three engines within two characters in a thousand of each other, so accuracy alone could not choose. The gate weighed accuracy, then tables and reading order, then speed, licence and install. For the failover the rule was different and stricter: it must share no runtime with the primary, so that a broken Python environment cannot take out both. PaddleOCR-VL lives in a pip venv; OCRia-1 lives in the Ollama server. Different processes, different failure modes, same measured quality.

3 — AgenticOS on macserver

The host now has a working ocr on Tesseract 5.5 with RapidOCR behind it, both installed user-local with no root, plus ocr-mcp.py exposing the same stack as MCP tools ocr_extract and ocr_engines.

Registered. The connection ocr is live for the Infinity Brands organization (scope org, bearer auth, tools narrowed to those two). It was written through the platform's own McpConnectionService.create_for_org, so the token is sealed by their vault and the URL passed their SSRF check — the same path the console takes. Their own reachability probe then answered reachable, 2 tools discovered, last_status: ok, and both the backend and worker containers completed a real extraction through it. A five-minute cron keepalive restarts the endpoint if it ever stops; the table was dumped to backups/ before the write.

The honest consequence: documents read by AgenticOS are transcribed by Tesseract, which is reliable on clean text and destroys table structure. For an invoice whose columns matter, have that work done on the Mac mini stack instead, or give the VM more memory — 5.7 GB was not enough for the 0.9B model.

Using it

ocr page.png                  # primary, then failover, then last resort
ocr scan.pdf --page 2         # render one PDF page first
ocr page.png --json           # {"engine": …, "seconds": …, "text": …}
ocr page.png --engine primary # the honest test that the primary still answers

# a born-digital PDF needs no OCR at all — check first:
pdftotext -l 1 file.pdf - | head

Two traps that cost real time

  • PYTHONPATH. Hermes exports its own python3.14 site-packages; inside a 3.12 venv that pulls in a 3.14 numpy and paddle dies with a cryptic _multiarray_umath error. The wrapper unsets it.
  • A silent fail-through looks like success. While the primary was missing paddlex[ocr] it answered nothing and OCRia-1 quietly covered for it — same quality, so the stack looked healthy. --engine primary is the only honest check, and it is what finally caught it.
