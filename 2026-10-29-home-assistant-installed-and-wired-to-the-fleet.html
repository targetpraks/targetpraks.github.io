02Why the first attempt failed — and the one route that fixed it

Every device answered 000 from inside Home Assistant while the Mac could reach them fine. The Colima VM carries two default routes: eth0 into Lima's user-mode NAT, which only carries host traffic, and col0, the bridged --network-address interface. Packets were leaving the wrong one.

# before — HA container, every LAN device unreachable
http://192.168.0.181:631/    000
http://192.168.0.118:1400/   000

# one route, pointed at the bridged interface
$ colima ssh -- sudo ip route replace 192.168.0.0/24 via 192.168.64.1 dev col0

# after — HA container
http://192.168.0.181:631/    301
http://192.168.0.118:1400/   200
http://192.168.0.174:5000/   200
http://192.168.0.133:8080/   200

That route now lives in ~/.config/maio-stack/stack-up.sh, next to the Colima start flags, so it is re-applied at every login. Without it, Home Assistant is blind to the house.

Where the config actually lives. Home Assistant's config sits on the Colima VM disk, not on a host folder: every Colima mount is read-only, so a bind mount of a host directory cannot work — Docker silently created the folder inside the VM instead. That survives reboots, but it would die with colima delete. A launchd job (com.maio.home-assistant-backup) now snapshots it to AI-Drive/backups/home-assistant/ every night at 03:20 and keeps fourteen days — first snapshot verified at 680 KB, 300 files.
