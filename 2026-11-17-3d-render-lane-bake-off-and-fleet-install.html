3D render lane: the bake-off, and where it now runs

Blender 5.3.0 vs Crucible 0.20.0, measured on the M4 Pro · installed on three agents' hosts

Nothing on the market beats Crucible on both axes — but Blender does beat it where it counts. On the identical scene, at identical settings, Blender's Cycles path trace is faster (2.75 s vs 3.17 s at 960×540, 64 samples, 6 bounces) and roughly a generation better in quality, materials and features. Crucible keeps exactly one crown: real-time raster frames, where a WebGL forward renderer is 14× cheaper per frame. So the lane now runs Blender + a thin render service, wired to all three hosts, and Crucible stays as a fast preview tool.

Why the service is a narrow DSL, not "run Python in Blender"

The GUI plugin already lets an agent execute arbitrary Python — fine on a laptop a person is watching. For a server that other people's agents can reach over the LAN, that is a remote-code-execution endpoint with a password that never rotates. So the service instead accepts a scene description: nodes (plane, box, sphere, cylinder, torus, cone), materials (colour, roughness, metal, transmission, emission), lights, camera, world, engine, resolution. Nothing the caller sends is executed — it is parsed, validated, and turned into a Blender script by the server itself.

{
  "jsonrpc": "2.0", "method": "tools/call",
  "params": { "name": "render_still", "arguments": {
      "scene": { "nodes": [ {"type": "sphere", "position": [0,0,1], "size": 1,
                               "material": "red"} ],
                  "materials": [ {"id": "red", "color": [0.8,0.12,0.1], "roughness": 0.2} ],
                  "lights": [ {"type": "sun", "position": [3,4,6], "target": [0,0,0.5],
                                "energy": 4} ],
                  "camera": { "eye": [4,4,3], "target": [0,0,0.6], "fov": 38 } },
      "width": 960, "height": 540, "engine": "EEVEE" } }
}

Tools: render_still (returns the PNG inline plus a job id), render_clip (orbit or static, 1–30 s, MP4 via ffmpeg), render_status, list_renders.

Operational notes — read these

  • One incident, fixed. The first attempt to admit the LAN host set MCP_ALLOWED_HOSTS=192.168.88.173 as a plain string; the app parses it as a JSON list, so app crash-looped for about a minute on the staging platform. Corrected to ["192.168.88.173"], containers recreated, health back to 200. Revert is one line: delete both variables from ~/agenticos/.env and docker compose up -d --no-deps app worker.
  • The token lives at ~/3d-render-mcp/token (0600) on each host and in Hermes's 0600 config; on AgenticOS it is sealed in the connection row and never read back.
  • Durability differs by host. This Mac: launchd with KeepAlive. The office mini: cron every five minutes and at reboot, because that account has no GUI session for launchd.
  • RAM. A clip render is one Blender process; the office mini has 16 GB and runs other work — render_clip is the expensive call, stills are cheap.

What is still open

  • No agent on AgenticOS has yet called the tool inside a run — the connection is proven, the tool surface is proven, an agent-initiated render is the next proof.
  • AgenticOS stored the tool list without input schemas (input_schema: null); if its agent prompts turn out to need parameter hints, that is a platform-side detail to chase.
  • Blender's MCP server in this session still needs /reload-mcp or a fresh chat to expose the plugin tools alongside the new HTTP ones.
