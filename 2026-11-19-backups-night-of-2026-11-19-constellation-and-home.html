The log, every single night, says the same thing:

tar: Failed to open '/Volumes/Hiksemi 1TB/AI-Drive/backups/home-assistant/home-assistant-config-2026-11-19.tar.gz'
open /Volumes/Hiksemi 1TB/AI-Drive/backups/home-assistant: operation not permitted

docker cp into the work dir succeeds (.work-2026-11-19 holds a 6.2 MB home-assistant_v2.db plus a 4.1 MB WAL) — because the Docker daemon does that write, not the launchd shell. The tar -czf runs in the launchd shell and is refused. set -e then aborts before the cleanup line, which is why nineteen half-built work dirs have piled up.

Why I believe it is the removable-volume permission rather than a broken script: the sibling job that does work runs through a wrapper. com.maio.backup's ProgramArguments point at launchers/backup.sh, which is a symlink to /usr/bin/osascript (a TCC-granted launcher); com.maio.home-assistant-backup runs /bin/zsh …/backup.sh directly, with no wrapper. I looked for the verdict in the TCC log — tccd does show service=kTCCServiceSystemPolicyRemovableVolumes AUTHREQ_CTX entries in the 03:20–03:25 window, but daemon_dict=<private> means macOS does not print allow/deny, so the denial itself is inference from the two facts above, not a logged verdict.

Consequence: the entire house config — integrations, auth, automations — exists only inside the Colima VM, and a colima delete loses it.

docker lives at /opt/homebrew/bin/docker; the LaunchAgent's PATH has no /opt/homebrew/bin, so docker fails, gzip happily compresses the empty stream into a 20-byte file, the script's if ! pipeline test reads gzip's exit status (0), gzip -t passes because an empty stream is well-formed, and the file is renamed into place.
