Executive summary. Three deliberate workstreams, one plan. What changed in v4. Three corrections, one document. Memory bridge and vault recall split across those layers — Router gets shared context and the dispatch decision, Workers get a scoped slice — instead of pretending DSH is one flat session. (2) The code-rendered video lane is restored as Workstream C: it was dropped when this document was re-emitted from the older v2 base on 2026-11-02. (3) The memory claim is corrected to what was actually measured: the fleet-wide Mnemosyne rollout ran, the trial was then reverted, and Hindsight is the active provider again — so the bridge is a provider adapter, not a plugin bolted to one vendor's tables.

1. Vision & Problem

Problem. DeepSeek Harness sessions are isolated from the rest of Ricardo's Mac stack. A DSH session cannot see Hermes memory (user preferences, standing rules, cross-session facts), cannot query the Obsidian vault (Maio Hub) for PRDs, research or guidelines, and has no curated, risk-assessed path to the community plugin ecosystem. With the super-agent, the problem gets sharper: work is spread across a Router and many Workers, so context must be deliberately placed — shared where it must be shared, isolated where it must be isolated. And when a brief asks for video, the only paths today are a stock subscription or a studio quote, while this Mac already holds the parts of a code-rendering pipeline that costs nothing per render.

Solution. dsh-maio-nexus registers Cordis handlers that (a) feed the Router a compact shared memory + vault context, (b) let the Router package a scoped context slice for each Worker dispatch, (c) give Workers a read-only vault_recall tool and a scoped memory query on the active provider, and (d) return durable facts from Workers to the Router, which is the only writer through Hermes' memory tools. No second memory store; no cross-worker leakage. Workstream C pins a short, verified, free stack that a DSH session can drive from brief to finished MP4.

That history is why the bridge is written as a provider adapter: it asks Hermes which provider is active, then reads that store through a documented, capability-detected path, with a SQLite busy timeout and bounded retry. If the fleet re-adopts Mnemosyne — or moves to a third store — the adapter swaps; the plugin does not.

2. Super-agent fit — how nexus works with the Router/Worker

The prototype's architecture, from its README and the DeepSeek design article: a long-lived Router handles people and dispatches; context-isolated Workers do one work item each in their own session and directory; events (chat, GitHub, CI) arrive as triggers; a Watchdog checks progress; state lives in a database while compute and machine are separated. The Router "cannot do the work" — it only decides which Worker gets which request.

2.1 Where each nexus module lives

Module Layer What it does in the super-agent
nexus-memory-bridge Router + Worker Router side: builds the compact shared memory block injected into the Router's context (standing rules, user preferences, active plans) so a plan agreed in Discord is understood when the same thread continues in DSH Web or Desktop. Worker side: answers a scoped query — only the facts relevant to that Worker's work item — never the whole store. Provider resolved at runtime.
nexus-profile-resolver Router Resolves which Hermes profile owns the conversation before any store is opened. Isolation is enforced per profile and per Worker: a Worker cannot open a sibling's store.
nexus-vault-recall Router + Worker Router uses it to answer "what did we decide?" and to cite PRDs/guidelines when dispatching. Each Worker gets the same read-only tool bound to its task (AI-Space scope), so it can pull the exact note it needs without a shared mutable cache.
nexus-context-packet (new in v4) Router The dispatch contract: Router hands each Worker a packet of {request, scoped memory facts, vault references, acceptance criteria, channel + thread id}. This is the Router's decision output — what the article calls "which Worker gets which request" — not a task breakdown.
nexus-memory-return (new in v4) Worker → Router Workers do not write memory. They return memory candidates (fact, confidence, source) to the Router; the Router writes through Hermes' memory tools, preserving one source of truth, consolidation and audit.
nexus-index-cron Router/ops Courage job refreshes the vault index and warms the memory read path; the Watchdog consumes its freshness timestamp.
nexus-watchdog (new in v4) Router/ops Separate timer session: checks every Worker is making real progress, checks the active memory store is readable (the lock observed during the Mnemosyne trial is exactly the failure mode it exists for), checks vault index freshness. On failure it reports in plain language and marks the recall path degraded — fail-closed, never blocks the harness.

2.2 The Router's dispatch decision (the "vote" step)

The prototype has no formal voting mechanism. The Router's dispatch is a rules-first, model-judged decision: deterministic filters run in code, and the model judges only what passes. nexus models that step explicitly in nexus-context-packet: the Router picks the Worker type, assembles the scoped memory + vault slice, and records why. If "router vote" meant a literal multi-agent vote, say so and I will add a scoring variant — otherwise this is the decision step the PRD implements.

2.3 Event-driven recall (proactive, but gated)

  • Triggers: new or changed vault note, a memory write, a chat message, a GitHub comment, a CI result. Code filters first — a note that fails the AI-Space scope filter never reaches a model.
  • Observe mode: unrequested proactive work is recorded only until Ricardo approves the rule that allows it — matching the prototype's "acts only when asked, or when a written rule allows it."
  • Freshness: a vault write invalidates the recall cache and schedules a reindex; the Router never answers from a stale index without saying so.

2.4 Continuity across channels

Discord, Telegram, DSH Web and DSH Desktop all terminate at the Router, so the same memory slice and vault scope apply everywhere. A Worker subscribes to its own thread, so follow-ups skip the Router — exactly the prototype's behavior — while the Router keeps the cross-channel record.

Acceptance criteria. F1 (memory): a canary fact written through Hermes' active memory tool is recalled by a DSH session unprompted, and the same canary written by a different profile is not recalled (isolation test). F2 (vault): vault_recall returns exact vault snippets and vault file hashes are unchanged. F3 (bundle): one bundle installs on Web, Desktop and the prototype without root or core breakage. F4 (index): nightly job completes silently and idempotently. S1 (Router): the Router injects shared memory + vault context and produces a context packet for every dispatch. S2 (Worker isolation): Worker A cannot recall Worker B's scratch facts or open a sibling profile's store. S3 (follow-up): a follow-up in the same thread reaches its Worker without a Router re-decision; the Router still records it. S4 (event freshness): a vault write is visible to recall within the configured SLA (default 5 min) or the answer says "stale index". S5 (watchdog): a forced lock on the active store is detected, reported in plain language, and the recall path degrades fail-closed. S6 (cross-channel): a plan agreed in Discord is recalled in a DSH Web session for the same profile. Fail-closed: if the active provider is locked or unreachable, DSH proceeds with built-in MEMORY.md/USER.md context and logs a warning — no fatal errors.

6. Plugin governance policy (applies to A, B and C)

  • No blind installs. Every plugin is staged, its dsh.bundle / cordis.patch.yml read, network calls and filesystem writes reviewed, license checked. A video repo is installable code too: same gate.
  • Ricardo installs. Adrianna A stages; Ricardo installs after reviewing the manifest. I never install third-party code or change a live profile on my own.
  • One memory source of truth. Whatever provider Hermes has active — Hindsight today. No parallel store, no direct store writes; Worker facts return to the Router, which writes through Hermes' memory tools.
  • Read-only vault. No plugin gets write access to Maio Hub. Beast remains the sole writer via OpenKnowledge.
  • No credentials. No key, token or password enters any plugin config, log or artifact — the credential hard stop applies unchanged.
  • Proactive work is gated. Unrequested actions run in observe mode until Ricardo approves a written rule — the prototype's own philosophy. A render never ships to a client channel without Ricardo's look first.
  • Fail-closed and revertible. A plugin failure degrades to standard DSH behaviour; every install has an uninstall step and a Safe Mode first run where offered.

7. UX & UI design

DSH Settings → Maio Nexus: memory-provider status (active provider, store path, last write, lock/degraded badge), vault scope (AI-Space default, read-only badge), Router/Worker panel (active Workers, dispatch reasons, context-packet sizes), recall latency and token telemetry, adopted-plugin list with version + install state, and a Video tab listing which lane elements are present (HyperFrames, Remotion, Blender, ComfyUI, FFmpeg, faster-whisper) with the last render path and duration. Third-party plugins keep their own pages; the panel only reports.

8. Non-functional requirements

  • Security: 100% local; no vault, memory or credential content leaves the machine; read-only vault and read-only memory store; no telemetry.
  • Performance: vault FTS recall < 50 ms warm; memory recall < 100 ms warm; Router dispatch adds no visible latency; context packets stay within a token budget (default 2k); a ≤ 30 s code render completes unattended in one pass.
  • Reliability: SQLite busy timeout + bounded retry on every memory-store read; fail-closed; nightly index idempotent; Watchdog detects lock/staleness; repeated renders of the same brief are reproducible.
  • Compatibility: DSH ≥ 0.2.x on Web and Desktop; super-agent bundle format tracked as research code (MIT, not an official product; may break); the memory adapter detects the active provider and its schema version, failing loudly rather than silently returning nothing.
