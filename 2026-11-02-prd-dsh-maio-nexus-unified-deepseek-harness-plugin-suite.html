Executive summary

Three workstreams, one plan, one constraint that shapes all of them: DSH's super-agent design splits work between a long-lived Router and context-isolated Workers, so context has to be placed deliberately rather than dumped into a single window.

(A) Build dsh-maio-nexus — eight modules that give DSH shared memory with Hermes, read-only recall over the Maio Hub vault, a dispatch contract between Router and Workers, and a watchdog that reports in plain language. It is written as a provider adapter, not a plugin bolted to one vendor's tables.

(B) Adopt a curated subset of the community plugin ecosystem — ten plugins, each with a decision and a manual install step you own.

(C) Render video from code — HTML, React, 3D, local captions, FFmpeg — so a brief becomes an MP4 with no stock library and no studio invoice. The lane is installed and gated; only stills are missing.

(D) Prove it through the same three-skill chain you built with Hermes: app-plan → app-build → app-verify, with an acceptance suite written from this PRD and kept where the builder cannot read it (§7). DSH's first real job is to run that chain, because a super-agent that cannot build and verify its own toolkit is a demo, not a tool.

The one-sentence case. DSH is already installed here (0.2.1-rc.5, six profiles, zero third-party plugins) and it can already reach your local models; what it cannot do is see what your Hermes fleet knows, read the vault, or make a video. Those three gaps are the entire PRD.

1. Vision and problem

Problem. DSH sessions are isolated from the rest of this Mac. A DSH session cannot see what Hermes knows (preferences, standing rules, cross-session facts across 2,550 vault notes and four active profiles), cannot query the Maio Hub vault for the PRD or the guideline it is supposed to follow, and has no risk-assessed path through a plugin ecosystem of 25,000+ tagged repos that is heavily tag-squatted. Three concrete gaps, measured today:

  1. No memory bridge. Hermes' memory is Hindsight on default, batman, beast and courage; DSH has no way to ask it anything. A rule you gave in Discord this morning is invisible to a DSH session this afternoon.
  2. No vault recall. The vault holds 2,550 markdown notes (OK's mirror at HEAD: 2,403 notes, 3,226 files). DSH can read files it is pointed at and cannot search them.
  3. No curated plugin path. ~/.dsh/profiles/web/package.json shows "dependencies": {} — zero third-party plugins. That is the right starting state; the wrong response would be to install ten of them.

And one sharpening. The article DSH published on 1 November ("Exploring Super-agent Design") moves the design target from "a session" to "a Router plus Workers". Every module below is placed against that split. A plan written against a single flat session would be obsolete before it shipped.

Solution. dsh-maio-nexus registers Cordis handlers that (a) feed the Router a compact shared memory + vault context, (b) let the Router package a scoped slice per Worker dispatch and record why, (c) give Workers a read-only vault_recall tool and a scoped memory query on the active provider, and (d) return durable facts from Workers to the Router — the only writer, through Hermes' memory tools. No second store. No cross-worker leakage. Plus a watchdog session outside the main system, which is the article's own control-loop pattern.

3. Architecture

3.1 Module map

Module Layer What it does
nexus-memory-bridge Router + Worker Router side: a compact shared block (standing rules, preferences, active plans). Worker side: a scoped query — only facts for that work item. Provider resolved at runtime, never assumed.
nexus-profile-resolver Router Resolves the owning Hermes profile before any store is opened. Isolation is per profile and per Worker. Six DSH profiles exist; each maps to exactly one Hermes profile.
nexus-vault-recall Router + Worker vault_recall tool: FTS5 + semantic over AI-Space markdown, read-only, through Beast/OpenKnowledge. Returns snippets with note paths and next-hop ids.
nexus-context-packet Router The dispatch contract in §4.3.1: request, scoped facts, vault refs, acceptance criteria, channel + thread id, and the recorded reason.
nexus-memory-return Worker → Router Workers never write. They return candidates (fact, confidence, source); the Router writes through Hermes' memory tools — one source of truth, consolidation, audit.
nexus-thread-bind (new in v5) Router → Worker The Worker holds its Thread id so follow-ups pass through without a Router re-decision — the article's 37% Router-token saving. The Router still records every event.
nexus-index-cron Ops Courage job refreshes the vault index and warms the read path; publishes a freshness timestamp the watchdog reads.
nexus-watchdog Ops Separate timer session: Worker progress, memory-store readability, index freshness, render-lane health. Reports in plain language, ≤100 words. Fail-closed.
dsh.bundle + cordis.patch.yml Packaging One bundle for web, desktop, dshweb, headless, mini, acp. desktop is app-owned: patch layer only, never hand-edited bundles.

3.2 The dispatch decision

The prototype has no voting mechanism. Dispatch is rules-first, model-judged: deterministic code filters, the model judges only what remains. nexus makes that step explicit and auditable — the Router chooses the Worker type, assembles the scoped slice, and records why. If you want a literal multi-agent vote (N candidates scored, best chosen), that is a variant I can add; today's design is the decision step the article actually describes.

3.3 Events, proactive work and freshness

  • Triggers: new or changed vault note, a memory write, a chat message, a GitHub comment, a CI result. Code filters first; a note outside the AI-Space scope never reaches a model.
  • Observe mode: unrequested proactive work is recorded only until you approve the written rule that allows it. This mirrors the prototype's "acts only when asked, or when a written rule allows it", and the article's own "silently reproduce and fix" policy — which is exactly the rule I would propose in phase 5, not phase 1.
  • Freshness: a vault write invalidates the recall cache and schedules a reindex. The Router never answers from a stale index without saying "stale index".

3.4 Continuity across channels

Discord, Telegram, DSH Web, DSH Desktop and T3 Code all terminate at the Router, so one memory slice and one vault scope apply everywhere. A Worker subscribes to its own Thread, so follow-ups skip the Router — as the article specifies — while the Router keeps the cross-channel record.

Until mflux is installed, stills come from three places that are already free and already here: an HTML/SVG frame laid out in a HyperFrames composition, a three.js or Remotion 3D frame, or Blender's offline renderer. That covers posters, title cards and typographic frames. A photographic still needs mflux — and installing it is a phase-3 step I stage, not a build I invent.

ComfyUI stays out unless a brief needs a node graph. It is GPL-3.0, heavy, and duplicates what mflux does for a single image; its real value is pipelines, not pictures.

6.3 Acceptance criteria

F5 (render): a brief produces a 1080×1920 MP4 of ≤30 s with no stock asset and no paid credit. F6 (text): all text arrives through cards, overlays or type — never an FFmpeg text filter. F7 (locality): every asset and render stays on this Mac; no paid or hosted call without separate approval. F8 (app): the DSH web app shows the last render, its size and its QC verdict without a terminal. F9 (CLI): dsh <profile> "<brief>" runs headless, prints a receipt path, and a second run of the same brief produces the same bytes. F10 (link): one durable token-free artefact link per render, resolving after a restart. F11 (reproducibility): same brief, same composition version, byte-comparable output. F12 (receipt): every render writes the receipt in §4.3.4 and the panel derives its link from that receipt. F13 (stills — new): a poster renders from the same brief through a free path (HTML/3D frame or local mflux) and the receipt records which path produced it. F14 (gate — new): no render counts as finished until render-qc passes; the receipt embeds the verdict, and only --allow-static and --allow-silent may waive a finding.

8. Governance

  1. No blind installs. Every plugin is staged, its dsh.bundle / cordis.patch.yml read, its network calls and filesystem writes reviewed, its licence checked. A video repo is installable code too: same gate.
  2. Ricardo installs. I stage and verify; you install after reviewing the manifest. I never install third-party code or change a live profile on my own.
  3. One memory source of truth. Whatever provider Hermes has active. No parallel store, no direct store writes; Worker facts return to the Router, which writes through Hermes' memory tools.
  4. Read-only vault. No plugin gets write access to Maio Hub. Beast remains the sole writer via OpenKnowledge.
  5. No credentials. No key, token or password enters any plugin config, log, receipt or artefact. The credential hard stop applies unchanged, including to me.
  6. Proactive work is gated. Unrequested actions run in observe mode until you approve a written rule.
  7. Fail-closed and revertible. A plugin failure degrades to standard DSH behaviour; every install has an uninstall step and a Safe Mode first run where offered.
  8. Free models only. No paid model credit, no API top-up, no render farm, no stock licence, no hosted video model. A lane that needs money stops and asks. (Your rule, 2026-11-02.)
  9. Independent verification. The acceptance suite is authored from the specification, stored outside the build, and the builder sees only the scorecard. A failing P0 escalates; it is never waived, and the suite is never edited to make a build pass.
