PRD: dsh-maio-nexus — Unified DeepSeek Harness Plugin Suite + Ecosystem Adoption

Targets: Web profile (dsh web) and official DSH Desktop app · Base integration: Hermes memory + Beast / OpenKnowledge vault (AI-Space) · Model path: local Ollama gateway :11434/v1 · Staged by Adrianna A, reviewed and manually installed by Ricardo.

Executive summary. Two deliberate workstreams, one plan. (A) Build a custom suite — dsh-maio-nexus — that gives DSH shared memory with Hermes and read-only recall over the Maio Hub vault. (B) Adopt a curated, verified subset of the community plugin ecosystem alongside it — each with an explicit adopt / evaluate / reject decision, a security review gate, and a manual install step owned by Ricardo. The two workstreams share one staging area, one security policy, and one install gate.

What changed in v2: v1 covered only the custom suite. This version adds the full ecosystem adoption matrix (all ten re-verified plugins from the top-10 study), the plugin governance policy, and a unified phased delivery plan.

1. Vision & Problem

Problem. DeepSeek Harness sessions are isolated from the rest of Ricardo's Mac stack. A DSH session cannot see Hermes memory (user preferences, standing rules, cross-session facts), cannot query the Obsidian vault (Maio Hub) for PRDs, research or guidelines, and has no curated, risk-assessed path to the community plugin ecosystem — the dsh-plugin topic alone carries 25,115 tagged repos, many of them tag-squatters.

Solution. dsh-maio-nexus registers Cordis plugin handlers that inject Hermes memory into DSH session context and expose a read-only vault_recall tool over AI-Space via Beast/OK. In parallel, the adoption workstream gives each community plugin an explicit decision and a reviewable install path — no blind installs, no third-party code run by me.

4. Plugin governance policy (applies to A and B)

  • No blind installs. Every plugin — mine or third-party — is staged, its dsh.bundle / cordis.patch.yml read, its network calls and filesystem writes reviewed, and its license checked.
  • Ricardo installs. Adrianna A stages; Ricardo runs the install command or uses the Desktop settings after reviewing the manifest. I never install third-party code or change a live profile on my own.
  • Read-only vault. No plugin gets write access to Maio Hub. Beast remains the sole writer via OpenKnowledge.
  • No credentials. No key, token or password enters any plugin config, log or artifact — the credential hard stop applies unchanged.
  • Fail-closed. A plugin failure degrades to standard DSH behaviour and is logged; it never blocks the harness.
  • Revert path. Every install has a documented uninstall step and, where offered, a Safe Mode / isolated profile for first run.

5. UX & UI design

The suite adds a settings panel under DSH Settings → Maio Nexus: connection status for Hermes memory and Beast/OK, vault scope selector (AI-Space default, read-only badge), recall latency and token telemetry, and a list of adopted community plugins with version + install state. Third-party plugins keep their own settings pages — the panel only reports their status.

6. Non-functional requirements

  • Security: 100% local execution; no vault contents or credentials leave the machine; read-only vault access; no telemetry.
  • Performance: local FTS5 vault recall < 50 ms warm; memory injection adds no visible latency to session start.
  • Reliability: fail-closed as above; nightly reindex idempotent.
  • Compatibility: DSH ≥ 0.2.x for both Web and Desktop; plugin API differences handled by capability detection, not version pinning alone.

7. Delivery plan

  • Phase 1 — Staging (Adrianna A). Build the dsh-maio-nexus bundle skeleton (manifest, TS glue, vault_recall tool, memory bridge) under ~/AI Hub/dsh-maio-nexus/; stage the adoption review notes for the Evaluate tier; no installs.
  • Phase 2 — Review (Ricardo). Manifest and code review; approve which Evaluate plugins graduate to Adopt.
  • Phase 3 — Install (Ricardo). Manual install into the Web profile and the Desktop app; first run in Safe Mode where available.
  • Phase 4 — Verify (Adrianna A). Run the acceptance criteria against real output; report pass/fail with evidence; log to AI-Drive/Agent-Output/adrianna.
  • Phase 5 — Operate. Courage nightly reindex; monthly plugin review (new versions, CVEs, license changes).

Out of scope. Installing any plugin without Ricardo's sign-off; writing to the vault; sending any credential, ID or health data to any plugin, gate or sandbox; auto-merging upstream plugin code; replacing Hermes memory or Beast with a community store.
