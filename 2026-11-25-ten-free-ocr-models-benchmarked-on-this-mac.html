Ten open OCR models, benchmarked on this Mac

The model in that Ollama post, LlamaIndex's OCRia-1, is genuinely excellent — and it is not quite the winner. Over eleven document pages, a 0.9 billion-parameter model from PaddleOCR beat it by a whisker, and a third model matched both while running five times faster. Every number here comes from actually installing and running each engine on an M4 Pro with 24 GB of RAM.

How the pick was made

Accuracy across the top three differs by two characters in a thousand — that is a tie, not a ranking. So the final pick went to the local decision model with the measured table and the priority order stated: accuracy first, then tables and reading order, then speed, then licence, then install. It ranked 5 candidates and then confirmed the winner head-to-head both ways round.

PaddleOCR-VL 1.6 48%
OCRia-1 (Ollama) 31%
Surya OCR 0.24 21%
GLM-OCR (Ollama) 0%
DeepSeek-OCR (Ollama) 0%

Confirmation against Surya, the speed alternative, asked both ways round: PaddleOCR-VL 1.6 91% as the question and 87% with the order reversed — order-invariant, so the pick stands. Against OCRia-1 the same head-to-head returned 96% and 95%. Route: local d3-flash, logged to gates.csv.

What to actually use

  • General documents, best quality, Apache-2.0: PaddleOCR-VL 1.6. Perfect on nine of eleven pages, the only slip being the maths sheet. 32 s per page on this Mac because it runs on the CPU, and 2 GB on disk. It emits HTML tables with the cells intact.
  • If you want the one from the tweet and a one-line install: OCRia-1 (Ollama). ollama pull llamaindex/ocria-1:bf16 and you are done — no Python environment. It costs 9.7 GB and 27s a page here, and it matched OCRia-1 (Ollama) to PaddleOCR-VL on every page except the form and the maths. If you process a lot of pages, get a quantised build: the model card says the served version is about ten times faster than these bf16 weights.
  • If throughput matters: Surya OCR 0.24 at 6.3s a page with the same accuracy as the leaders. Read the licence before you put it in a product: the code is Apache-2.0 but the weights are Open Rail-M, free for research, personal use and companies under $5M revenue.
  • Plain text at volume, nothing to download: Tesseract 5.5.4 — 9% error at 0.6s a page, 26 MB of RAM. It is still the right tool for a clean single-column page and the wrong one for a form, a dense table or a photographed receipt.
  • Do not judge a table page by its text score. Tesseract's 9% error on the invoice hides the fact that it recovers every value but destroys the column structure — copy that output into a spreadsheet and the numbers land in the wrong cells.
The honest caveat on "best". On this corpus the top three are inside the noise of a single page. What genuinely separates them is not accuracy but speed, disk, licence and how you install them. If your documents look like faded newsprint scans rather than clean renders, retest — a synthetic-but-realistic corpus flatters every engine, and degradation is where these models diverge most.

How this was measured

Corpus

Eleven page images built for this test, each with exact ground truth captured at authoring time rather than transcribed by another OCR tool: a business letter, a tax invoice with a five-column line-item table, a two-column academic page, a dense eight-quarter financial table, a credit application form with checkboxes, a statistics sheet of formulas, a narrow thermal receipt, a handwritten shopping list, and three degraded phone-photo variants (perspective warp, 2° rotation, uneven lighting, gaussian blur, JPEG quality 62) of the letter, invoice and receipt.

Fairness

  • Identical PNG renders at 200 DPI (3.9 megapixels) fed to every engine.
  • Each model got its own documented prompt. OCRia-1 ran with its published system prompt and thinking off. DeepSeek-OCR ran without its grounding mode, whose coordinate tags would have polluted a text comparison.
  • Scores compare normalised text: markdown and HTML markup, checkbox glyphs and common LaTeX symbols are mapped to one form, so no model is punished for writing a ticked checkbox where the ground truth says [x].
  • Models ran one at a time, so no engine's latency was measured against another's load.

Metrics

  • CER — character error rate, Levenshtein over normalised text. Lower is better.
  • Lines — share of ground-truth lines that appear intact and in order.
  • Table cells — F1 over cells parsed from HTML or pipe tables, fuzzy credit at 85% similarity.
  • Table values — share of table values present anywhere in the output, ignoring structure.

Hardware and caveats

Apple M4 Pro, 16 cores, 24 GB unified memory, macOS 27.2.1, no CUDA. OCRia-1 ran as unquantised bf16 through Ollama on Metal; PaddleOCR-VL ran on the CPU because PaddlePaddle has no Metal backend here, which is why it is the slowest of the accurate models — expect a large speed-up on an NVIDIA box. Surya ran on the GPU through the llama.cpp server it spawns itself. One page per category means one bad page moves a category; the eleven-page mean is steadier than any single cell.
