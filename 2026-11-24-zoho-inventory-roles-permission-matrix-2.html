Zoho constraints found while building these (measured, not assumed)

  1. The role API cannot create roles on this org. POST /inventory/v1/roles returns 500 {"code":1000,"message":"Internal Error"} for every payload shape — including a body copied verbatim from the role's own GET /roles/{id} permissions. role_type accepts only Default; Custom, custom, Accountant, Standard and nine other spellings return 400 code 6517 "The role type you've provided does not exist". Reads work (GET /roles, GET /roles/{id}), so roles were created and corrected through the UI (Settings › Users & Roles › Roles), and every role was read back from the UI afterwards.
  2. GET /roles/{id} does not return the Inventory permission set. It returns a fixed catalogue of 26 entities from the neighbouring apps (expense reports, trips, petty cash, budgets). No items, invoices, salesorder or bill entity ever appears, so the API cannot verify an Inventory role. UI read-back is the only evidence channel.
  3. Report View forces module View. Granting a report's View auto-enables View on its module, and a report cannot stay enabled once that module View is removed — Zoho raises "You cannot enable access for the following report(s) without enabling at least view access for their associated modules" and blocks Proceed. This is why every role was finished by selecting report groups first, then stripping module permissions back to the intended list, then letting Zoho drop the reports it refuses.
  4. tax_rules View is unreachable without Settings access. Its View toggle is welded to the tax_rules full toggle, and both fall away when Settings access is off. Purchasing Manager, Accountant and Read-Only Auditor therefore carry no tax-rules permission; granting it would mean granting Settings access. Verified three times on separate saves.
  5. The "Full access" checkbox in a row overrides the row. Ticking it re-checks view/create/edit/ delete/approve; unticking any single permission clears "Full access". Every role was therefore written with individual permissions, never with "Full access".
  6. New roles start with everything ticked. A role is created from an all-permissions default, so the working method is "untick everything not in the spec", not "tick what is in the spec".
