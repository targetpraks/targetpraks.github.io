1. The correction that unblocked the view pass

The first build concluded "view filters are a UI-only job — POST …/view accepts filters and the read-back is {}". That conclusion was a mis-probe, and it is the single reason 98 views sat empty.

What is actually true (probed and verified tonight):

Call Result
POST /list/{id}/view with filters creates the view, drops the filters
PUT /view/{id} with only {filters} 400 VIEWS_015 View schema not found
PUT /view/{id} with a complete body (name, type, settings, filters, sorting, grouping) 200 — filters, sorting and grouping all persist
GET /view/{id} afterwards returns the stored filter objects, not {}

PUT is a full replace: any key you omit resets to its default. The rule that makes a view build safe is therefore read → merge → write, never a bare patch.

Also discovered:

  • Allowed filter operators: GT GTE LT LTE EQ NOT ANY ALL "NOT ANY" "NOT ALL" "IS SET" "NOT SET".
  • Allowed filter fields are native only — status priority dueDate dateCreated dateClosed dateDone assignee tag name description statusType timeEstimate timeLogged waiting_on watcher …. Custom fields cannot be filtered by this API, and their ids are rejected with the full allowed list.
  • Allowed grouping fields: subcategory assignee group priority status tag dueDate customItems none. Custom fields cannot be grouped either.
  • status NOT <value> is silently dropped for some Spaces; status ANY [values] is silently truncated in FLF, EXCO, MANCO, SNR EXCO (EXCO keeps 6 of 9 values, FLF 3 of 10). Worked around.
  • Formula fields: POST /list/{id}/field with type: formula rejects every field reference and even NOW() with 400 FIELD_600 Invalid formula; a literal CONCATENATE("a","b") is accepted. Field-referencing formulas exist only through the UI editor.

4. Formula fields — the API refuses, the UI accepts

POST /list/{id}/field → 400 FIELD_600 Invalid formula for field("First Response At"), {First Response At}, a bare field name, IF(...) in any shape, and NOW(). Literal formulas only.

The UI editor does work. Driven through Dia, on SLA - TLF:

Created field First Response Due — confirmed by the toast "Created field First Response Due" and by the list's Custom Fields list growing to 8 with First Response Due → Edit field.

The formula itself is not written, on purpose: First Response Due = created + tier response hours, and the hours table in §10.3 is marked in the spec as "a proposal for you and Jaques to set, not a policy I have invented". Writing numbers nobody has agreed is the one thing a setup pass must not do.

Decision needed (Ricardo): adopt the proposed windows — Platinum 1 h / 4 h, Gold 4 h / 1 business day, Silver 1 / 3 business days, Bronze (from service_tier = Black) 2 / 5 business days — or supply your own. Until then SLA State can be built against Due Date instead, which the spec already sanctions ("Until you set the hours, SLA State still works — it measures against Due Date").
