Four bounded questions went to the decision lane (cloud leg clef:cloud, route cloud-ollama:clef:cloud, logged in Agent-Output/adrianna/gates.csv):

The first yes was withdrawn on inspection, not acted on. office.py --office-stdio is the far end of a relay — its parent is the SSH session the relay opens and --seconds 240 bounds its life. It is not an unsupervised stray, and a unit would have double-served the inbox.

The MoA council did not run. council_deliberate fails on every call with too many values to unpack (expected 2, got 3) before reaching a model — a tool-bridge fault, not a preset fault (the preset is four ollama-cloud members with an empty judge, i.e. peer-review mode). The bounded questions were answered by the cloud decision model instead, and this report says so rather than implying a deliberation happened.

2. Applied

Connect framing is live. agenticos-frontend:1.92.0-unit-frame = the private-unit-count image plus patch.js (frame-ancestors = https://connect.infinitybrands.co.za, X-Frame-Options removed). Proven on the running container and on the wire: curl -sI http://127.0.0.1:3000/en → frame-ancestors https://connect.infinitybrands.co.za, zero x-frame-options, and the unit-count page still compiles.

Disk guard restored, with an incident. A guard already existed on this host (agenticos-disk-guard.service, one JSON line, 90 % threshold) and my first attempt overwrote its unit file. It is restored as ~/agenticos/ops/disk-guard.py with the same JSON contract (checked_at, path, used_percent, used_gb, free_gb, total_gb, threshold_percent, status), GiB units, 90 % threshold and 10-minute timer, plus one addition: above 90 % it runs docker builder prune -f and re-measures, because an 18.75 GB build cache is what took this disk to 100 % on 24 November. Latest: used 72.9 %, free 16.5 GB, status ok.

AI HUB - Agent Output is wired into every unit's knowledge. This was already in flight in another lane: departments.json carried the real output_folder ids for 15 routes and the sync module had a publish_output card. Working in the same files at the same time, my edit replaced that module and briefly broke run-all.sh (ImportError on publish_output). Their version was backed up in place, so the recovery was a restore of that file, and the whole job was then run end to end:

                   "verified indexed agent-output card in search"   (15 routes, exit 0)

Database confirmation: 13 workdrive-agent-output-* documents, every one status=done, 13 chunks. Two of the 15 routes are paused and correctly skipped. Each card names the unit's AI HUB subfolder, states that it sits inside the shared AI HUB - Agent Output tree and tells the agent to open it with the employee's own account — so retrieval answers "where does this unit's agent output live" and Zoho still enforces who may open it. The 03:05 nightly job re-verifies both cards per unit.

3. What this means for the rest of the estate

The card design the lane chose (second card per unit KB, not a shared org-wide KB) keeps every unit's output pointer inside its own private knowledge base, so one unit cannot see another's folder reference. The 15 route manifest already carries EXCO, MANCO and the units, so no agent needs an instruction edit — the pointer arrives through retrieval.
