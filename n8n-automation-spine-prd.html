PRD — n8n Automation Spine on the Mac mini

Owner: Ricardo Da Costa Maio · Author: Adrianna A (AI stack) · Date: 2026-11-28 Status: v1.2 — built and running on this Mac (§19); one launchd bootstrap command outstanding Target machine: Mac mini ricardos-mac-mini (M4 Pro, 24 GB, macOS 27.2.1) Reviews: MoA panel (§14) · Claude Code audit (§15) · Changelog (§18)

1. Summary

Install n8n 2.49.8 (self-hosted, Community, Sustainable Use Licence) natively on the Mac mini under a pinned Node 24 runtime and a launchd agent, wired to Ollama Cloud through the local Ollama daemon so every model call leaves on one credential, one account, one bill. Then turn the estate's deterministic work into three multi-purpose bots — Courage (the machine), Splinter (personal and home) and Bruce Wayne (work) — each one unit of ownership carrying five jobs, absorbing the 57 script-only cron jobs those lanes already run and triggering the 16 that need judgment. Between them the four profiles run 73 scheduled jobs today; the fleet is designed around that number, not beside it.

n8n is not a replacement for Hermes or Courage. It is the deterministic glue layer: schedules, webhooks, retries, approvals-in-principle and an execution log a human can read — the work that today lives in ad-hoc launchd scripts and one-off cron jobs, and the work that is silently missing when a bot dies.

What changed between v0.1 and this version (all three blockers came from the Claude audit): the build now starts with a disk-reclaim phase because the machine cannot pass its own install gate; the model ladder is gated on identifying which Ollama account the daemon bills; and the backup is encrypted and taken with sqlite3 .backup because the drive it lands on is USB and unencrypted.

What changed in v1.1 (Ricardo's review): the fleet is no longer seven single-purpose bots standing beside the existing work. It is three bots, one per lane, five jobs each, built on a measured inventory of the 73 Hermes cron jobs already running across Adrianna, Courage, Splinter and Bruce Wayne — 57 script-mode jobs absorbed, 16 agent-mode jobs triggered but not re-implemented. §7. Details in §15 and §18.

2. Goals and non-goals

Goals

  1. One always-on local automation service on http://127.0.0.1:5678, started at boot by launchd, independent of any agent session.
  2. All AI inside n8n routed through Ollama Cloud via http://127.0.0.1:11434/v1 — no second vendor, no second key, no silent substitution, no unattributed spend.
  3. Three bots carrying five jobs each, consolidated from the 73 cron jobs the four profiles run today; each producing high-signal, low-noise output into channels Ricardo already reads.
  4. Every standing rule enforced by something a reviewer can run — a lint, a credential that physically cannot write, a node that is absent — not by a prompt and not by discipline.
  5. A build a second agent can repeat from this document, with the verification commands in §11.

Non-goals (v1)

  • Not n8n Cloud, not queue mode, not multi-user, not a public webhook endpoint.
  • Not a replacement for Hermes agents, the MoA/council lane, or Beast's vault writing.
  • Not a client-facing workflow service — the Sustainable Use Licence permits internal business use only.
  • No Python Code nodes in v1 (n8n 2.x requires external task runners for native Python, §6.7).
  • No approvals that resume over a loopback URL (§15, A12) and no instance-level MCP (§15, A15).

What the constraints force

  • C2 is the binding constraint — and the build currently fails its own first gate. v0.1 required 8 GB free to install; the machine has 7.6 GB (Claude A2). The build therefore starts with a reclaim phase (§10, P-1), not an install.
  • C4 says no new VM. A second colima profile at 3–4 GiB on a machine already swapping 5.2 GB repeats a known failure mode.
  • C7 rules out the Docker lane for anything touching AI-Drive. A container cannot read/write the 220 GB of agent output without a colima restart that stops all 26 running containers — and it still could not launchctl, lsof or df the host, which is exactly what the health bot must do.
  • C3 means every backup is plaintext on removable media. The tarball carries the credential-encryption key, so it is encrypted before it leaves the machine (§8).
  • C10 means the cloud account is reachable from the LAN. Accepted with named controls (§16, R9, gate G8).
  • C12 means "survives reboot" is only true after someone logs in. Every boot test is stated that way (§10, P2 exit test), never claimed as unattended.

4. Architecture decision

4.1 Options considered

Option Shape Fit against the evidence
A. Native n8n, pinned Node 24, launchd brew node@24 (keg-only) → npm install n8n@2.49.8 into a private prefix → com.maio.n8n LaunchAgent ~400 MB RSS, no VM, direct 127.0.0.1:11434, host context for probes, rw access to /Volumes
B. Docker in the existing colima profile n8nio/n8n:2.49.8 beside 26 containers 6 GiB VM already saturated, /Volumes read-only (C7), host-invisible, images inside a VM disk on a volume with 7.6 GB free
C. Docker in a new dedicated colima profile second VM, 2–4 vCPU / 3 GiB / 20 GiB, Hiksemi mounted rw Clean isolation, but more swap pressure (C4), a sparse image against 7.6 GB free (C2), and still host-invisible

4.2 Decision

Option A — native, version-pinned, launchd-managed. Recorded as decision D-01. Adopted by the MoA panel independently (call M-1) and not contested by the audit.

  1. Host context is the product. C1, C2 and C3 are worthless if they cannot see launchctl, lsof, df and the launchd logs. Only a native process can.
  2. Filesystem continuity. W5 reads /Volumes/Hiksemi 1TB/AI-Drive; native sees it rw today, Docker cannot (C7).
  3. RAM. n8n idle is a few hundred MB; a new 3 GiB VM on a host swapping 5.2 GB is a regression felt in the MoA and council lanes within a day (C4).
  4. Disk. The freed headroom (P-1) goes further on a Node install than on images plus a VM disk (C2, C6).
  5. Latency. 127.0.0.1:11434 with no NAT hop, on the same route Hermes uses (C9).

4.3 Objections to the decision, and the answers

O1 — "n8n deprecates npm installs from 3.0; you are building on a dead lane." Accepted. Mitigations: pin the version (2.49.8) and brew pin node@24; keep ~/.n8n portable (SQLite file + encryption key, restorable into a container); stage a Compose file in the repo from day one; gate G3 re-evaluates Docker at 3.0 when the disk situation has changed. npm is deprecated for 3.0, not broken today.

O2 — "No container isolation; a compromised workflow owns the host." Partly true, and why §9 exists, now with the audit's corrections: bind to 127.0.0.1, a password-manager secret for the owner account, N8N_BLOCK_ENV_ACCESS_IN_NODE=true, ExecuteCommand/LocalFileTrigger off, file access restricted to Agent-Output only, task runners on, a publish-time lint (§9.8) and a launchd-level kill switch. Host facts arrive through a read-only probe script, so n8n needs no shell.

O3 — "A second Node runtime on a machine with Node 26 will confuse tooling." node@24 is brew keg-only (not linked into /opt/homebrew/bin), n8n gets its own prefix (~/AI Hub/n8n), and the LaunchAgent wrapper sets PATH explicitly. node -v stays 26 everywhere else.

O4 — "Why not queue mode / Postgres now?" Queue mode needs Redis and a second process for a single operator; Postgres costs ~150 MB RSS plus a service to babysit for tens of rows a minute. n8n 2.x's pooled SQLite driver (WAL) is the documented default. DB_TYPE is one env var and the migration tool is documented; gate G4 defines when we take it.

O5 — "The plan depends on a USB drive." (audit A4) Accepted and designed around: the DB, the logs and the binary data now live on the internal volume; only artefacts and encrypted backups go to Hiksemi. Nothing in the boot path touches the external drive.

Mount gate (adopted from MoA, M-2 as amended). Every workflow that touches the external volume starts with a shared mount-gate sub-workflow: exact path present, write test succeeds, else the run fails closed with one alert and writes nothing. 6.3 Credentials inside n8n

  1. OpenAI-compatible → Ollama — Type: OpenAI. Base URL http://127.0.0.1:11434/v1, API key the literal ollama (the local daemon ignores it). This is the route that supports tool calling — measured (C9).
  2. Ollama — Type: Ollama, Base URL http://127.0.0.1:11434, no key. For embeddings and plain LLM Chain nodes.
  3. Service credentials, scoped per workflow, read-only wherever the vendor offers a read-only token: Firefly gets an app password that is never used for writes; Gmail gets the narrowest scope that can still list and draft; HA gets a long-lived token; Discord/Cliq get webhook URLs stored as credentials, never as node parameters (audit A14).

No credential is ever pasted into a node parameter, a Code node, or a git-tracked file. Webhook URLs are secrets too, and are stored as credentials — the audit correctly pointed out that a URL in an HTTP node lands in every weekly export.

6.4 Model ladder — gated on the account (audit A1, BLOCKER)

The gate. Before any bot calls a model, P0 identifies which Ollama account the local daemon is signed into (Ricardo's own Pro/Max account, or the Infinity company account). The company key is restricted to deepseek-v4.1-flash and mimo-v2.6-flash; if the daemon bills that account, the ladder below narrows to those two tags plus local models, and S1 and the mail jobs are re-costed before they are built. This is gate G0 and it blocks P3.

Job Model (if the daemon bills Ricardo's account) Why
Classify / extract / route glm-5.3-flash:cloud Fleet default; tool-calling verified today
Draft / summarise deepseek-v4.1-flash:1017-cloud The chairman-grade writer, already the default model
Deep reasoning in an agent loop kimi-k3.1-pro:cloud Strongest long-context reasoning seat
Vision inkling-2-small The registered vision route
Embeddings nomic-embed-text (local) Zero cloud cost

Every tag in this table is a hypothesis to probe at P3 (one generation + one tool call each, MoA call M-15), not an assumption.

Fallback rule (rewritten after audit A10). The daemon answers /api/tags with 200 even while the cloud lane is 429-ing, so a health check on the daemon proves nothing. Degraded mode is therefore triggered by the model node's own error output (non-2xx, timeout, invalid tool JSON), not by a pre-check: bounded retries (2), then the deterministic template answer — raw values, no prose — plus one alert, execution tagged degraded-model. A daily call budget per bot stops the retry loop from burning the shared quota.

6.5 Agent vs chain

  • Basic LLM Chain for one-shot generation (digest prose, eight-line briefs).
  • AI Agent (tools) only where a lookup is needed: inbox triage, copilot. Agent runs are capped at maxIterations 6, one tool-call per item, and an explicit maxTokens per call with a per-execution counter (audit A24 — a token ceiling must exist as a number, not a hope).
  • MCP Client Tool only against read-only MCP servers. The OpenKnowledge server on :64200 exposes write/edit/delete and is never connected (audit A7).

6.6 Notification routes

Discord for stack-health lines; DM-locked Cliq for anything personal, financial or business; the kanban board for work items; AI-Drive for artefacts. Nothing posts to a public channel. Every route carries a source field so a message can be traced to an execution ID.

6.7 Python

v1 is JavaScript only. n8n 2.x removed the Pyodide Python node; native Python needs external task runners (n8nio/runners) — a container dependency we have argued against. Revisit with the 3.0 migration.

Plus 80 com.maio.* launchd labels, of which roughly twenty are periodic jobs (backup, firefly-backup, home-assistant-backup, courage-health, courage-backups, google-health, qmd-refresh, maio-os-refresh, top8-refresh, meta-reap, ram-guard, keep-awake-guard, mount-nas, hiksemi-recover, watchtower, deadman) and the rest are long-running servers, MCP endpoints and tunnels.

This changes the plan's shape. v1.0 proposed seven new bots standing beside 73 existing jobs — more surface without removing any. The right move is the opposite: absorb the script-only jobs into three bots organised by the lane that owns them, and leave the remaining work where it is.

7.1 The rule that decides what moves

  1. Script-mode jobs move (57 of 73): fixed input, fixed output, no language model in the loop. They gain an execution history, retries, one dashboard, dependency ordering and failure alerting they do not have now.
  2. Agent-mode jobs stay in Hermes (16 of 73) and, where their trigger is deterministic, n8n calls them through the Hermes API. A prompt that must reason is not re-implemented as an n8n graph — that is how you get a bot that looks automated and quietly stops thinking.
  3. launchd keeps servers and sub-5-minute guards. n8n does not duplicate a 1-minute guard, an MCP server or a tunnel; it watches their health instead. A scheduler with a 15-minute floor does not replace a 60-second loop.
  4. One bot is not one graph. A bot is a unit of ownership: one lane, one credential set, one channel, one error workflow, five jobs — but five separate workflows under one tag. Job 3 failing must never stop jobs 1, 2, 4 and 5, which is exactly what a single five-branch workflow would do.
  5. Migrate by pausing, never deleting. The Hermes cron job is paused the same day its n8n twin is published, then removed after a two-week shadow with identical output. Two live copies of one alert is a bug, not a safety net.

7.6 Shared infrastructure (not a bot, and not one of the five)

Mount gate · model fallback · idempotency with pending → done states · HTTP allowlist · audit ledger · publish-time lint · error workflow · kill switch per bot. Every job calls these; none of them is a job.

Every bot also gets one deadman outside n8n (launchd + curl /healthz), because a scheduler that dies silently is worse than no scheduler: it looks like calm.

8. Data, state, retention and backup

  • Store: SQLite pooling driver (2.x default, WAL). Single writer, read pool. No Postgres in v1.
  • Retention: prune by age (14 days) as the binding rule; the row count is a secondary guard set to 0 (off) until measured, because sub-workflow executions multiply the count (audit A8). Success payloads stop being saved after the 14-day tuning window, replaced by the JSONL ledger.
  • Audit ledger: append-only JSONL outside the DB — execution ID, workflow ID + version, dedupe key, model tag, tool calls, action status, artefact reference. No payloads, no secrets.
  • Backup (rewritten after audit A3/A5):
    1. sqlite3 "$DB" ".backup '/tmp/n8n-backup/db.sqlite'" — never tar a live WAL database.
    2. Collect .n8n/config (the encryption key), manifest.json (versions, plist hash), and the JSONL ledger.
    3. tar → age-encrypt to a public key whose identity lives in the login Keychain → write to /Volumes/Hiksemi 1TB/AI-Drive/Backups/n8n/ — outside the file-access root, so no workflow can read it.
    4. Keep 14. Log every run with size + hash.
  • Restore drill (monthly): decrypt to a scratch dir, PRAGMA integrity_check, then boot n8n on port 5680 against the restored data and decrypt one credential through the UI (audit A5: an integrity check does not prove the key works). Recovery objective: 30 minutes, measured in the drill.

Additional operational guardrails:

  1. Idempotency (audit A18). Keys are per object, not per window (W5: file path + hash; S2/W2: message ID + thread). A key is written in state pending and moved to done only after the output succeeds, so a failed send retries and a successful one never duplicates.
  2. Loop and cost caps. maxIterations 6, explicit maxTokens per call, per-run item caps (S2/W2: 40 messages/run), a daily call budget per bot, and retries capped at 2.
  3. Alert hygiene. State-change only; 2 consecutive misses = down (one number everywhere — audit A20); one digest per 4 h at most.
  4. Kill switch. bin/n8n-panic.sh → launchctl bootout gui/$UID/com.maio.n8n, timestamp, one Cliq line. Resume is the mirror. The drill asserts the service is gone within 45 s — longer than the 30 s graceful shutdown, which v0.1 contradicted (audit A20). Soft stop is Publish/Unpublish in 2.x.
  5. Audit. 14 days of executions in the UI, the JSONL ledger indefinitely, and C2 surfacing failed executions rather than leaving them to be discovered.
  6. Egress, honestly stated. n8n itself has no firewall; a determined workflow could call any host. v1 compensates with credentials that cannot write money, a publish-time lint, and no ExecuteCommand. A pf egress allowlist is listed as future hardening, not claimed as present (audit A6).
  7. Credential store — the one approved exception. n8n keeps credentials encrypted in SQLite, unlocked by the key in ~/.n8n/config (0600). That is n8n's own config, and the only place a service credential may live. The consequences are accepted in writing: the backup is encrypted before it leaves the machine, the key never appears outside that archive, and a restore onto a machine we do not own is forbidden.

19.3 Deviations from this PRD, and why

  1. Alerts go to Discord, not Cliq. The stack's ZOHO_MCP_CLIQ_URL answers HTTP 400 for a bot-style {"text": …} body, so the relay delivers to the Discord home channel first and keeps Cliq as a fallback. Nothing personal or financial is posted there; that rule stands for when a working Cliq DM route exists.
  2. No Hermes cron was paused. §7.1 rule 5 says pause the twin the day its replacement publishes — but the n8n twins are not yet identical (the DNS check, the ollama model battery and the Hiksemi real-read test do more than C1–C5 do). Pausing now would leave a coverage hole, so the estate runs in shadow until the twins match for 14 days. This is the safe reading of the rule, not a skip of it.
  3. C3/C4/S5 read the probe through a local HTTP endpoint (notifyd /probe) rather than n8n's file node: the file node's output shape could not be verified without the UI, and a bot that cannot parse its input must not guess. The guard now emits probe-unreadable instead of a plausible-looking number (observed working).
  4. The deadman and the probe were wrong twice before they were right — a pgrep that matched nothing said "process down" while healthz was 200, and a one-shot failed touch reported the drive read-only. Both are fixed (port-based check, three-attempt write test with retries) and both false alarms are in the ledger.
  5. C4's log-rotation check is optional, not required: a missing rotation file is normal on a fresh boot, so only the vault-index age can raise the maintenance warning.
