0. What the two reviews changed

Two independent reviews ran against v0.1. Claude returned 19 findings; the MoA panel returned a structural verdict. Where they agreed, I changed the plan; where only one spoke, §13 records the call.

The four changes that matter:

  1. The licence gate is real and it is first. PolyForm Noncommercial 1.0.0 does not cover evaluating the tool for company work, so "install it for a week and see" is not an available option. Either Ricardo buys a licence, or the install is personal-only and the roster is cut to match.
  2. Bots are job packs, not single tasks — and they ship in stages. v0.1 gave each bot one job (Claude cut the roster to four, MoA to one). Ricardo's correction is the shape that fits this machine: each bot carries five jobs, so four bots cover twenty (FR-4). Fewer agents means fewer permission surfaces; breadth lives in the instruction file, not in extra bots. The four still arrive on a schedule — Canary first, one bot per week after that — because a bot with five jobs is a bigger thing to prove than a bot with one.
  3. OpenBot gets no scheduler and no clock. Routines are Hermes cron entries calling openbot-cli. That removes the "missed run because the app was closed" class of failure and keeps one clock on the machine.
  4. Permissions are fail-closed, and drift is checked. The product default is full local access; agents created by an update, a restore or a careless click would inherit it. So the permission mode is pinned in a policy file with a config hash, re-verified before launch, after every update, and daily.

Two claims from v0.1 were wrong and are corrected: the dmg's notarisation was asserted rather than verified, and "workspace-only" was treated as a read barrier when it is a write barrier.

1. What OpenBot is, precisely

OpenBot (openbot.run, source github.com/nightly-labs/openbot, latest v0.81.0, published 2026-11-27) is a local-first Electron workspace for persistent AI teammates: per-agent workspace, conversation, FIFO queue, embedded browser, agent-to-agent messages, routines, MCP connectors, and an optional bundled cua-driver for computer use.

On the lane this PRD uses, OpenBot is the agent runtime — it runs the agent loop, the tool runner, the permission model and the approval cards. It is only "a window" on lanes where it shells out to another harness (Hermes over ACP, Claude Code, Codex, OpenCode). That distinction is why §8 exists: on our default lane the safety of this machine is OpenBot's permission model plus what we configure — not somebody else's sandbox.

3. Goals and non-goals

Goals

  1. One OpenBot install, current release, verified, with zero new vendor keys.
  2. Every bot model resolves through http://127.0.0.1:11434/v1 — the same route the fleet uses.
  3. A go/no-go Canary that must pass before any real bot exists.
  4. Four bots of five jobs each, staged: Canary first, then one bot per week on evidence (FR-4).
  5. Routines owned by Hermes cron, calling bots through openbot-cli.
  6. A bridge so any Hermes session can hand work to a bot and get JSON back, including "a human is needed".
  7. Nothing in Ricardo's money, legal, vault-write, secret or notification surfaces reachable by a bot.

Non-goals (v1)

  • Replacing any Hermes profile, cron or channel. Hermes owns cron, kanban, channels, the vault and the gates. OpenBot owns no owner-facing channel and no scheduler.
  • OpenBot's Multiplayer/Teams, iPhone pairing, hosted servers, Docker, remote desktop.
  • Computer Use. Not because our Cua grant "owns" the OS (TCC grants are per-application, so OpenBot would get its own) but because a second computer-use daemon on one desktop doubles the cursor, doubles the grant surface and has no v1 job. Revisit on a dedicated macOS user, never on this account by accident.
  • The Hermes-over-ACP provider lane. A bot on hermes acp would put bot turns on the live fleet's profile, session DB and memory. If ever wanted, it gets a dedicated openbot Hermes profile first.
  • MCP servers. No zoho-api, no google-workspace, no comfyui server in v1: each brings its own OAuth tokens or credit-spending tools, and none is in the standing fleet list. Bots use the shell and the CLIs the fleet already owns.
  • Any commercial or staff-facing use before G1 is settled.

5. Functional requirements

FR-1 Install, pin, verify

  • Download v0.81.0 arm64 dmg to the external volume, verify SHA-256 against SHA256SUMS-macos.txt (exact-name match, not a substring), mount at a fixed mountpoint, copy to /Applications.
  • Prove the signature rather than assume it: 
    codesign --verify --deep --strict /Applications/OpenBot.app
spctl -a -vvv /Applications/OpenBot.app      # expect: source=Notarized Developer ID
    If spctl rejects it, stop. Do not strip the quarantine flag to get past a security decision.
  • Pin: record CFBundleShortVersionString and the release tag in openbot-version.lock. Manual update checks only for two weeks; after that, deliberate updates with a 3-turn smoke test afterwards.
  • No OpenBot account sign-in. Launch at login: off. Notifications: off. Computer Use: off.

FR-2 Model route

  • Settings → Providers → custom OpenAI-compatible endpoint:

    • name Ollama Cloud, base URL http://127.0.0.1:11434/v1
    • key: the literal ollama — a sentinel, not a credential. The daemon is already authenticated; this field must never hold OLLAMA_API_KEY.
    • model list entered explicitly: discovery also lists the 13 local tags, two of which (d3-flash-mlx, clef-flash) are decision-only models that reject generation.

  • Allowlist (all six measured at ~1M context, tools + vision):

    Model id Role
    glm-5.3-flash:cloud default workhorse
    glm-5.3:cloud reasoning / planning
    kimi-k3.1-pro:cloud long-form writing
    deepseek-v4.1-flash:1017-cloud synthesis, comparison
    minimax-m3.1-flash:cloud bulk / cheap
    inkling-2-small:cloud vision

  • Backup chain per bot: primary → glm-5.3-flash:cloud → minimax-m3.1-flash:cloud, never repeating the primary. Known limit: the whole chain is one daemon and one account, so a lapsed sign-in or a daemon restart takes all three down together. Accepted; the mitigation is the liveness check in FR-5, not a second vendor.

  • Bind the daemon to loopback only after confirming nothing on the LAN consumes it. The probe shows no remote peer, but the MacBook Air pairing must be checked before OLLAMA_HOST=127.0.0.1 is written. If any LAN consumer exists, leave the bind and record why.

FR-3 Permissions are fail-closed and drift-checked [new in v1.1]

The product default is full local access with no per-action approval. Every bot is created in Workspace only, and that configuration is pinned in Agent-Output/openbot/permission_policy.md:

app_default        = workspace_only
per_agent_default  = workspace_only
full_access_allowed= false
computer_use       = off
openbot_tcc_grants = none
vault_mount        = none
workspace_root     = /Volumes/Hiksemi 1TB/AI-Drive/Agent-Output/openbot
drift_check        = before_launch, after_update, daily
escape_test        = must_fail

drift_check is a three-line habit, not a tool: before launching, after every update, and once a day, read each bot's permission mode in the app and compare it with the policy file. Any bot not workspace_only → stop and fix before it takes a turn. This is the control that survives an app update silently re-creating an agent with defaults.

FR-4 Roster — staged

Instruction files live in Agent-Output/openbot/bots/<bot>/INSTRUCTIONS.md and are pasted verbatim, so the roster is reviewable as plain text and rebuildable by hand. Each bot's workspace carries a single OWNER_RULES.md — the authority the instructions point to — rather than the rules being retyped in four prompts.

Stage Bot Its five jobs Model Permission Ships when
0 Canary Runs the §10 canary script and the escape probe. Not a worker; it never talks to Ricardo glm-5.3-flash:cloud Workspace only first, before any other bot
1 Quill ① PRD/spec · ② report or audit write-up · ③ one-page HTML explainer · ④ notes → decisions and action items · ⑤ publish + vault handoff kimi-k3.1-pro:cloud Workspace only Canary passes
2 Post ① inbox triage · ② draft replies (never sent) · ③ meeting notes → action items · ④ follow-up tracker · ⑤ contact dossier glm-5.3-flash:cloud Workspace only A8 escape canary passes; company mail needs G1-B
3 Bench ① model comparison · ② weekly fleet digest · ③ product/price/spec research · ④ second opinion on a document · ⑤ decision ballot deepseek-v4.1-flash:1017-cloud Workspace only Quill clean 7 days
4 Studio ① stills · ② clip from a brief · ③ fix an existing asset · ④ look-and-report (vision QA) · ⑤ asset pack + manifest glm-5.3:cloud + inkling-2-small:cloud Workspace only Bench clean 7 days

What a job pack changes, and what it must not. Each instruction file opens with a job router: decide which of the five jobs this is; if it is genuinely ambiguous, ask once. The jobs differ in method, never in privilege — every bot has the same workspace, the same OWNER_RULES.md, and the same workspace-only permission. That is deliberate: breadth inside one bot is a writing problem, while breadth across bots would be a permission problem. Every job card also carries its own "never" line, so a mail bot does not borrow the latitude of a media bot.

Why the order. Canary proves the lane and the sandbox. Quill is file-in/file-out — the least privileged useful bot. Post is the highest volume of real work and goes second, once the escape canary has proven a bot cannot read outside its workspace. Bench needs no shell beyond its own calls, and Studio needs shell plus a media path, so they follow.

Cut outright (and why they are not coming back):

  • Desk (intake router) duplicates routing the Hermes roster already owns, has no tools, and its output would land in a chat Ricardo does not monitor.
  • Watch (machine health) cannot be trusted: a monitor must not depend on the thing it monitors, and a workspace-only shell cannot read process, launchd or TCC state. Host health stays in the Hermes/launchd check with the thresholds in §7.
  • Board (kanban) would be a second writer to a board Hermes owns. Reconsider only as a read-only summariser on the hermes kanban CLI, after G1-B.

FR-5 Routines — owned by Hermes, not by OpenBot

OpenBot's scheduler only fires while the app is running and has no notion of a missed run. So the bot-side scheduler stays empty; the routines are Hermes cron entries (com.maio.openbot-*), added only after the Canary passes and after three manual dry runs have been read:

Routine Fires Calls Expected silence
openbot-quill-morning 07:30 Mon–Fri openbot-run quill "<today's brief>" quiet unless a document is due
openbot-bench-weekly Sun 09:00 openbot-run bench "<week's question>" always a table — it is a report, not a notification

A bot with nothing to say answers with the single token [[no-update]]; Hermes treats that as "no message for Ricardo". This reuses the fleet's existing silent-run convention instead of inventing a second one. A failed run never goes silent: exit 1 or 3 reaches the gate.

FR-6 Fleet bridge

  • Enable Local scripts on each bot at creation (per-agent, off by default, and an agent cannot switch it on for itself).

  • ~/AI Hub/bin/openbot-run wraps node /Applications/OpenBot.app/Contents/Resources/cli/openbot-cli.mjs run <bot> - --wait --json, reads ~/Library/Application Support/OpenBot/automation/{url,headers} at call time, and maps exit codes:

    Exit Meaning What the wrapper does
    0 turn completed print the JSON answer
    1 failed / refused / unknown delivery fail loudly, quote the error
    3 a person is needed open a kanban block card in plain English
    4 wait timed out (work continues) report "still running", never "done"
    5 OpenBot not running / no Local scripts / bot missing fail with that exact sentence

  • Rate limit stays 30 requests/hour/bot. A 429 is reported, never retried in a loop.

  • The automation token never enters a prompt, a log, a report or a git tree.

  • Add a daemon liveness check to the fleet heartbeat: curl -sf -m 5 http://127.0.0.1:11434/api/version and POST /api/me — one lapsed sign-in otherwise kills every bot model at once.

FR-7 Naming, silence, non-duplication

  • No bot name may collide with a fleet profile: no Adrianna, Beast, Courage, Scribe, Batman. Hence Quill. A reserved_names.txt generated from ~/.hermes/profiles is checked before each bot is created.
  • OpenBot's notifications, dock badges and sounds are off. Output reaches Ricardo through Hermes or not at all; the bot chats are a workbench, not a channel.
  • Nothing in OpenBot writes the vault. Quill's output ends at publish-document, whose handoff card Beast files.
  • Studio may call only the local ComfyUI tools (comfy_generate, comfy_img2img, comfy_upscale, comfy_status, comfy_outputs). Any comfy_cloud_* tool spends real credits and is excluded.

8. Governance gates

G1 — money/legal — blocks the download.

  • A. Personal / noncommercial. Free. Post reads personal mail only; Quill writes personal documents only; Studio and Bench are tools, not company output. No Infinity Brands deliverable, no staff-facing work.
  • B. Commercial. Buy the licence in Settings → Billing (Starter, 1 seat, or Team, 2–25) before any company work; the price is shown in-app and Ricardo signs.
  • There is no defer option. PolyForm Noncommercial forbids use "with any anticipated commercial application", so "evaluate it on company work for a week" is exactly what the licence does not grant.

G2 — routing — Adrianna decides. OpenBot sits in the AI-stack family. Work → Bruce Wayne, personal → Splinter, stack → Adrianna A. A bot is a tool those seats use, not a seat.

G3 — memory — before retaining. No bot receives health, financial or identity detail. Bot memory is per-bot and local; anything worth keeping goes to a skill or a vault note through Beast.

G4 — escalation. OpenBot chat is not a channel Ricardo monitors. A bot that needs a decision stops and files a card (exit 3 → plain-English block).

G5 — capability gate. Any change that widens a bot — full access, a new MCP connector, Computer Use, the Hermes lane, one more bot — is Ricardo's decision, recorded with the evidence that justified it.

13.3 Ricardo's correction — one bot, many jobs

Review after v1.1, from the owner: bots should cover many functions, not one. Adopted, and it improves the plan. A single-job bot needs its own profile, workspace, permission set and canary run to do what one job card inside an existing bot does — the reviews' objection to a big roster was really an objection to many permission surfaces, and a job pack removes most of them. The roster keeps four working bots and the job count goes from 4 to 20; the staging schedule stays, because five jobs is a bigger thing to prove than one. The measure added to §11 is the test of whether the packs earn their keep: a bot that only ever uses one of its five jobs should be merged.

13.4 Rejected outright

  • Cutting to a single bot permanently. Both reviews lean this way; it would leave OpenBot as a curiosity rather than a workspace Ricardo opens. The staging schedule gets the safety they asked for without throwing the product away — and each stage has an exit test.
  • Adding a Hermes ACP profile in v1. Nothing in v1 needs it, and it is the one change that could put bot turns on the live fleet's session database.
