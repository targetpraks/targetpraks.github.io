BU bot tooling — ClickUp bindings for the thirteen departmental bots

Why this PRD

The work platform has thirteen departmental bots and four shared report bots, and seventeen of the twenty-two published agents cannot call a single tool. They can talk; they cannot file a task, read a list, or look up a colleague. The only agents with tools are the two admin agents (Batman, Superman) and three platform agents.

ClickUp is already connected and healthy — the official ClickUp server at https://mcp.clickup.com/mcp, OAuth, last check ok, 67 tools. It is bound to Batman and Superman with approval: writes and no tool narrowing at all.

So the gap is not a missing integration. It is that nothing is bound, and that where it is bound the whole surface is exposed. This PRD closes both: bind ClickUp to the bot that owns each business unit, and cut each binding down to the tools that unit's work actually needs.

Product in five lines

  1. Every departmental bot files and reads work in ClickUp — in its own list, with its own tools.
  2. No bot gets a delete tool, a chat-delete tool, or a bulk mutation. Ever.
  3. Writes stay human-approved: approval: writes holds every mutating call for a person to click.
  4. The narrowing is expressed twice — an administrator ceiling on the connection, a per-bot allowlist on the binding — and the platform intersects them.
  5. One shared ClickUp credential today; per-unit narrowing is enforced by allowlists, not by separate credentials, until the BU groups have members.

How narrowing actually works here

Read from the running code, not assumed:

  • A binding carries allowed_tools, a list of the server's own tool names — clickup_create_task, not a prefixed name (presented_tool_names, app/services/mcp_connection.py:3509).
  • The connection carries its own allowed_tools, and the platform intersects the two: the connection's list is an administrator ceiling, the binding's is the agent's own limit. A tool excluded at the connection can never be reached by a binding that still names it (_narrowed_tools, mcp_connection.py:3536).
  • null on either side means "no narrowing from here". Both null = every tool the server offers.
  • approval: writes holds every call that changes something for a human approval; read-only tools run automatically under that policy (app/schemas/agent.py:883).
  • Publish refuses a binding whose presented tool names collide with the agent's other tools — the run would abort, so the platform stops it at publish (app/services/agent_registry.py:3048-3060).

That is the whole mechanism. No new code is needed to enforce per-bot limits; only the lists.

The binding design

Two tiers per bot, plus a hard exclusion list.

Tier Contents Approval
Read list/folder/task read, comments read, member lookup, custom fields runs freely
Write create task, create task comment, create/update reminder held for human approval
Never every delete, every chat delete/update, tag removal, folder/space creation, document page mutation absent from the allowlist

Binding shape, one per bot, added to its draft_spec.mcp_servers:

{
  "account": "organization",
  "connection_id": "391a67f7-ab74-4a90-8496-1549dd2ef72c",
  "approval": "writes",
  "allowed_tools": [
    "clickup_get_list",
    "clickup_get_task_comments",
    "clickup_find_member_by_name",
    "clickup_create_task",
    "clickup_create_task_comment"
  ]
}

account is free text used as the binding's label; the connection is resolved by connection_id, and the platform only resolves org-scoped rows for a published agent (get_org_scoped_by_ids).

Acceptance criteria

  1. select name, draft_spec->'mcp_servers' from agents where name in (...13...) shows a ClickUp binding with a non-null allowed_tools on all thirteen bots.
  2. A publish of each bot succeeds — no prefix-collision refusal in the platform log (E6).
  3. Running a departmental bot, ask it to delete a ClickUp comment. It must answer that it cannot: the tool is not in its toolset. Evidence: the run's tool list, not the bot's prose.
  4. Ask the same bot to file a task. The call must park for approval before anything is written to ClickUp, and only complete after a human approves it.
  5. ClickUp connection last_tools still reports 67 — binding changes must not alter the connection.
  6. used_by for the ClickUp connection lists the thirteen bots plus the pre-existing two.
  7. A non-admin member (role builder) cannot see the connection in MCP servers unless a grant is added — the connection stays private.

Failure modes

Failure Detection Response
Tool name typo in an allowlist Publish refuses on prefix/collision check, or the tool silently absent Verify against last_tools before publish; acceptance 3 catches it
A bot cannot file because ClickUp OAuth expires last_status != ok, last_error set Reconnect the org connection; do not add a second credential
Approval fatigue — every task parks Monitoring shows a queue That is the policy working; widen approval only with a separate decision
ClickUp changes a tool name last_tools diff on the 6-hourly check Update allowlists; add a check that allowlist entries are a subset of last_tools

Security, permissions, audit

  • The credential stays one org-scoped OAuth connection owned by Ricardo; nobody gains a new secret.
  • mcp:manage is ALL for owner/admin and SHARED for builder — a builder reaches this connection only if a grant names them or their group (list_for_org, mcp_connection.py:2362).
  • Every tool call is recorded against the connection; recent_calls exposes tool name and who ran it, never arguments or results.
  • No delete tool is bound, so no delete can be approved by mistake.

Build order

  1. Dump all 67 ClickUp tools and classify into read / write / never. Gate: Ricardo reviews the table.

  3. Bind and publish the thirteen bots, one business unit at a time, running acceptance 3 and 4 on the first.
  4. Bind the four report bots (read-only) and DOC Bot.
  5. Decide separately on Batman/Superman narrowing.
