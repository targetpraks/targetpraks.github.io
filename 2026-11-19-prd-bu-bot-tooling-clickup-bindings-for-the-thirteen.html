BU bot tooling — ClickUp bindings for the thirteen departmental bots

What v1.1 changes

An external review rejected v1.0 as not-ready on four counts. Each is corrected here rather than argued with.

  1. The premise was false. v1.0 said seventeen bots "cannot call a single tool". They cannot reach ClickUp; they do have native capabilities — FIN 11, HRM 12, SAL 13, DASH 13, DOC 25 enabled. The claim is narrowed to what is true: seventeen agents have zero MCP server bindings.
  2. Allowlists do not isolate business units. They narrow which tools exist, not which records those tools reach. v1.0 implied a bot could be limited to "its own list". It cannot. That is now decision D1, stated plainly, with two options and a recommendation.
  3. A connection-level ceiling would silently change Batman and Superman before their own approval. That step is removed; the admin pair is untouched by this PRD and gets its own reviewed change.
  4. The tiers contradicted each other — document-page creation sat in "Never" yet was granted to DOC Bot; report bots were read-only yet offered writes. All 67 ClickUp tools are classified in Appendix A, and every unresolved tool defaults to excluded.

Two smaller corrections: the org has three org-scoped connections, not four (the fourth is a personal-scope row with a null organization id), and ClickUp health is a scheduled sweep, not the six-hourly check v1.0 claimed — the exact cadence is confirmed at build time (AC10).

Why this PRD

Thirteen departmental bots and four shared report bots have no connection to any business system. They answer from knowledge and instructions; they cannot file a task, read a list or look up a colleague.

ClickUp is already connected and healthy: the official server at https://mcp.clickup.com/mcp, OAuth, last_status = ok, 67 tools. It is bound to Batman and Superman with approval: writes and no tool narrowing.

So the gap is not an integration. It is that nothing is bound, and where it is bound the whole surface is exposed.

Product in five lines

  1. Every departmental bot files and reads work in ClickUp, with a tool list it was explicitly given.
  2. Writes stay human-approved: approval: writes holds every mutating call for a person.
  3. No bot in this rollout gets a ClickUp delete, merge or opaque-operator tool. (Other capabilities — the platform toolset Batman and Superman already hold — are outside this PRD's scope.)
  4. These limits bound capability, and a server-side mapping bounds data — a bot reaches only the lists and tasks its business unit owns, checked before dispatch (decision D1 = B, v1.3).
  5. Batman and Superman are not touched here; their narrowing is a separate, separately approved change.

What this design can and cannot enforce

Enforced — which tools a bot can call. allowed_tools filters the toolset the model sees; a tool absent from it cannot be called, approved or dispatched.

Not enforced — which ClickUp records a permitted tool reaches. create_task takes a list_id string, get_task takes a task_id, neither checked against a business unit. Any bot allowed to read ClickUp reads the whole workspace the OAuth connection sees. Connection grants control who may discover or bind the credential; they do not constrain resource ids at run time.

Not enforced either — who a run acts for. A published private agent that a builder can run lends them its credential, and agents:run is ALL for builders (E6).

That is the provider's shape, not a defect this PRD introduces. The PRD's job is to say so out loud.

D1 — the data-scope decision: B, decided in v1.3

Decided: Option B — enforce a BU → list/task mapping, fail-closed, before provider dispatch. Basis: the LLM council (four seats, unanimous ranking) against the local decision model. The council's argument, paraphrased honestly: A is not a control, it is a documented acceptance of exposure, and it compounds — workflows, summaries, logs and embeddings form around workspace-wide visibility and become impossible to narrow later; C is the seductive trap because restricting writes while leaving reads open does nothing for confidentiality; B can be widened cheaply, while A and C cannot be narrowed retroactively.

Option Ruling
A. Workspace-wide access Rejected. Cheap but structural and back-loaded; the first time a Finance bot summarises HR the platform loses its credibility.
B. Enforced BU → list/task mapping Chosen, with the seven commitments below.
C. Hybrid (wide reads, mapped writes) Rejected. Fails the confidentiality test while creating a misleading "restricted" paper trail.

B is only a boundary if it is built as one:

  1. One enforcement chokepoint before provider dispatch, deny-by-default, fail-closed. Per-bot middleware is a convention, not a boundary.
  2. Server-established bot identity bound to the request before authorisation.
  3. Mapping derived from ClickUp structure where possible (space/folder/list ownership per BU), synced, with alerts for unmapped lists and explicit handling for cross-BU projects. Never a hand-curated file that silently drifts.
  4. Deny unknown, moved or unmapped objects; disable broad endpoints that cannot be mediated reliably.
  5. Tests beyond cross-BU denial: reads, writes, search, enumeration, subtasks, comments, attachments, caller-supplied ids and indirect references, plus positive authorisation tests.
  6. Provision the BU groups before production — joiner/mover/leaver and list migration are the long pole, not the middleware.
  7. Explicit extra grants — thirteen bots across twelve BUs; not every bot maps to exactly one BU.

Interim rule: no bot runs against the real workspace before its mapping exists. Pilots run on an isolated workspace, and bots are enabled one at a time as their mapping is populated.

The binding

{
  "account": "organization",
  "connection_id": "391a67f7-ab74-4a90-8496-1549dd2ef72c",
  "approval": "writes",
  "allowed_tools": ["clickup_get_list", "clickup_create_task"]
}

account is the binding's discriminator — platform, organization or personal — resolved as a typed reference (PlatformMcpServerRef, OrgMcpServerRef, PersonalMcpServerRef), not as a label. allowed_tools holds the server's own tool names. The connection's own allowed_tools is an administrator ceiling and the two lists are intersected (_narrowed_tools, app/services/mcp_connection.py:3536).

Approval semantics

  • approval: writes holds calls that change something for a human approval; read-only tools run automatically (app/schemas/agent.py:883).
  • The platform may treat a tool as read-only from the server's readOnlyHint. trust_read_only_hints is passed false in this deployment's isolation metadata and does not alter approval behaviour, so a vendor that mislabels a mutating tool would have it run unapproved. Mitigation: freeze tool_approval with an explicit required on every write-tier tool, so the guarantee does not rest on a vendor hint.
  • Unattended runs (schedules, channels, triggers) have nobody to approve. A scheduled bot that reaches a write must fail that step with a clear "needs approval" outcome — not hang, not silently skip (AC9).

Each is checkable with scripts/sql.sh and scripts/app.sh. Anything needing a live ClickUp write runs against an isolated list or a fake MCP server, never production.

Security, permissions, audit

  • One org-scoped OAuth credential, owned by Ricardo; no new secret anywhere.
  • mcp:manage is ALL for owner/admin, SHARED for builder — a builder reaches the connection only via a grant, but agents:run is ALL for builders (E6): a builder who may run a published bot uses its credential. That is a lending boundary, not a data boundary; Option B is what changes it.
  • Every call is recorded against the connection. recent_calls returns agent identity and run id, not a human actor, and it hides arguments and results in that view only — the underlying tool_calls rows retain them. recent_calls is not a storage guarantee.
  • No delete, merge or operator tool is bound, so none can be approved by mistake.

Deployment contract

  • List map: one versioned file mapping each bot to the ClickUp list ids it is expected to use. Published as the record of intent even under Option A.
  • Artifact: the approved allowlist per bot and its explicit tool_approval overrides (every write-tier tool marked required) are committed as one versioned table; published agents are compared against it, not against memory.
  • Rollback: revert the agent to its previous published version. Rolling back does not silently restore a tool removed for being dangerous — that is a deliberate second decision.
  • Retry/idempotency: an approval timeout is retried by the operator, not automatically. A dispatch whose outcome is unknown (timeout after send, connection dropped) is recorded as outcome_unknown and the bot is told so; before any second attempt the provider is searched for the expected task by title, list and creation window, and a match is adopted rather than duplicated. If the search is inconclusive the operator decides — the lane never retries blind.
  • Health ownership: named owner for the ClickUp health alert; sweep cadence recorded at build time (D7).
