How a plugin lands in DSH

A plugin is a package that declares dsh.bundle.patch. It becomes a layer in one profile — an ordered stack of bundles plus your own patch file. dsh plugin forwards to pnpm, so npm names, git URLs and tarballs all work. Nothing is live until you restart the surface: the web app and the desktop app load their plugin tree at boot.

Install to one profile

dsh plugin --profile web add <package> then restart dsh web. Never install into desktop from the CLI — the app owns that profile; use its Plugins panel.

Respect the version gate

A plugin whose engines.dsh misses your build is refused, not silently broken. Pin the version that matches 0.2.2-rc.5 instead of taking @latest.

Prove it composed

dsh --profile web --dump-config | grep <plugin-id>. A YAML error echoes the file back, so validate by exit code, never by grepping for the name.

Budget the prompt

Every enabled plugin adds tool schemas to every request. Two big MCP servers can cost more context than your actual work — that is why the efficiency pillar exists.

How this list was built

  1. Read the shipped catalogue from the installed harness itself — dsh-official-bundles (16 optional bundles, 2 on-demand subagent bundles) and the locale titles/descriptions of each — so the official lane is exact, not remembered.
  2. Pulled the live community index (7,073 plugins) and the curated awesome list (23 categories), then searched GitHub directly for real repositories and star counts rather than trusting index claims.
  3. Dropped anything that failed verification: three shortlisted repos now 404, one plugin superseded by a built-in feature (dsh-at-file → native @file references), one mobile client with no installable bundle.
  4. For each finalist: repository metadata (stars, last push, archive flag, licence), root package.json dsh.bundle presence, npm version and engines.dsh compatibility with 0.2.2-rc.5, and the install command read from the project's own README.
  5. Ranked inside each pillar by adoption × fit × maintenance. Star counts are the GitHub API's own numbers for 2026-11-28; they measure attention, not safety.

The one rule that matters: a plugin is third-party code with your credentials in reach. Install one at a time, restart, and read its source link before you trust it with an unattended profile.
