Persistent bots for work — QwenPaw vs dsh

Checked: Courage · 2026-11-09 · read-only survey (no installs, no config edits) Question: which of the two is better at persistent bots for work — named agents that keep their own identity, memory, skills, schedule and inbound channel.

Verdict: QwenPaw, and not narrowly. It is the only one of the two with a real bot object: one workspace per agent, with its own channels, memory, cron jobs, persona and skills. dsh is the better environment, but its agents are children of a session — they die with it and remember nothing.

What each actually offers for work

QwenPaw

  • qwenpaw agents create --name "Research Bot" --agent-id research_bot — creates the config and the workspace.
  • qwenpaw agents chat --from-agent bot_a --to-agent bot_b --text "…" — bots talk to each other directly.
  • qwenpaw agents list — the roster. Per-agent model, per-agent cron, per-agent memory.
  • qwenpaw hub — a multi-user control plane (admin bootstrap, loopback by default) if several people share the bots.
  • Console at 127.0.0.1:8088 to manage all of it visually; qwenpaw daemon status|restart|reload-config.

dsh

  • dsh --profile <name> — a persistent configuration, not a persistent agent: profiles are ordered plugin patch layers you can compose per job.
  • Subagents are genuinely good workhorses within a run: named, per-subagent model, send_message / wait_agent / interrupt_agent, Team mode with a shared task board, worktrees, LSP, sandbox, approvals.
  • Scheduled tasks re-enter a chosen session, so a recurring job can keep continuity — but there is no persona or memory to continue with, and nothing to message it from a phone.

Where each one breaks

  • QwenPaw is the youngest of the harnesses surveyed (repo created 2026-02-24, current line 2.3.0-beta.3), its Console is the real control surface, and on this Mac there is no runtime at all — only the CLI in ~/.local/bin, no ~/.qwenpaw, no daemon, no port. A bot here would start from zero.
  • dsh gives you no bot at all without plugin work: no channel, no memory, no persona. Its strength — approvals, sandbox, worktrees, session replay — is aimed at code, not at colleagues.

If Ricardo wants bots for the business

  1. Hermes still beats both for this exact job (Bot Mode: named bots with their own model, memory, skills, routines and chats, already running here with 11 cron jobs). QwenPaw is the closest second, and the only one of these two designed for it.
  2. If QwenPaw is wanted: install the current stable, run qwenpaw init, create one bot per function, bind each to its own channel, and give each its own MEMORY.md + jobs.json. Roughly a day's setup, and its beta status argues for one pilot bot first, not the whole roster.
  3. Keep dsh for what it is good at: sandboxed, approval-gated repo work from the bench.
