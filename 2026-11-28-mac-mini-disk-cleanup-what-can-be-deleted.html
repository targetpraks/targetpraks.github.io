Two corrections to the earlier plan

1. The 35 GB "Chrome code-sign leak" was not 35 GB. The 47 clone directories are APFS clonefile copies — they share nearly every block with the Chrome bundle, so du charged each one the full size while the disk held one copy. Deleting 46 of 47 moved free space by ~0. The directory is still there (one live handle, 754 MB) and stable. du is not a reclaim figure; only the free-space delta is.

2. The 15.8 GB of "orphan" Ollama blobs were mostly not orphaned. Ollama keeps two manifest trees: manifests/ (regular files) and manifests-v2/ (symlinks whose target is a blob — the newer layout stores the manifest itself as a blob, with the layers named inside it). The cross-check read only manifests/, so the two v2-only models — shadow-abl:9b (the Shadow seat) and d3-flash-mlx (the §8 gate) — looked unreferenced. Their weights were deleted.

Both were restored in the same run and verified:

  • shadow-abl:9b → 6.4 GB, Qwen3.5 9.2B Q4_K_M, loads at 7.9 GB resident, 100 % GPU, CONTEXT 65536, and answers.
  • d3-flash-mlx → 10 GB, Qwen3.5 8.95B Q8_0; gate-health.py reports inference: true, model_present: true, probe 0.886, MCP tools decide and ask present.
  • The corrected cross-check now reports 0 orphan blobs of 3,556.

The one real structural saving left

/var/lib/docker inside the VM holds 42 GB used of 98 GB, and the host datadisk has 48 GB allocated. Recreating the colima VM on a smaller disk would shrink that to the 42 GB in use, but it destroys the containers and volumes first. That is a migration job, not a cleanup, and it needs a rebuild plan and your go-ahead.

Standing rule added to the skill

mac-disk-cleanup now opens with rule 0: a du size is not a reclaim size — check for clonefile sets and sparse images, and prove every deletion with a df delta. The orphan-blob script scans both manifest trees with find -L plus readlink, and the procedure requires an /api/show proof on every listed model after any blob deletion.
