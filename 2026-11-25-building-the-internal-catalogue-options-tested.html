Building the internal catalogue — the options, tested

Summary: A catalogue is a data product, not a document. The format (website, PDF, deck, Gamma) is an output; the thing that decides whether it works is the source of truth and the sign-off. Infinity Brands already owns the source — Zoho Inventory holds 839 items, 696 of them ACDC Express, with 637 product photos, five category codes and 11 price lists. The best build is therefore not a website or a deck: it is a generator that turns that master into a frozen, numbered edition — searchable HTML for the screen, A4 PDF for print, one SHA-256 per edition for sign-off. Licence cost R0. Built and proven today, with a 343-item working edition.

The expensive part of any catalogue — a photo, a name, a category and a price per item — is already in the master. Any tool that asks someone to re-key that is a second source of truth and will drift.

Two limits found while measuring, both design constraints not blockers:

  • The image endpoint throttles hard. Six parallel image fetches triggered Zoho's per-minute block (429 code 43), which held for 15+ minutes even though the item API kept answering 200. Images must be fetched once into a cache, paced ≤ 1 request/second, and never re-fetched per edition.
  • The master moves. While this research ran, the pending 244 SKU renames were completed (17:23, 243 applied) and a second pass fixed 57 more (17:56); the EXP count went 640 → 696. An edition must be stamped with its read time and hash, because "the catalogue" is a moment, not a state. The earlier figure of 415 coded SKUs is superseded: 696 of 696 are coded now.

Why the obvious tools lose: Gamma, PowerPoint and InDesign are layout tools. They are excellent for a 12-page brand deck and wrong for 696 items that change weekly — every price change becomes a manual edit, and the deck silently becomes a second source of truth. A website built by hand has the same problem, plus hosting and code to maintain. The generated lane keeps the layout cheap and repeatable and puts the effort where it belongs: the data and the approval.

Zoho Creator (option B) is the right next step, not the first: it adds logins and real ordering, but it does not solve the catalogue-of-record problem, costs per user, and needs its own build. Zoho's own customer portal does invoices and sales orders, not a browsable catalogue — verified in their documentation — so it is not an alternative.

Five rules make it a system rather than a script:

  1. The master is the only source. The catalogue is never edited; a change goes into Zoho, then a new edition is generated.
  2. Prices come from price lists, not the page. The page shows what the list says at read time.
  3. Every edition is frozen and named: STA-UNI-20261125T180438, with a SHA-256 over a canonical item payload (sku, name, category, unit, rate, purchase_rate, status, image), sorted by SKU.
  4. Images are cached once and reused; only new items hit the API.
  5. A signed edition is immutable. Any later change creates edition n+1; the signed one stays as it was.

One property worth noting: the hash covers data only. Restyling the page changed the HTML and the PDF but left the hash identical (b3d648ba…) — so a design tweak never invalidates a signature, and a price change always does.

4. Sign-off — what actually gets approved

Three different things get signed, at three levels:

What Who How Evidence
Item change (new item, price, category, copy) Field owner — merchandising (category/copy), finance (price), warehouse (SKU/stock) Approved in Zoho before it becomes active Zoho audit log on the item
Edition (this month's catalogue as a whole) Brand owner + finance, Ricardo final Approval sheet of the diff, then signature Signed PDF + edition hash + ledger row
Customer-facing release (if ever) Ricardo Zoho Sign Certificate of completion

The mechanism that makes this cheap and honest:

sequenceDiagram
    participant B as Edition builder
    participant R as Reviewer (brand owner / finance)
    participant S as Zoho Sign
    participant V as Ledger + archive
    B->>B: freeze edition.json + SHA-256
    B->>R: approval sheet (diff only: added / changed / removed)
    R->>B: approve or reject per line, with comments
    B->>S: edition PDF + hash (Ricardo sends/signs)
    S->>V: signed PDF + certificate
    V->>V: ledger row — edition, hash, signer, date
  • Reviewing only the diff is what makes sign-off fast: 340 unchanged lines are not re-read every month; the approver sees the 12 items that moved.
  • The hash is what is signed, so a signature can never be quietly attached to a different version. Anyone can re-run the build against the same items and get the same hash.
  • Two levels of rigour: an approval ledger (edition id, hash, approver, timestamp, comments — stored in the vault and WorkDrive) is enough for internal use. Zoho Sign adds legal-grade evidence at $0.50 per envelope pay-as-you-go (free plan: 5 documents/month). Per Ricardo's standing rule, the agent prepares; Ricardo sends and signs.
  • Two adjacent review surfaces are already configured but unproven: the fleet holds a Filestage API token (visual proofing with versioned annotations — my probe reached their API but not a working endpoint map yet) and a Zoho Sign MCP endpoint is registered. Neither has been exercised end-to-end; each needs a short spike before it is relied on.

7. Risks and how the lane handles them

Risk Mitigation

Master changes while a catalogue is being approved Edition hash + read timestamp; a change means a new edition
Duplicate/legacy categories (zzUniform, zzPromotional, two empty In-stores) Fold into the six canonical codes; catalogue maps zz* to the canonical code
Per-item price lists behave differently on transactions (unmeasured) Treat the catalogue as display, the transaction as truth; measure before quoting from a subset list
Inactive items vanish from the catalogue --all flag prints them marked; decide per edition
A hand-made deck drifts from the master Only generated editions are the catalogue of record; decks are collateral

8. Recommendation

Adopt A now, and make B the roadmap item. Generated editions give Infinity Brands a single-source catalogue this week at zero licence cost, with a sign-off that names exactly what was approved. Zoho Creator earns its licence the day staff need to order from the catalogue rather than read it — then the same edition data feeds the portal. A paid PIM only becomes rational when the catalogue has to serve several external channels at once.
