Finding 1 — Constellation: nine nights with no backup, because the database it dumps is empty

backup.sh line 81 dumps constellation_dev from constellation-dev-pg. That container is up (Up 36 hours, POSTGRES_USER=owner), the database exists, and I ran the exact dump by hand at 04:00:

docker exec constellation-dev-pg pg_dump -U owner -d constellation_dev --no-owner --no-privileges
exit=0    57,418 bytes     no stderr

The dump does not fail. It produces a valid gzip of 5,655 B — under the 102,400 B floor on line 72 — so the size guard correctly refuses to promote it. That guard is working as designed; it is telling the truth about the database:

last good dump, 2026-11-06 46,445 lines · 29 COPY blocks · PositionFit 29,853 · Response 10,307 · Score 1,687 · AuditLog 1,491 · Esoteric 131

So between the 2026-11-06 03:30 dump and the 2026-11-07 03:30 run, constellation_dev was reset to an empty schema. That is why the lane has failed every night since: 7, 8, 9, 10 (twice), 11 (twice), 12, 13, 14, 15.

The live data moved. The container pair actually serving Constellation now is constellation-preview-app-1 (healthy) + constellation-preview-db-1, with DATABASE_URL=postgresql://***:***@db:5432/constellation_fixture_preview. That database is real:

constellation_fixture_preview has no backup lane at all. backup.sh only ever touches constellation-dev-pg. Eighteen thousand responses and 2,920 scores exist on a single Docker volume with no nightly dump — the exact gap that adding the constellation lane on 2026-10-15 was meant to close, now re-opened by the data changing address.

Time pressure: backup.sh line 108 runs find "$D" -type f -mtime +14 -delete. The 2026-11-06 dump is 9.0 days old and crosses 14 days in 5.0 days — the night of 20→21 November the sweep deletes the last valid Constellation backup this stack holds.

Same error for every date from 2026-10-30 through 2026-11-15. ls | grep -c tar.gz → 0: not one archive has ever been written. This is the launchd-zsh-lacks-the-removable-volume-grant failure the main backup job was moved behind the osascript wrapper to fix; this job never got the same treatment.

Consequences, both real today:

  • because set -e aborts at the failed tar, the cleanup on line 16 never runs, so 17 .work-* directories, 169 MB, are accumulating on the backup drive.
