01What exists, and why it does not fit

the app and the practice are two different instruments

The Wheel of Life already exists in three places, and they disagree with each other. The app inside Maio OS scores monthly, by hand, in whole numbers, across 8 areas. The household actually runs a weekly wheel: eight seats file a score every Sunday evening between 18:00 and 19:30, and Splinter compiles them at 06:00 on Monday into a markdown record — 4 consecutive compiles so far (wheel-2026-10-07, 10-12, 10-19, 10-26). That wheel has 9 areas and takes half points.

None of that is a scandal — the app was built as a personal monthly reflection tool, and it is good at that. The problem is that Ricardo now runs a weekly, multi-agent instrument and the software that bears its name cannot represent it. Every Monday the best data in the household is compiled into a file that no screen reads, and every screen that shows a wheel is showing a hand-typed monthly approximation of it.

The principle this PRD is built on

One wheel. The database becomes the record of what the seats filed; the compile reads from it instead of from markdown; the markdown becomes an export. Two writers with no reconciliation is how the current state happened.

Why D5 and D6 matter more than they look

The H3.0 field test of 26 October (filed separately) established two things from this household's own data: Personal Development sat at 2/10 for five consecutive weeks against an action that had failed five times as prescribed — a push, not a pull — and three areas going dark in one week was one season with one cause, not three failures. Neither reading is expressible in the current schema. Both are one field each.

03Requirements

P0 blocks the release; P1 ships with it if the week allows

R0 is a gate: nothing below can be judged until the app can hold a real week. The rest are ordered so that each one leaves the app working.

R0

A week is a first-class period

GATE

Add a period resolver that understands both shapes. Keep the existing month rows working; add ISO week keys (YYYY-Www) as an equal citizen. Store a real periodStart DateTime next to the display key so ordering, ranges and 'last week' comparisons never depend on string parsing.

Done when

  • A week key and a month key can both be written through the same action and both render on /wheel
  • The period switcher steps by the period's own unit, not by months
  • Existing month rows render unchanged after migration

Evidence today the regex in both the page and the server action rejects anything that is not YYYY-MM

schemaactionspage
R1

Scores carry one decimal place

P0

Store scores as integer tenths (scoreTenths Int, 10–100) rather than a float. Integer arithmetic keeps the existing engine honest, avoids float drift in averages, and still represents 6.5 exactly. The UI reads and writes 1.0–10.0 in half-point steps.

Done when

  • 6.5 saves, reloads and renders as 6.5 on the wheel, the history chart and the radar
  • averageScore and balanceIndex return identical results for whole-number input before and after migration
  • A value outside 1.0–10.0 or on a quarter step is rejected with a visible message, not silently rounded

R2

Nine areas, and a legal 'unmeasured'

P0

Seed romance and reconcile the names with the practice (Health &amp; Fitness → Health; Career &amp; Work → Work &amp; Career; Personal Growth → Personal Development; Physical Environment → Home &amp; Environment; Spirituality &amp; Purpose → Spirituality). Renames must preserve the key so no history is orphaned.

R3

Every score knows where it came from

P0

Extend WheelScore with owner (the seat that filed it), source (a path or link to the evidence), filedAt, verification in (verified, filed, unconfirmed, unmeasured) and evidenceNote. A manually typed score is filed by definition and says so.

Done when

  • Any score can be opened and shows its seat, its filed time and a clickable source
  • An unconfirmed score carries a visible amber badge with its reason — the Home &amp; Environment 8 is the live example
  • The history chart marks unconfirmed points differently from verified ones

Evidence the 19 October compile had to footnote that a filed 8/10 rested on Home Assistant readings that could not be produced; the app has no place to say that

R4

An area can be parked without being scored down

P0

Add state to the score: live or parked, with an optional parkedReason and reviewAfter. A parked area keeps its spoke and its history, is excluded from the average and from the two lowest, and shows as deliberately parked rather than missing.

Done when

  • Parking an area changes the average and the lowest-two list immediately
  • The wheel still draws the spoke, visually distinct, with the reason on tap
  • A parked area past its review date surfaces as a prompt, not as a failure
schemaengineui
R5

Pulled or pushed — one bit per area per week

P1

Optional channel on the score: pulled, pushed, or unset. Collected with the score, in one tap, never mandatory. It is the only field that lets the app distinguish an area that is moving on its own from one being held up by hand.

Done when

  • The value round-trips and is visible on the score row
  • A weekly summary lists every area pushed for three or more weeks running — the Personal Development pattern by name
  • Leaving it unset is a normal state and renders as nothing, not as a default
schemaui
R6

The quadrant roll-up

P1

Add quadrant to LifeArea — mind, body, spirit, vocation — and a second chart that averages live areas per quadrant. This is the one thing worth keeping from Dan Koe's model: not the levels, the shape.

Done when

  • The quadrant chart matches a hand calculation on the current data (Mind 2.0 · Body 4.5 · Spirit 4.0 · Vocation 6.3)
  • Adding or parking an area changes it without a code change
  • The screen states which areas feed each bar and how many are unmeasured
schemachart
R7

One ingest command, idempotent

P0

A single npm run wheel:ingest -- --from &lt;dir&gt; that reads the seat score files, validates them against the same zod schema the UI uses, and upserts by (area, period, owner) with source recorded. Dry-run by default; --write to commit.

Done when

  • Running the same week twice writes nothing the second time and says so
  • One malformed file fails the whole run with the file and line named, and writes nothing
  • Ingesting wheel-2026-10-07, 10-12, 10-19, 10-26 reproduces the four compiled weeks exactly — every score, every owner, every note

Evidence this is the requirement that ends the split between the markdown wheel and the app wheel

R8

The compile reads the database

P1

Change Splinter's Monday 06:00 compile to read from the wheel database instead of eight agent files, and to write the markdown record as an export. The database becomes the source of truth; the markdown remains the human-readable artefact and the vault handoff.

Done when

  • A compile run produces the same wheel-&lt;date&gt;.md shape from SQLite
  • The two lowest areas are computed by the same lowestAreas function the app uses
  • A week with no ingest is labelled as such in the export rather than rendering as an empty wheel

04The data model change

one migration, additive where possible

model LifeArea {
  ...existing...
  quadrant   String?   // mind | body | spirit | vocation
}

model WheelScore {
  id            String   @id @default(cuid())
  areaId        String
  period        String   // display key: YYYY-Www or YYYY-MM
  periodStart   DateTime // real ordering key
  periodKind    String   // week | month
  scoreTenths   Int      // 10..100  (replaces score Int)
  state         String   @default("live")     // live | parked
  parkedReason  String?
  reviewAfter   DateTime?
  channel       String?  // pulled | pushed
  owner         String?  // the seat that filed it
  source        String?  // evidence path or link
  verification  String   @default("filed")    // verified|filed|unconfirmed|unmeasured
  evidenceNote  String?
  note          String?
  filedAt       DateTime?
  createdAt     DateTime @default(now())
  updatedAt     DateTime @updatedAt

  @@unique([areaId, period, periodKind])
  @@index([periodStart])
}
Migration order. Each step is reversible until step 4.
StepChangeReversible?Note
1Add nullable columns to WheelScore and quadrant to LifeAreaYesNothing reads them yet
2Backfill scoreTenths = score * 10, periodStart from the existing month key, periodKind = 'month'YesVerified by recount: every row has a tenths value
3Seed romance; apply the five renames against preserved keysYesKey is the join, not the name
4Drop score; add the new unique indexNoOnly after the app reads scoreTenths everywhere
5Ingest the four compiled weeks; reconcile against the markdown by hand onceYesThe one-off proof that app and practice agree

The migration touches a live database

apps/wheel/dev.db is a real SQLite file holding every score ever typed into the app. Take a copy before step 4, keep it outside the repo, and restore it once as a drill — an untested backup is a rumour. No destructive migration step ships without that copy existing.

05How it will be verified

the acceptance is performed, not asserted

  1. Schema and engine: npm test and npm run typecheck green, plus new unit tests for the period resolver, tenths arithmetic and parked-exclusion from the average.
  2. Migration: a scripted recount — row count before and after, sum of scoreTenths equals ten times the sum of the old score, zero rows with a null periodStart.
  3. Ingest: ingest wheel-2026-10-07, 10-12, 10-19, 10-26 into a scratch database and diff the result against the four markdown files, area by area. Any mismatch is a defect in the ingester, not a tolerable difference.
  4. Rendering: the real page, in a browser, at 1440 px and at 390 px, light and dark — with a screenshot filed as evidence for the phone width. Radar labels are checked by measuring their bounding boxes against the viewBox, not by eye.
  5. Honesty states: three seeded fixtures — one unmeasured area, one unconfirmed score, one parked area — each of which must be visibly distinct on the wheel, in the average and in the lowest-two list.

Definition of done for the release

A Monday compile can be produced end-to-end from the database; a week with a parked area and an unconfirmed score renders correctly on a phone; and every number on screen can be traced back to a seat and a source with one tap.

06Non-goals

what this deliberately does not do

  • No level scoring. The twelve-slice HUMAN 3.0 Metatype score is excluded on purpose: it is unfalsifiable by construction, and a number that cannot be wrong is not a measurement. Only the four-quadrant grouping and the pull-or-push bit are adopted.
  • No touching thinking profile, ikigai, goals or the board. Those are separate working features inside the same app and this PRD does not re-open them.
  • No new seat for Romance in this release. The area becomes measurable; who measures it is a decision, not a task.
  • No public build. The wheel stays companion-only, as the rest of the Life section is.
  • No Social Contribution. Splinter holds it and no score has ever been filed; it is out of scope until there is a practice behind it.

08Two decisions are yours

cheap to answer now, expensive to guess

Everything else in this PRD is engineering. These two change what the product is, so they are not mine to take.

#DecisionOptionsMy recommendation
D-01Where is the source of truth for a score?(a) the database, with the markdown as export — needs R7 and R8 in one release; (b) the markdown files, with the app read-only(a). The seats already write files every Sunday; making the database the record is the only version where a screen and a compile cannot disagree.
D-02Does Romance get its own seat, or stay unmeasured?(a) a new seat scores it weekly; (b) it stays in the wheel as an explicitly unmeasured spoke; (c) it leaves the wheel entirely(b) for now. The H3.0 report showed one eighth of the wheel inferred from nothing — showing that honestly is worth more than inventing a number for it. Revisit if you want it measured.
