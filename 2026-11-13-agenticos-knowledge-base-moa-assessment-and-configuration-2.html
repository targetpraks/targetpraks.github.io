1. Verdict

The section was structurally sound and under-supplied, and now it is smaller, cleaner and correctly named. Twenty-three bases remain: one per authorised unit, one per forum, one for the company, five artifact lanes. Every surviving bot is bound to exactly one base and returns the surrounding text of what it matches.

What was wrong was inside the bases: role documents chunked at three to five times the size their headings imply, titles carrying retired codes that then appeared in citations, nine duplicate copies of unit content in the company base, and one base holding another unit's workbook. All of that is fixed.

What still limits the section is not configuration — it is corpus. Most bases hold one document, because WorkDrive read access is still refused, so the SOPs, brand manuals and policies that would make these bots useful cannot be loaded yet.

4. Two faults found while executing

The embedding runtime fell off the network

Every new document failed to index with a name-resolution error. The documents were not the problem: the dedicated embedding container had been brought up alone and sat on its own bridge (agenticos_embed), while the API and worker were on backend, render and browser only — so ollama-embed stopped resolving inside them.

Fixed live with a network attach, and made durable in docker-compose.yml: both services now declare the embed network, which carries the fixed name the embed overlay uses. docker compose config validates. Without this fix every upload after the last container restart would have failed quietly into error.

The "deployment-level hybrid switch" is not a switch

enable_hybrid_search exists and defaults to false, but nothing in this build can set it:

  • app/services/rag/config.py:242 — the field, default False.
  • app/core/config.py, computed field rag — returns a bare RAGSettings(), explicitly "with nothing of the deployment's in them". No environment variable reaches it.
  • app/services/ingestion_config.py:465 — rag_settings_for() builds the settings object from the collection's config and never passes enable_hybrid_search.
  • app/services/rag/retrieval.py:57 reads it, and :107 _bm25_search is real — a BM25 rerank over the vector store's already-filtered candidates, fused by RRF, needing no new index.

So the wiring is one line in vendor source, not an operator setting. Patched into a running container it would vanish on the next image pull; mounted as a file it would silently pin old code over a newer image. Recorded here as a change request for the platform image rather than hacked in: carry the field through ingestion_config per base, or read it from a real settings source — retrieval picks it up on the next query, with no re-ingestion.

7. Rules now in force

  1. One base per authorised unit, named on the authority label, holding that unit's material only.
  2. The company base holds cross-unit material only — never a copy of a unit slice.
  3. Ingestion config is forward-only: a chunking change is not live until its documents are re-ingested.
  4. Markdown for narrative documents, recursive for tables and registers. A departure gets a written reason.
  5. No document title may carry a retired form. A document cannot be renamed — replace it, then remove the old row.
  6. Re-ingest on a source change, a naming change or a chunking change — never to "refresh".
  7. A forum base is created with a frame that names its owner, or not at all. "Empty until the pack arrives" needs the frame to say what is missing.
  8. New base: authority name, standard profile, one unit bot, knowledge-reach proof.
