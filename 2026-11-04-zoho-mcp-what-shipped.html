The state it started from

95 Zoho MCP servers existed and answered — but reaching them depended on the client. MetaMCP held five namespaces; Claude and Codex could not hold 54 MB of schema, so 25 hand-packed stdio bins carried the catalogue locally; every status question needed a fresh session; and 44 servers were unauthorised, leaving 7,955 of the 14,550 tools dark.

What shipped

1. One surface, three verbs (zoho_search_mcp.py)

search_tools · describe_tool · call_tool over the whole estate. The index is built from the local server catalogues, so search costs nothing and needs no network; only call_tool goes upstream.

  • Index verified at 14,550 tools across 95 servers.
  • Search verified: "crm leads list" returns ZohoCRM_getLeadsRecords first, "invoice" and "projects tasks" resolve too.
  • call_tool verified live: real leads from Zoho CRM (Arvind Pandey, two records, page token returned).
  • --compact drops prose at every depth: a 345,481-byte schema becomes 141,461 bytes (59 % saved) while keeping property names, types and required fields.
  • --read-only exposes 6,565 read verbs and refuses writes by name: "read-only mode: ZohoCRM_createLeadsRecords is a write tool and is not exposed here."
  • Token bucket (8/s default) and exponential backoff on 429/5xx wrap every upstream call.

Wired into every harness: Hermes (global + 31 profiles), omp, dsh (all 7 profiles), Claude Code, Codex. Proof from the client side: Codex called search_tools and answered ZohoCRM_getLeadsRecords, 3; Hermes lists zoho-search all tools enabled; Claude shows zoho-search … Connected.

2. A status page that answers without a session (zoho_estate.py)

status collects live namespace counts, per-server authorisation, bin coverage, container health and the keep-alive state; dashboard renders it to a self-contained HTML page.

  • Namespace measurement is serial with a retry on purpose: five concurrent fetches contend inside MetaMCP and return partial lists — measured 491 tools instead of 2,024 for one namespace, and 0 for another. Serial measurement returned the exact 2,524 / 2,024 / 3,679 / 4,242 / 2,081 = 14,550 twice in a row. The page now flags any namespace short of its expected count, which is the silent-drop detector the estate previously lacked.

3. Scheduled maintenance (cron, verified)

When Job Effect
02:40 daily zoho-backup.sh pg_dump of Metamcp, gzip, 7-day retention — first run produced 3.2 MB
03:10 daily zoho-probe.sh real tools/call per server, rewrites auth state
07:00 daily zoho-dashboard.sh refreshes the status page
04:00 Sunday zoho-refresh.sh probe → re-pack bins → re-warm caches
every 10 min zoho-keepalive.sh keeps upstream Zoho sessions warm for all five namespaces

Scheduling runs on the Hermes gateway scheduler, not crontab: macOS TCC blocks cron from writing to the external volume at all (verified — every write returned "Operation not permitted" while the job reported success). The gateway runs in the user session; the 16:10 keep-alive tick was observed returning exact counts (2,524 / 2,024 / 3,679 / 4,242 / 2,081) into keepalive.log. The old launchd keep-alive agent is retired (plist renamed .disabled, launchctl bootout exit 0).

4. Bin configuration that maintains itself (apply_zoho_bins.py)

The 25 bins are now generated from zoho_bins.json into both Claude and Codex, idempotently, with the three-tool search server preserved. Two real defects were caught and fixed here: duplicated interpreter in the args (bins silently failed to start, Codex saw 0 tools) and a regex that deleted the search server along with the bins. After the fix, Codex counted 14,553 tools (14,550 bin tools + 3 search verbs).

The 43 servers Zoho will not connect — and the lane that does

A per-server check that fetches each server's own tool list and calls a tool it actually owns gives the honest split: 48 answer, 43 return "Connection not authorised", 4 are blocked by the product itself (sign — "Zoho Sign MCP has been disabled", site24x7 — "API is not supported for this pack", endpointcentral-2/3). The 43 are a Zoho-side connection cap, not a configuration fault, and they hold 6,151 of the 14,550 tools.

So the estate does not depend on them. The API lane (zoho_api_mcp.py, its own grant, 98 scopes, already wired to Hermes, Claude and Codex as zoho-api) reaches those services over REST. Verified live today, with real HTTP codes:

Service REST call Result
Projects GET /portals 200 — real portals, while MCP says "not authorised"
Desk GET /tickets 200
Calendar GET /calendars 200
Inventory GET /items 200
People GET /forms 200
CRM GET /Leads?fields=… 200 (the API needs fields; the MCP shard does not)
Books GET /organizations 200 — "Infinity Brands"

Still short on the API side, recorded rather than assumed: sign needs a re-grant with ZohoSign.documents.READ (403), books /invoices rejects organization_id as a query parameter (400), mail 404s on both known account paths, workdrive 405/415, sheet and tables 400 on the guessed paths. Each is a scope or path problem on a live connection — not a dead end.

The lesson worth keeping: a server answering "not authorised" over MCP says nothing about whether its data is reachable. Projects proved that in one call.

Still open

  1. 30 servers unauthorised — 6,102 tools. Heaviest: crm-2/3/4, inventory ×3, site24x7 ×3, books-3, mail. Console work only; the nightly probe reports progress.
  2. Keep-alive — solved, no action needed. The launchd agent was retired and replaced by a 10-minute Hermes cron job, verified live with exact counts. Helper scripts were moved out of the agent scratch directory (pruned after 24 h) to ~/.local/bin/zoho_tools/, so the schedules survive.
  3. Claude Code weekly limit blocked conversational verification until 2026-11-05 14:00; the bin connection and a live CRM call were verified before the limit hit.
  4. Namespace consolidation (one namespace for all 95 servers) was not attempted: the five-way split is exact, and each measurement costs a full fan-out. Revisit only if the pool ceiling proves stable over a week of the new status page.
